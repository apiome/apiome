# Apiome 10-2026 RC7

We continue to improve the platform based on your feedback with improvements and new features!

---

## Features/Improvements

- Suite Access:
  - **Designer** and **Developer** now show in the **Build** section and on the launcher only for a user an administrator gives **Suite Access** (admin console → **Users** → ⋮ → **Grant Suite Access**). A license, including the free plan, no longer shows them
- Version:
  - The version shown on the home page, in the user menu and on **Help & docs** now names its release candidate (`RC7`)
- Import:
  - Postman collections — a Postman Collection v2.0/v2.1 is now read by the same engine as Insomnia, Bruno and HAR: requests that share a method and path become one operation, schemas are inferred from example bodies, folders group operations, and saved credentials are removed. The **Postman Collection** card converts through it too, so the OpenAPI it imports has schemas and lists what was left out
  - Array merge — with **Additive merge** or **Override merge** selected on the **Changes** step, **Arrays** decides what happens to a list both sides define (`enum`, `required`, `examples` …): **Replace** keeps the merge's list, **Append** adds the other side's items, **Deduplicate** does the same without repeats. **Done** says how many lists were combined
  - Override merge — the **Changes** step's **Merge strategy** also offers **Override merge**: like additive, nothing in the latest version is removed, but wherever both define the same property, operation or security scheme, the spec's definition wins. **Done** says what was merged, added, updated and kept
  - Additive merge — when an import adds a new version to an existing project, the **Changes** step's **Merge strategy** can keep everything in the latest version and add only what the spec newly defines (schemas, properties, paths, operations). Nothing is removed or overwritten, and **Done** says what was merged and kept
  - URL imports stay up to date — a project imported with **URL Import** keeps following its URL: Apiome checks it every five minutes and, when the document changed, imports it into the same project with the options you chose, as a new date/time version. An unchanged or older document is skipped, a version you edited in Apiome is never overwritten, and a URL imported with credentials is not refreshed
  - Version already taken — importing into an existing project at a **Version** it already has no longer fails: the import is added as the next free sub-version (`2.5.0b`, `2.5.0c` …). The **Changes** step says which one, and **Done** lists it
  - References that won't resolve — the **Preview** step now warns when a schema you tick references a schema the spec doesn't define, or a URL Apiome doesn't fetch, naming each one. The import still runs and keeps the reference as written
  - Property conflicts — the **Preview** step now warns when the schemas you tick use one property name with different definitions (for example `status` as two different enums), listing every definition and the schemas that use it. The import still runs: each definition becomes its own library property (`status`, `status_1`)
  - Schemas that other schemas use — on the **Preview** step, ticking a schema also ticks every schema it references (`$ref`), and a schema that a ticked schema references can't be unticked: its row says **Required by …** until you untick the schema that uses it. An import can no longer leave a reference pointing at a schema it skipped
  - Changes step — importing a spec whose slug matches an existing project now stops at **Changes** before **Import**: added, changed, removed and breaking counts against the project's latest version, a filterable list of every changed path, operation, schema and property (breaking first), and a **Side-by-side spec** tab with the latest version on the left and the incoming spec on the right. Breaking changes are a warning, never a block — **Continue to import** is always available, for a dry run too
  - Catalog dry run — **Import to catalog** has a **Dry run** button on the **Options** step: it shows the detected format, where the import would land and why, the catalog item's name and slug, its contents, quality score and fingerprint, and saves nothing. **Continue** still goes on to **Quality** and **Import**
- Catalog:
  - FHIR servers — a FHIR server's CapabilityStatement (its `/metadata`) now imports as the server's API, a service per resource with the interactions it declares, and FHIR items say whether they are R4, R5 or R6. **Live refresh** can re-read a FHIR server's `/metadata` (**Discover with → FHIR server /metadata**)
  - Re-upload — an item imported from an uploaded file now says when it **may be stale**: a banner names the file and how long ago it was uploaded (90 days by default). **Re-upload…** imports the current copy with the same import settings the first upload used, adding a version only when the file changed. The **Uploaded file** card on **Provenance** shows the age and the settings a re-upload uses
  - Search box — the Catalog's search now says what it matches, **Search name, slug, format, protocol…  ( / )**, and is wide enough to show it; the **Cards / Table** switch moves to the next line of the toolbar
  - Live refresh — a GraphQL or gRPC catalog item can be re-checked against its live endpoint (GraphQL introspection or gRPC server reflection) **Hourly**, **Daily**, **Weekly** or on demand: set it up from the **Live refresh** card on the item's **Provenance** tab (**Set up refresh…**), with an optional credential stored encrypted and never shown again. The card says whether the source is **Up to date** or has **Changed**; a check that fails shows **Last check failed** with the reason, backs off, and never changes the item. **Check now** runs one at once, an administrator can pause every check in the workspace, and the CLI has `apiome catalog refresh` and `apiome catalog refresh-policy`
  - Drift alerts — when a live refresh adds a version, the change is graded **Breaking**, **Dangerous** or **Safe**: the catalog card shows a drift badge, the item shows a banner (**See what changed** opens **What changed** on the **Versions** tab, with every change and the two versions ticked for the diff; **Dismiss** clears it), and the workspace's webhooks and the item's owner team are told. **Drift alerts** on the Catalog page chooses which grades are announced (safe drift only badges by default) and whether they go out right away or in one daily digest; `apiome catalog drift` and `apiome catalog drift-alerts` do the same from the CLI
  - Drift email — ticking **Email me about drift too** in **Drift alerts** now emails the item's owner team: each alert right away, or one email per member per daily digest listing their team's items. It needs a mail sender on the server; without one, the other alerts still go out
  - Version retention — the **Live refresh** dialog has **Keep versions** (50 by default): refresh keeps that many of the versions it adds and prunes older ones, never a tagged, breaking-drift or converted version or one you imported yourself. When **What changed** compares with a pruned version it says so and diffs against the nearest kept one; `apiome catalog refresh set --keep-versions` does the same from the CLI
  - Convert button — the conversion preview's button now says what it does: **Convert & create Project** on a first conversion, **Re-convert** when the item has been converted before (a re-convert adds a version to the same project). The item's primary **Convert to OpenAPI Project** action opens the preview
- Export:
  - JSON Schema card — the **Export** dialog's **JSON Schema** card now badges a JSON Schema item **lossless** (it said **types-only**); an item with operations stays **types-only**. Pick the card to set **Draft**, **Packaging** and **Mode**; the CLI exports it with `apiome export jsonschema`
  - Overlays on export — the **Export studio** has an **Overlays** step: add OpenAPI Overlay files (1.0, 1.1 or 1.2) and set their order, and the export applies them to the version's OpenAPI document before anything else runs, so a partner gets their own servers, descriptions or `x-` extensions without a fork. **Verify** and **Review** list every value an overlay changed and any action that matched nothing (`overlay.unmatched-target`); the fidelity, lint grade and export policy describe the overlaid document. The CLI takes `--overlay FILE` on `apiome export`
  - Round-trip diff — the round-trip check has two views: **Model diff** (what changed in the API, with each predicted drop marked seen or not seen) and **Text diff** (the exported file beside the same file read back and exported again, side by side). Start it from the **Fidelity** tab with **“See what a round-trip changes”**
  - Healthcare targets — **Export studio**'s **Target** step files **FHIR** and **HL7 v2** under a new **Healthcare** heading; the FHIR card picks **fhir_version** (`R4` or `R5`) and **packaging**
  - Fewer failed exports — a format that needs an HTTP operation (Kong, Gateway API, Envoy, Istio, Traefik, Apigee, AWS API Gateway, Azure APIM, Hoppscotch, Thunder Client, `.http`) or a record type (ODCS, Kafka Connect) is greyed out with the reason for a source that has none, instead of failing; GraphQL, Avro, ASN.1 and Kafka Connect exports from many more catalog formats now succeed, and say what they had to rename or approximate
  - Nothing to export from — a catalog item whose source file wasn't kept (or wasn't stored because it contained credentials) now says so in the **Export** dialog, with a **Re-import** button that opens **Import to catalog**, instead of an error. A format this deployment can't run is greyed out with the reason and is never offered and then failed
  - Every file in the .zip — exporting to a format that writes several files (an Avro or Protobuf schema set, for example) from the **Export** dialog now puts every file in **Download all files (.zip)**, with a `manifest.json` listing them; before, the .zip held only the main file. Single-file formats are unchanged
  - Safer downloads — an exported file named in any script (`注文-api.jtd.json`) now downloads under its own name instead of failing, and every file and folder in a download stays inside the folder you unpack it into, whatever names the source uses
  - Protobuf and Thrift from OpenAPI — exporting an OpenAPI project to Protobuf or Thrift now writes files that compile: `integer`, `number` and `boolean` fields become `int32`/`int64`, `double`/`float` and `bool` (the schema's `format` picks the width), and Thrift fields get their own ids instead of all being `1`
  - Stable Thrift field ids — exporting an item to Thrift again keeps every field's id, like Protobuf; a field added later gets a new id, and an id of a removed field is never reused
  - Cap'n Proto export compiles — exporting any item to Cap'n Proto now writes a `.capnp` schema that `capnp` compiles: fields, enum values and methods numbered `@0`, `@1`, … with no gaps, a file `@0x…` id, unions, maps and interfaces, and names in Cap'n Proto's style; every later export keeps the same numbers and file id, and a removed field stays as `obsolete<Name>`
  - CORBA IDL exports are checked by an IDL compiler — omniidl for the `corba` profile, Cyclone DDS idlc for `dds`; a compile error quotes the compiler's message and line
  - FHIR export checks list every issue — each validator error, or each broken structural rule when the server has no validator, is its own finding with its resource path
  - OData exports check every reference and key before download — each OASIS schema violation is its own finding, every `$Type` and `$Key` must resolve, and multi-schema OData items now export with references that resolve
  - OpenRPC exports check every reference before they are offered — each meta-schema violation is its own finding with its pointer, a `$ref` to a missing component fails, and the document must import again
  - Postman exports list every schema violation — each break of the Collection v2.1.0 schema is its own finding with its JSON path, and the collection must import again before download
  - Thrift exports are compiled and read by a second parser before download — a compile error quotes the compiler, thriftpy2 must agree with the importer on every type and field id, and the export must import again
  - XSD exports are built by a schema processor before download — every `xs:import` must be in the export, an XSD 1.0 export must build under the 1.0 and 1.1 processors, and the export must import again
  - JSON Schema exports check every reference before download — each document passes its draft's metaschema, every `$ref` into the export resolves (also between `per-type` files), and each document imports again
  - Smithy exports are validated by the Smithy CLI before download — an `ERROR` or `DANGER` event names its validator, shape, line and column, and a model that does not import again is not delivered
  - API Blueprint exports must pass drafter with no warnings — a drafter error or warning names its code, line and column, and a document that does not import again is not delivered
  - OMG IDL fidelity report — a CORBA IDL export keeps a maximum string length or list size as `string<N>` / `sequence<T, N>`, writes other constraints as comments, and its report follows the profile: under `corba` HTTP operations lose their method, path and status codes and channels are dropped; under `dds` operations are dropped and each channel is a DDS topic named in a comment
  - Thrift fidelity report — a Thrift export now writes each field's constraints as a `// constraints: …` comment, and its fidelity report names every change: nullable fields written optional, HTTP operations written as RPC methods with their method, path and status codes dropped, event operations and channels dropped, inherited fields flattened into one struct, and the field ids and names Apiome assigned
  - API-client export cards — the **Export** dialog shows **Postman**, **Insomnia** and **Bruno** cards, each with the fidelity badge for this version, and **Bruno** marked multi-file; the **Postman** card's **Flavor** writes the same collection for Insomnia or Bruno. `apiome export postman --flavor insomnia|bruno` does the same from the CLI, which unpacks a Bruno bundle into the `--out` folder. On a public version page, a multi-file export now downloads every file as a `.zip`
  - Insomnia and Bruno export — any HTTP API exports as an Insomnia v4 export (a workspace with folders, requests and a base environment) or a Bruno collection (`bruno.json` and one `.bru` file per request, delivered as a `.zip`); credentials are empty or secret variables, never values, and the export is read back by Apiome's own Insomnia or Bruno importer before download. The **Postman** target's `flavor` option writes the same files
  - RAML fidelity report — exporting a GraphQL, gRPC, event or data-schema item to RAML now warns **RAML captures REST only** at the top of the report, with the operations and channels that are not written; the report also names what reads back differently (services merged into one API, renamed types, properties numbered by position, source details on types and parameters)
  - RAML exports are validated by AMF and imported again before download — a RAML 1.0 violation names its rule, line and column, and a document that does not import again is not delivered
  - TypeSpec exports are compiled to OpenAPI before download — a compile error names its file, line and code, and an export whose compiled OpenAPI does not import is not delivered
  - WSDL exports are checked before download — the `.zip` must hold every schema the WSDL imports, pass the WS-I checks, validate against the WSDL 1.1 schema with every reference resolving, and re-import; a bundle that fails is not delivered, and one-way and rpc-style operations of imported WSDL now export correctly
  - WSDL export is valid from any source — exporting to WSDL now writes a `.wsdl` and its `.xsd` types (or one file with **layout** `single`) that XML tools and the WS-I checks accept: 64-bit integers and dates keep their XSD types, lists repeat, optional fields are `minOccurs="0"`, lengths, ranges, patterns and enums become facets, and each operation's parameters, body and error responses become its SOAP request, response and faults; renames, the target namespace and anything XSD cannot express are listed in the fidelity report
  - WADL export validates — exporting to WADL now writes a `.wadl` that passes the W3C WADL schema and a linked `.xsd` grammar (or one file with **layout** `single`): query and header parameters, status codes, error responses and media types are written, operations on `/` are kept, and operations WADL cannot carry, cookie parameters, status ranges, extra servers and gateway details are listed in the fidelity report; WADL imports now read method request parameters and an included grammar, so a WADL item round-trips unchanged
  - RAML export is valid RAML 1.0 — exporting any item to RAML now writes a `.raml` that starts with the `#%RAML 1.0` header RAML tools require: fields keep their order, 64-bit integers and dates their types, constraints become facets, unions, maps and aliases are written, and each method gets its query parameters, headers, operation name, media types and error responses; the export is checked with AMF when the server has it, and operations RAML cannot carry, cookie parameters, status ranges, extra servers, formats and renamed types are listed in the fidelity report
  - Postman export is ready to run — exporting any HTTP API to Postman now writes a Collection v2.1 that passes the published schema: requests grouped in folders by tag or service, every server as a collection variable (`{{baseUrl}}`), example request bodies and saved example responses built from the schemas, and Bearer, Basic, Digest, API key and OAuth 2 auth with empty credential variables; choose **folder_strategy**, **variable_style** and **example_depth** in the export options, and a collection imported from Postman exports back unchanged
  - API Blueprint export reads as documentation — exporting any item to API Blueprint now writes a `.apib` that starts with `FORMAT: 1A`: each action keeps its description, query parameters (in the URI), path parameters, request media type and one response per status code, and data structures keep their field order, `required` members, descriptions and defaults; the export is checked with drafter when the server has it, and validation rules MSON cannot express, operations API Blueprint cannot carry, header and cookie parameters, status ranges and renamed types are listed in the fidelity report
  - Export guides — **Help & docs** finds the **Export studio** guide again and a new **Export catalog items** guide: the **Export** dialog, the studio, bulk export from the Catalog and the CLI side by side, with each target's fidelity tier for a REST API, an RPC service, an event API and a set of types
- API Formats:
  - Adds formats:
    - Bruno collection import — a Bruno collection folder (`bruno.json` and its `.bru` files) imports as one REST API from an archive or straight from git, with the same result either way: folders as operation groups, requests as operations with inferred body schemas, `{{baseUrl}}` as a server variable and whole-variable parameters with their value as default; credentials and secret variables are never kept, and scripts and tests are listed in the coverage ledger
    - Insomnia collection import — an Insomnia v4 (JSON) or v5 (YAML) export and its environment files become one REST API: folders as operation groups, requests as operations with inferred body schemas, `{{ _.baseUrl }}` as a server variable and whole-variable parameters with their environment value as default; saved credentials, secret variables and cookie jars are never kept, and scripts, template tags, gRPC and WebSocket requests are listed in the coverage ledger
    - HAR capture import — save your browser's devtools Network log (or a proxy capture) as HAR and catalog the API it called: repeated calls become parameterized operations with request and response schemas inferred from the traffic, page assets and analytics are left out, each host becomes its own catalog item, and cookies and credentials are never kept
  - Collection source cards — **HAR (inferred)**, **Insomnia collection** and **Bruno collection** each have a card in **Import to catalog** (HAR with an activity icon), take a file or a `.zip` / `.tar.gz` archive, and import from the CLI with `apiome import har`, `apiome import insomnia` and `apiome import bruno`. A single Bruno `.bru` request is no longer mistaken for an `.http` file
  - RAML includes and libraries — a RAML API split across files imports whole: types pulled in with `!include` and the types of `uses` libraries (as `alias.Type`) join the catalog item, references that leave the upload are refused, and a missing file or invalid document says exactly what and where
  - RAML resource types and traits — a RAML API that shares shapes through `type:` and `is:` imports with them applied: each operation carries the headers, parameters, bodies and responses they add (with `<<parameters>>` filled in), bodiless responses such as `204` keep their status, the operation records which resource type and traits shaped it, and an OpenAPI export keeps every response under its own status code
  - Thrift file sets — upload a `.zip` / `.tar.gz` of a Thrift API split across files and every `include`d file joins the catalog item: `shared.Money` links to its definition, services that `extend` another record it, diffs between versions grade fields by their Thrift id (a rename that keeps the id is dangerous, a reused id breaking), and a Thrift lint pack checks namespaces, `required` fields, duplicate ids, enum numbering and `oneway` methods
  - Smithy multi-file models — upload a `.zip` / `.tar.gz` of a Smithy model split across files and the Smithy CLI assembles it into one JSON AST before cataloging: namespaces spread over files and shapes from other namespaces join one catalog item, and the item records the model's `$version`, namespaces and source files. A Smithy JSON AST (`.json`) imports on its own too
  - TypeSpec projects — upload a `.zip` / `.tar.gz` of a TypeSpec API split across `.tsp` files and the TypeSpec compiler turns it into OpenAPI, which is cataloged (with the server now shipping `@typespec/http`, `rest`, `openapi3` and `versioning`); a project that does not compile lists each error with its file and line, and archives of RAML, Smithy, Thrift and TypeSpec files now find their entry point instead of being refused
  - TypeSpec `tspconfig.yaml` — a TypeSpec project's `tspconfig.yaml` now sets the emitted OpenAPI version and options (`omit-unreachable-types`, `safeint-strategy`, …), a single `.tsp` with its config compiles as a project, every setting left out is listed on the catalog item, and `apiome import typespec ./my-api/` imports a project folder from the CLI
  - OData CSDL JSON — OData v4 metadata imports in its JSON form as well as XML, every v4 document is checked against the OASIS CSDL schema, and a document that strays from it still imports with each problem listed on the catalog item and reported by the new `odata.csdl-schema` lint rule
  - Smithy from the CLI — `apiome import smithy` takes a `.smithy` file, a JSON AST, an archive or a model folder (packed for you, build output left out), and the Smithy card accepts the same files
  - OData live discovery — `apiome import odata --discover <service root>` imports a running OData service's `$metadata` (a `$metadata` URL or SAP `sap-client` query works too), and OData now counts among the live-discovery formats
  - WSDL live fetch — `apiome import wsdl --discover <service URL>` imports a running SOAP service's WSDL (`?singleWsdl` first, so WCF services arrive fully inlined), a WSDL split across files with `wsdl:import` now imports whole, and archives of `.wsdl` / `.xsd` files find their root
  - OpenRPC live discovery — `apiome import openrpc --discover <endpoint>` imports a running JSON-RPC service's OpenRPC document through `rpc.discover`, diffs now grade parameter changes by position, name and requiredness, and a new `openrpc` lint pack checks duplicate methods and parameters and parameter order
  - OData validation — OData metadata is now checked against the OASIS CSDL XML schemas too (catching misspelled attributes the JSON form cannot see), and every name it uses is followed: an undeclared type, entity set, partner, binding or operation, or an entity type with no usable key, is listed on the catalog item and reported by the new `odata.unresolved-reference` and `odata.entity-key` lint rules (v2, v3 and v4)
  - Avro lint pack — Avro schemas (`.avsc` and IDL) are now linted as written: a default that is not a value of its type (or of a union's first branch), a nested or repeated union branch, an optional field written `[T, "null"]` or missing `"default": null`, an invalid or clashing alias, and a `doc` tools would drop are each reported by a new `avro.*` rule
  - Avro fingerprints — every Avro schema now records Avro's Parsing Canonical Form hashes (CRC-64-AVRO and SHA-256) and a semantic hash that also covers `doc`, `default`, `aliases` and `order` for each type it declares; a `doc`-only edit changes the semantic hash but not the PCF, and mints no new catalog version
  - Avro compatibility — Avro schemas are now checked the way a Confluent Schema Registry checks them: comparing two versions grades each change by whether new readers can read old data (breaking) or only old readers fail (dangerous), and the schema registry enforces `BACKWARD`, `FORWARD` and `FULL` (and their `TRANSITIVE` forms) on Avro subjects, refusing an incompatible version with Confluent's own messages
  - REST hypermedia conventions — an OpenAPI, Swagger or RAML API that declares JSON:API, HAL, HAL-FORMS, JSON-LD or Hydra media types is tagged with them: the catalog item lists each convention with its resource types, link relations or templates, a **Convention** filter appears on the Catalog to narrow the list to one, and a new `rest-conventions` lint pack checks each body against its convention (resource objects, `_links.self`, link `href`s, `_templates.default`, `@context`, Hydra members)
  - z/OS Connect binding — a z/OS Connect descriptor, the copybooks that declare its request and response structures, and the OpenAPI it targets are suggested as links to each other, and the descriptor's catalog item shows a **z/OS Connect binding** panel: each operation with its COBOL structures, the copybook items that declare them and the OpenAPI that defines it
  - WS-I lint pack — SOAP / WSDL descriptions are now checked against the WS-I Basic Profile: `encoded` messages, bindings that mix rpc and document styles, document-/rpc-literal bodies with the wrong parts, operations a receiver cannot tell apart, shared `soapAction`s, and imports that do not resolve are each reported by a new `wsi.*` lint rule
  - TypeSpec compiler warnings — a compiled TypeSpec project now runs TypeSpec's built-in linter rules, and every warning the compile reports (such as `deprecated` or `@typespec/http/op-reference-container-route`) is kept on the catalog item with its file and line and reported by the new `typespec.compiler-diagnostic` lint rule
  - RAML lint pack — RAML APIs are now checked by AMF's validation of the RAML profile on every import, each problem reported with its file and line (a self-contained document AMF rejects now imports, with its violations as errors), plus hygiene checks for undeclared `securedBy` schemes, unused base-URI and URI parameters, and methods without responses
  - API Blueprint lint pack — API Blueprint imports are now also run through drafter, the reference API Blueprint parser, and each warning (a parameter missing from the URI template, a duplicate resource, an action with no response) or error (an undefined base type) is reported with its line by a new `apiblueprint.*` lint rule
  - Smithy lint pack — Smithy models are now validated by the Smithy CLI on import with the `smithy-linters` validators switched on (`CamelCase`, `MissingPaginatedTrait`, `AbbreviationName`, `ShouldHaveUsedTimestamp`, `MissingSensitiveTrait`, …), and each event is reported with its file and line by a new `smithy.*` lint rule
  - OData breaking changes — comparing two versions of an OData service now grades each change by OData's own model-versioning rules: a new nullable property or collection navigation is safe, a new required property, a changed key or a changed property type is breaking, and every breaking change says whether the schema's `Core.SchemaVersion` was bumped
  - WSDL / XSD breaking changes — comparing two versions of a SOAP service now grades soapAction, binding-style and message-pattern changes, and XML Schema changes element by element (minOccurs / maxOccurs, nillable, defaults, enumerations, lengths, patterns and bounds), treating new optional elements as dangerous because SOAP receivers validate strictly
  - Fuller WSDL catalog items — a SOAP service's faults now appear as error messages, rpc-style messages with several parts keep every part, and each port is a server with its SOAP 1.1 / SOAP 1.2 / HTTP binding, all written back when you export to WSDL
  - TypeSpec versioned services — a TypeSpec service using `@typespec/versioning` now compiles every version: the catalog item describes the newest one, and lists each version with whether the step from the previous one was breaking or safe (and why)
  - RAML breaking changes — comparing two versions of a RAML API now grades parameter, property and enum changes individually: a new required parameter or property, a changed type or a removed enum value is breaking, a new optional one is safe
  - Smithy breaking changes — comparing two versions of a Smithy model now runs Smithy's own `smithy diff` and grades each change by its findings: `ERROR` is breaking, `DANGER` and `WARNING` are dangerous, `NOTE` is safe. Findings that belong to no single change, such as reordered members, are listed separately and still count toward the overall result, and a single `.smithy` file is now read by the Smithy CLI too, inline input and output members included
  - Arazzo source resolution — a Projects import of an Arazzo workflow validates its `sourceDescriptions` and resolves each step's `operationId` / `operationPath` against the documents supplied with the import, keeps an unresolved reference with a warning, and returns the result as `arazzoResolution` on the import job; the **Import** dialog sends only the workflow for now, so sources show as not in the import bundle
  - OpenAPI 3.2 `$self` references — a `$ref` that resolves against the document's `$self` back into the same document links to its class like a local reference, references to other documents are kept and listed in a warning, a `summary` / `description` beside a `$ref` is kept as a local override, and **Analyze** lists **Document base URI ($self)**
  - OpenAPI 3.2 tag hierarchy — tags keep their `summary`, `parent`, `kind` and `externalDocs` on the project (`x-apiome-tag-taxonomy`), classes list the tags their schema declares, a cyclic or undeclared parent imports as a top-level tag with a warning, and **Analyze** lists the taxonomy under **Feature compatibility**
  - OpenAPI 3.2 QUERY and custom methods — a path's `query` operation and its `additionalOperations` entries (such as `REPORT`) import as path operations with their request and response schemas, keep their method token, and export to `x-apiome-query-operation` / `x-apiome-additional-operations` so they survive a round-trip
  - OpenAPI 3.2 streaming responses — an `itemSchema` under JSON Lines (`application/jsonl`), JSON text sequences (`application/json-seq`) or Server-Sent Events (`text/event-stream`) imports its element schema as a class tagged `x-apiome-stream-kind`, the operation links to it, and **Analyze** lists the streaming media types under **Feature compatibility**
  - Secret scrubbing for collections and captures — Postman, Insomnia, Bruno, HAR and `.http` imports always strip credentials, whatever your workspace's scrub policy says. Variables keep their names but not their secret values, auth becomes security-scheme stubs in the converted OpenAPI document, and the catalog item's **Provenance** tab lists every redaction in a new **Secret scrub** row

## Bug Fixes

- Browse:
  - Versions created before Apiome recorded each version's format now show under the **format** and **paradigm** filters too: OpenAPI versions as `openapi` (or their exact version, such as `openapi-3.1`, when Apiome knows it) and Arazzo versions as `arazzo`, both under **REST**. Before, they matched no format or paradigm filter
- Sign-in:
  - Confirming a new account no longer flashes *We could not sign you in automatically* before the **Let's set up your first workspace** screen
  - **Sign In** stays disabled while you are being signed in, instead of turning back on and inviting a second click; it comes back only if the attempt fails
  - The sign-in page's *Watch our intro video* link, which no longer worked, is now **Explore our YouTube** and opens the Apiome YouTube channel
- Code editors:
  - Code in Apiome's editors (the spec viewer under **Versions**, and others) is easier to read: keys, strings, numbers and line numbers now have enough contrast against the code background in every theme. Before, light-theme keys, strings and line numbers were too faint
- Admin console:
  - Signing up again with the address of a deleted account no longer fails with *We could not send the confirmation email*. Deleting a user now releases their email address and linked sign-ins, signs them out everywhere, and the reason for a failed sign-up is logged
  - A disabled or deleted account can no longer sign in with its password
  - The **Users** list shows each account's **Created** date instead of *Invalid Date*, and a new **Last active** column shows its last sign-in or activity (*Never* for an unused account). Email and password sign-ins are now recorded too, not just provider sign-ins
