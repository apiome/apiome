# Apiome 11-2026 RC10

We continue to improve the platform based on your feedback with improvements and new features!

---

## Features/Improvements

- **RC10 begins** — RC9 is complete, and its notes are kept in the **Apiome RC9** release notes. The version on the launcher, in the user menu and on **Help & docs** now names the new release candidate (`RC10`). RC10 is about **contracts**: Pact Broker and PactFlow compatibility, bi-directional contract testing, and contract agreements
- **The MCP Catalog opens faster on large catalogs** — the **Servers** grid, its filters and **Analytics** now read each server's tool counts, safety flags and complexity from what was stored at discovery instead of working them out on every load. In a workspace with 2,000 servers of 50 tools each, the grid went from about 8 seconds to under 50 ms, and a filtered view from about 7.5 seconds to under 10 ms. **Analytics** numbers refresh every 30 seconds.
- **Faster search suggestions on the browse site** — the search palette (**⌘K** or **/**) on the public browse site now answers each keystroke in under 50 ms; on a large catalog it took up to a second. It suggests by **name** — organizations, API products, projects, operations, schemas and properties — and shows `40+` when a kind has more matches than it read. **Press ↵ on the first row** to run the full search. The counts in the browse site's top bar and the lists on its home page now refresh every 2 minutes, so a newly published version can take that long to be counted there; its own page and search show it at once.
- **Long lists load a page at a time** — **Export history**, the **MCP capability directory**, **Published versions**, a connector's **Items** and **Refresh runs**, and the admin **Users**, **Tenants**, **Licenses** and **Templates** lists now read one page and offer previous and next page arrows or **Load more**, so a workspace with thousands of rows opens as quickly as a small one. A count that would mean reading every row shows as `10,000+`
- **Pact Broker: pacticipants, versions, branches and tags** — the REST API now keeps the registry Pact tooling names applications by: register a **pacticipant**, record each build as a **version** with its branch and tags, and read every branch's head. A version never changes once recorded, a branch head only moves forward, and deleting a project keeps its pacticipant. **Roles** has a new **Pacts** row for it: **Editor** can view, create and edit; only **Owner** and **Admin** can delete. Verification results and can-i-deploy build on this and are not yet available
- **Pact Broker: publish and fetch pacts** — the Pact CLI and Pact libraries now publish to Apiome. Give `pact-broker publish` or pact-js `publishPacts` your workspace's broker base URL (`…/v1/tenants/<workspace>/pact-broker`) and an API key as the token. Consumers and providers are registered the first time a pact names them, a build's pacts are stored all together or not at all, and identical pacts are stored once, so ten builds of an unchanged pact give the provider one pact to verify. A different pact for a version that already has one is refused; an invalid pact is refused with the place in the file. Verification results and can-i-deploy are not yet available
- **Pact Broker: choose pacts to verify with selectors** — a provider's Pact verifier now fetches the pacts it must verify from Apiome. Send consumer-version selectors such as `{ mainBranch: true }`, `{ matchingBranch: true }` or `{ tag: "prod", latest: true }` with the same broker base URL and token you publish with. Each pact comes back once, with the reasons it was chosen in the words the Pact Broker uses, and an ambiguous selector is refused with the place in the request. You can also read the latest pact of a consumer from a tag or a branch. Environment selectors select nothing until deployments can be recorded
- **Pact Broker: publish verification results** — a provider's Pact verifier now reports back to Apiome. Run it with `publishVerificationResult: true`, a provider version and a branch, and each pact it verified gets a result: passed or failed, with the outcome of every interaction kept as the verifier sent it, the build URL and the provider branch. Results never change once published and are numbered per pact, and a provider version is registered on first use. A result can link an Apiome provider verification report instead of copying it. Can-i-deploy will read these results; it is not yet available
- **Pact Broker: environments and deployments** — your deploy jobs can now tell Apiome what runs where. Create environments such as `test` and `production` with `pact-broker create-environment`, then run `pact-broker record-deployment` after each deployment: it replaces the version deployed there before and keeps the old one in the history. Several copies of an application in one environment are recorded per **application instance**, and apps with several live versions use `record-release` and `record-support-ended`. A provider verifier's `deployed`, `released` and `environment` selectors now return the pacts of what is recorded there.
- **Pact Broker: can I deploy?** — `pact-broker can-i-deploy --pacticipant "Billing Service" --version "$GIT_COMMIT" --to-environment production` now asks Apiome whether a version is compatible with what runs in an environment, and stops your deploy job when it is not. The answer is **yes**, **no** or **unknown**, with the reason for each integration in the Pact Broker's words: a consumer needs its providers to be there, a provider does not need its consumers, and every version live in the environment is checked. `--retry-while-unknown` waits for a result that has not arrived yet, `--ignore` leaves one application out, and an environment marked `contractRequired` refuses a version with no pact. The same answer is on `GET …/pact-broker/can-i-deploy` and the matrix on `GET …/pact-broker/matrix`
- **Pact Broker: pending and work-in-progress pacts** — a consumer's new expectation no longer breaks the provider's build the moment it is published. With `enablePending: true` in the provider's verifier, a pact the provider branch has not verified yet comes back **pending**: its failure is reported but does not fail the build, and the first successful result from that branch ends the pending state. A branch you create later inherits what was already verified, so a new feature branch does not start with every pact pending. Add `includeWipPactsSince` and the verifier also gets **work-in-progress** pacts: the latest pact of each consumer branch that your selectors did not choose and the provider has not verified, always as pending. The matrix shows whether each result was for a pending or work-in-progress pact
- **Pact Broker: compatibility tested in CI** — the official `pact-broker` CLI, pact-js and pact-jvm now run against Apiome on every Pact Broker change, and **Pact Broker compatibility** in the docs lists every Pact Broker endpoint as supported, partial, planned or not planned. Three differences the tests found now match the Pact Broker: the first version published on `main` (or `develop`, `master`) sets the main branch, results from the Ruby `pact-provider-verifier` are accepted, and the pact-js verifier can fetch its pacts. An endpoint Apiome does not serve answers `501` with a link to the page and the issue that tracks it, never a bare `404`.
- **Pact Broker: contract webhooks** — Apiome can now tell your CI when a pact needs verifying and when a verification finishes. `pact-broker create-webhook` and `create-or-update-webhook` work unchanged with the broker base URL and token you already use. Use the `contract_requiring_verification_published` event to start a provider build: it fires once for each provider version that has not verified the pact yet — the head of the main branch and what is deployed or released — and carries that version and its branch. `${pactbroker.pactUrl}` and the other Pact Broker parameters are filled into the URL, headers and body. A webhook can start a **GitHub Actions** workflow directly, sign each request with a secret of yours, and is retried three times before it is marked failed; the log of every attempt can be read back. Tokens and passwords are sealed and never shown again. There is no screen for webhooks yet
- **Pact Broker: labels, deletes and retention** — group pacticipants with labels (`team-billing`, `tier-1`) and list the ones carrying a label. Deleting a version or a pacticipant now hides it, with its pacts, results and deployments, and you can restore it for 30 days; a deployed version is only deleted when you force it. A retention run keeps the newest versions of each branch, anything deployed and anything recent, and deletes the rest — it always shows you the plan first, and applies only that plan. Every delete and cleanup is in the audit log
- **Pact Broker: one overview page** — the Pact Broker core is complete, and **Pact Broker overview** in the docs walks through it end to end: the consumer publishes, a webhook starts the provider, the verifier reports back, deploy jobs record what runs where, and `can-i-deploy` decides. It links the page for each step, and **Help & docs** finds it when you search for `can-i-deploy` or `contract testing`. There is no screen for pacts yet
