The **Sunset timeline** is the end-of-life schedule for deprecated versions — and for deprecated
[API products and plans](#api-products-and-plans): which ones sunset when, what replaces them, and
which sunsets are close. **Go to Ship → Sunset timeline.** A sunset is
**imminent** when it falls within 30 days.

<Screenshot id="sunset-timeline" alt="Sunset timeline: one lane per project with a marker per sunset, and the table of deprecated versions" />

## Schedule a sunset

Sunsets are set on [Versions](../build/versions.mdx), not here:

1. On **Versions**, open a version's row menu and **choose “Schedule sunset (EOL)…”** (or the
   **Schedule sunset (EOL)** quick action on a deprecated row).
2. Set **Lifecycle** to **Deprecated** — a sunset date requires it — and add a **Deprecation
   message**, for example *Use v2 — v1 stops answering on 30 September.*
3. Enter the **Sunset date and time**. It is entered in your local time and stored in UTC.
4. Optionally choose a **Successor revision** for consumers to migrate to, or leave **No successor
   (end of life)**.
5. **Click “Save”.** A toast confirms *Sunset schedule saved.*

On a published version only a workspace administrator can change the sunset. To clear a sunset, use
**Edit version** from the row menu. The dialog is described in
[Version dialogs](../build/version-dialogs.mdx#schedule-sunset).

<Screenshot id="version-sunset-dialog" alt="Schedule sunset (EOL): lifecycle, deprecation message, sunset date and time, successor revision" />

## Read the timeline

The **Timeline** card covers one month back and the next five, with one lane per project and a
**today** line.

- Each **◆** is a sunset, labelled with its version line and how far away it is (`v1 · 12 d`,
  **today** or **past**), and its date in UTC.
- Colour and the legend say whether it is **past**, **imminent (≤ 30 days)** or **scheduled**.
- **Select a ◆** to highlight and scroll to its row in the table.

The foot counts what is on the timeline, what falls outside the six months and what has no sunset
date — every entry is in the table either way. The card is hidden when no sunset falls in the
window.

## The table

**Filter by project** (press <Kbd keys="/"/>) narrows both the timeline and the table to one
project.

| Column | What it shows |
| --- | --- |
| **Project** | The project. |
| **Version line** | The deprecated version. |
| **Sunset** | The sunset instant, or — when none is set. |
| **Timeline** | **past**, **imminent** or **scheduled**. |
| **Lifecycle** | **Deprecated (migrate before sunset)** or **Sunset reached (read-only / redirect)**. |
| **Successor** | The replacement version, or —. |
| **Notes / #507** | Who still calls the version (see [Who still uses a version](#who-still-uses-a-version)), the deprecation message or warning, and a **Migration guide** link. |

When rows carry the same structured warnings as compatibility checks, a **Where these warnings come
from** button appears next to **Export CSV**. **Click it** for the explanation, then open the
version on [Versions](../build/versions.mdx) to see the warnings in context.

## Who still uses a version

When the version's project has a [usage source](../govern/runtime-usage.mdx), the **Notes / #507**
cell opens with who still calls the version, counted over the last 7 days of `prod` traffic:

- *Still used by 2 consumers (1,240 calls, 7-day)* — consumers you have bound to their traffic still
  call it. Their handles follow (`billing-service, orders-web`, then *+N more*), and
  **“Consumers”** opens the project's Consumers page (see [Attribute traffic to consumers](../govern/runtime-usage.mdx#attribute-traffic-to-consumers)). Handles
  show only if you hold `consumer_contracts:view`; otherwise you see the count alone.
- *Anonymous traffic only — bind consumers to attribute it* — the version is still called, but no
  [consumer binding](../govern/runtime-usage.mdx#attribute-traffic-to-consumers) recognises who calls it.
  **“Bind consumers”** opens the Consumers page, where you add one.
- *No traffic in the last 7 days* — nobody calls it, so the sunset can go ahead.

A version whose project has no usage source shows no line: there is no traffic to go on.

<Screenshot id="sunset-timeline-still-used" alt="Sunset timeline Notes cells: still used by 2 consumers with their handles, anonymous traffic only, and no traffic in the last 7 days" />

### The weekly warning

Each time the usage sweep rolls up usage (hourly by default), Apiome checks every version whose
sunset is **30 days away or less**. If bound consumers called it in the last 7 days, the version's collaborators get a
**Sunsets still in use** [notification](../workspace/notifications.mdx#sunsets-still-in-use) —
*1.2.0 sunsets in 20 days and is still used by 2 consumers (1,240 calls, 7-day)* — and every push
webhook subscription in the workspace receives a `sunset.still_used` event. The event carries
the project, the revision, the sunset, the days left, the call counts and each consumer's handle.

A version is warned about **at most once a week**. Apiome records when it last warned, so a restart
or a second server never sends the warning twice. Anonymous traffic on its own never sends one,
because there is nobody to tell. The weekly warning stops once the sunset date has passed.

## API products and plans

Under the version table, **API products and plans** lists every deprecated or retired
[API product and plan](./api-products.mdx#lifecycle) in the workspace, soonest retirement first. It
appears only when there is one, and only to readers who can view projects.

| Column | What it shows |
| --- | --- |
| **Product or plan** | The product, or `Payments · Standard` for a plan. **Click it** to open the product. |
| **Retires** | The **Retire on** date (the day it retired, for a retired one), or —. |
| **Timeline** | **past**, **imminent (≤ 30 days)** or **scheduled**, the same words as the versions. |
| **Lifecycle** | **Deprecated (no new subscriptions)**, **Retirement date passed — ready to retire** or **Retired**. |
| **Moves to** | A plan's replacement plan, or —. |
| **Message** | The deprecation message, or —. |

**Filter by project** narrows it to the products that include that project. Retirement dates are set
on the product, not here — see [Deprecate a plan](./api-products.mdx#deprecate-a-plan). The CSV export
covers versions only.

## Export CSV

**Click “Export CSV”** to download `sunset-timeline.csv` for the rows on screen, with the columns
`project`, `versionLine`, `sunsetDate`, `timelineStatus`, `lifecyclePhase`, `successorRevisionId` and
`deprecationMessage`. The button is disabled when there are no rows.

## When it is empty

*No deprecation or sunset entries* means no version is deprecated or has a sunset date; **“Go to
Versions”** takes you there. If the schedule cannot be read, the table says *Could not load the
sunset schedule* with the reason and **“Try again”**.

## With the API

`GET /v1/versions/{tenant}/sunset-timeline` (optionally `?projectId=`) returns the same entries.
Each entry's `stillUsed` holds the usage line: `state` (`bound`, `anonymous` or `unused`),
`summary`, `calls`, `boundCalls`, `anonymousCalls`, `consumerCount`, `consumers` (`null` without
`consumer_contracts:view`) and `consumersHref`. `stillUsed` is `null` when the project has no
usage source. The sunset itself is version metadata, set with `PUT /v1/versions/{tenant}/{project_id}/{version_record_id}`.

The same response carries `products`: one entry per deprecated or retired API product or plan, with
`kind` (`product` or `plan`), `productSlug`, `productName`, `planSlug`, `planName`, `state`,
`deprecatedAt`, `retireAt`, `retiredAt`, `timelineStatus`, `lifecyclePhase` (`deprecated`,
`sunset_reached` or `retired`), `deprecationMessage`, `successorPlanSlug` and `successorPlanName`. It
is empty without `projects:view`; with `projectId`, it holds only products that include the project.
See the [API reference](../reference/api-reference.md).
