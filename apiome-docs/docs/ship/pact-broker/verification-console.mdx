The **Verification** page of a provider shows how its pacts stand and every
[verification result](./verification-results.mdx) it has. From there you can open one result to see
exactly what failed, copy or download its log, **Re-run** a pact, or **Verify all stale** pacts at
once. Re-runs use the [hosted verifier](./hosted-verification.mdx): Apiome replays the pact against
a registered verification target and publishes a new result.

To start a new run with your own selectors and options instead of re-running a recorded pact, use
**Contracts** → **Verification** (**Run a verification**). See
[Run a verification from the app](./hosted-verification.mdx#run-a-verification-from-the-app). That run
is followed live in the run drawer: see [Watch a run as it happens](#watch-a-run-as-it-happens).

## Before you start

- You hold **Pacts** → **View** to read the page. Without it, the page shows **Permission denied**.
- To re-run, you also hold **Pacts** → **Create** and **Verification evidence** → **Create**. The
  built-in **Editor** role has both.
- To re-run, the provider has a **verification target**: a running copy of it that Apiome can reach.
  See [Verify a provider from Apiome](./hosted-verification.mdx#before-you-start).

## Open the Verification page

1. In the rail, under **Ship**, click **Contracts**.
2. On the **Pacticipants** page, click the provider.
3. In the **Pacts** section, click **Verification**.

You can also start on a pact: in its **Verification status** section, click **Results and logs**.
That opens the provider's page with the history narrowed to that consumer.

The page is at `/ade/dashboard/pacts/pacticipants/<provider>/verification`.

## Read where the provider stands

The strip at the top counts the newest pact of each consumer:

| Count | What it counts |
| --- | --- |
| **Pacts** | Consumers with a pact for this provider. |
| **Verified** | Newest pacts whose newest result passed. |
| **Failing** | Newest pacts whose newest result failed. |
| **Stale** | Newest pacts with no result yet. |
| **Overdue** | Newest pacts not verified for longer than their [stale threshold](./stale-pacts.mdx). |
| **Interactions passing** | Of the interactions in those newest results, the share that passed. |
| **Last verified** | When the newest of those results was published. |

The **Pacts** table lists each consumer's newest pact: the consumer version and pact version, the
newest result with its verdict, and the provider version that published it. Click **Result N** to
open that result. Next to each consumer's name, its [contract health](./contract-health.mdx) state
(**Healthy**, **Degraded**, **Failing** or **Unknown**) opens the pair's health and trends.

**A stale pact** has no verification result. Its consumer changed the pact since the provider last
verified it, or the provider never verified it. It is marked **Stale — not verified**. A stale pact
reads as *not known yet* in [can-i-deploy](./can-i-deploy.mdx), so a deployment that depends on it
waits.

Below the strip, a line names the **verification cadence** and **stale threshold** that apply to the
provider, with a link to **Verification settings**. A pact not verified for longer than its threshold
is marked **Overdue**, and links to its open re-publish request (**Re-publish requested**). A pact
whose scheduled verification was skipped says why. See
[Stale pacts and verification scheduling](./stale-pacts.mdx).

## Re-run one pact

1. In the **Pacts** table, click **Re-run** on the consumer's row.
2. Choose the **Verification target**.
3. Check the **Provider version**. It is filled in with the provider version of the pact's newest
   result, so a re-run answers "does that build still honour this pact?". Change it to verify another
   build. If the pact has no result yet, enter the version.
4. Optionally change the **Provider branch**, and tick **Send mutating requests** if the pact's
   `POST`, `PUT`, `PATCH` and `DELETE` interactions may be sent. The target's own policy must allow
   them too, and the target must not be a production target: such a run is refused with
   *Requests that change data are never sent to a production target*.
5. Click **Re-run verification**.

The dialog then says how the run went: **Passed**, **Failed**, **Incomplete — nothing published**
when an interaction could not be replayed, or **Could not connect — nothing published** when no
request reached the target. A target that cannot be reached is not a failed verification. Click **Done**. The page reads the results again, and
the new result is first in the history, with the trigger **Re-run**.

You can also re-run from a result's own page: click **Re-run verification** in its header.

**One run per pact at a time.** While a re-run or a **Verify all stale** run of a consumer and
provider is still going, another re-run of the same pair is refused with *a verification of … is
already running*. Wait for it to finish and run again.

## Watch a run as it happens

When you select **Run verification** on **Run a verification**, the **run drawer** opens beside the
page and follows the run as Apiome replays it. It reads the run again every second.

<Screenshot id="pact-verify-live" alt="The run drawer: Verifying Billing Service 2.7.0+9f31c20 against staging, 13 of 18 interactions, with a striped progress bar; a table of pacts (Orders UI 3.4.0 Failed 5 / 6, Orders UI 3.3.2 Passed 6 / 6, Mobile App Running 1 / 4, Checkout Queued 0 / 2); the failing interaction POST /invoices, Body differs, Orders UI 3.4.0 with the state “a customer 7 exists”, Expected /currency matching ^[A-Z]{3}$ beside Provider returned /currency missing, with Show the request, Re-run this interaction and Reproduce on the mock; then the run log and Stop run."/>

- **The progress bar** and the subtitle (*Against staging · started 14:02:11 · 13 of 18
  interactions*) follow every interaction.
- **The table** has one row per pact: **Queued**, **Running**, then **Passed**, **Failed** or
  **Incomplete**, with the interactions that passed of the pact's total. A pact the run did not reach
  is **Stopped**.
- **The failing interaction** is the newest one that did not pass: its request, what differs, and
  **Expected** beside **Provider returned**, one line per mismatch.
  - **Show the request** prints the request against the target, with the provider states it needs.
  - **Re-run this interaction** replays just that interaction against the same target, once the run
    is over. **Nothing is published** and no evidence is recorded: one interaction does not verify a
    pact. Start a new run to record a result.
  - **Reproduce on the mock** opens the provider's project on **Versions**, where each version's
    hosted mock can be turned on. It shows when the provider is
    [bound to a project](./pacticipants.mdx#open-a-pacticipant); otherwise the drawer says to bind it.
- **The run log** lists each provider state set up and each interaction with its status and how it
  went. It keeps the newest 2,000 lines and says how many older lines it let go.

**Closing the drawer keeps the run going.** The header's main button reads **Show the run** while
it runs. When the run ends, a toast says how it went; select **Show the run** in the toast to open
the drawer again.

**Stop run** ends the run before its next interaction. Pacts that finished keep their published
results. The pact being replayed publishes nothing, and the pacts not reached are listed as not
verified. The run's outcome is **Stopped**.

A run is kept for 30 minutes after it ends. A workspace runs at most three at once; a fourth is
refused with *This workspace already has 3 verification runs going*.

## Verify all stale pacts

1. Above the **Pacts** table, click **Verify all stale (N)**. The button is off when nothing is stale.
2. Choose the **Verification target** and enter the **Provider version** the pacts are verified as,
   usually the commit SHA of the build running on the target. Optionally give the branch.
3. Click **Verify stale pacts**.

One run verifies at most 25 pacts. The dialog lists every stale pact it did not run, with the reason:
past the limit (run **Verify all stale** again for the rest), or already being verified.

## The history

**History** lists every verification result of the provider, newest first: results Pact verifiers
published, hosted runs, re-runs and bi-directional comparisons. Each row shows:

| Column | What it shows |
| --- | --- |
| **Result** | Its number for the pact version, and the pact version. Click it to open the result. |
| **Consumer** | The consumer whose pact was verified. |
| **Provider version** | The provider build, and its branch when known. |
| **Verdict** | **Passed**, **Failed**, or **Failed (pending)** when the pact was pending. |
| **Interactions** | How many of the result's interactions passed. |
| **Trigger** | How the result came to be (see below). |
| **Duration** | How long the run took, when Apiome ran it. |
| **Build** | The CI build, when the verifier sent one. |
| **Verified** | When the result was published, in UTC. |

Choose a consumer in the list above the table to see only its results. The address keeps
`?consumer=`, so you can share it. **Load more** reads the next 25.

| Trigger | Meaning |
| --- | --- |
| **Pact verifier** | A Pact verifier in the provider's build published it. |
| **Hosted verifier** | A [hosted verification](./hosted-verification.mdx) request ran it. |
| **Re-run** | Someone clicked **Re-run**. |
| **Stale re-check** | **Verify all stale** ran it. |
| **Bi-directional** | Apiome compared the pact with the provider contract. See [Bi-directional contracts](./bi-directional.mdx). |
| **Not recorded** | It was published before Apiome recorded triggers. |

## Read one result

Open a result from the **Pacts** table or the history.

<Screenshot id="pact-verification-result" alt="Result 3 of Billing Service's pact with Ledger API: the overview with provider build 4f1e2d0 on main, trigger Re-run and duration 1.8 s; the failed summary interaction open with expected and actual values side by side; the requests the run sent; and the raw log with Copy and Download."/>

- **Overview** shows the verdict, the pact, the provider build (version and branch), the CI build,
  the verifier, the trigger, the duration and how many interactions passed.
- **Interactions** lists each interaction. A failed one is open. Each mismatch names where it is
  (for example `body /year`) and the matching rule, and shows the **Expected** and **Actual** values
  side by side. An interaction that failed without a mismatch shows the verifier's message.
- **Requests** lists the requests a hosted run sent, with the status returned and how many
  assertions passed. A result a Pact verifier published has no requests here: its log is in the build
  that ran it. The page also says when retention removed the log, or when your role cannot read
  verification evidence.
- **Raw log** is the whole result as text: every interaction, mismatch and request. Click **Copy**
  to copy it, or **Download** to save it as a `.log` file.

## From CI or a script

The page uses these REST endpoints, which you can call with an API key. They live beside the hosted
verifier, under `/v1/tenants/<tenant>/pact-verifier/pacts/provider/<provider>`:

| Endpoint | What it does |
| --- | --- |
| `GET …/verification-status` | Each consumer's newest pact, its newest result, and whether it is stale. |
| `GET …/results?consumer=&cursor=` | The history, newest first. |
| `GET …/results/<id>` | One result with its test results and evidence run. |
| `POST …/consumer/<consumer>/pact-version/<sha>/reverify` | Re-run one pact. |
| `POST …/verify-stale` | Verify every stale pact (`provider_version` required). |
| `POST …/verify/runs` | Start a live run: the body of `…/verify`, answered at once with the run's id. |

A live run is then read and controlled at `/v1/tenants/<tenant>/pact-verifier/runs/<run_id>`:

| Endpoint | What it does |
| --- | --- |
| `GET …/runs/<run_id>?log_after=<seq>` | The run as it stands: each pact's row, the failing interaction, the log after `log_after`, and `result` once finished. |
| `POST …/runs/<run_id>/stop` | Stop the run before its next interaction. |
| `POST …/runs/<run_id>/rerun` | Replay one interaction (`pact_version_sha`, `case_id`) of a finished run. Publishes nothing. |

```bash
curl -X POST \
  "$APIOME/v1/tenants/acme/pact-verifier/pacts/provider/ledger-api/verify-stale" \
  -H "Authorization: Bearer $APIOME_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "target_ref": "ledger-staging", "provider_version": "4f1e2d0", "provider_branch": "main" }'
```

A key with the `pact:verify` scope may run them. See the
[Pact broker REST reference](../../reference/rest/pact-broker.md).

## Who is told about a failure

When a verification result fails — published by a Pact verifier, or run by Apiome — the provider's
and the consumer's [owner teams](./pacticipants.mdx#give-a-pacticipant-an-owner) are told. Each
team's members get a **Verification drift** notification, and its chat channel a message, such as
*Verification failed: Ledger API 4f1e2d0 did not verify Billing Service's pact (version 1.4.0)*.
Clicking it opens the result.

- A pacticipant with no owner team falls back to the owner of the consumer or project it is bound
  to. With none, the failure is recorded in the **Unowned findings** report, or sent to the
  workspace's catch-all team.
- When one team owns both pacticipants, it is told once.
- A failed pending pact is reported too; the message says it does not block deploys.
- A team hears about the same pacticipant at most once an hour.
- A passing result tells nobody. Notifying never changes the result or fails the publish.

## Who can do what

| Action | Permission |
| --- | --- |
| Open the Verification page and a result | **Pacts** → **View** |
| See a result's requests | **Verification evidence** → **View** as well |
| **Re-run** and **Verify all stale** | **Pacts** → **Create** and **Verification evidence** → **Create** |
| Watch a live run | **Pacts** → **View** |
| **Stop run** | **Pacts** → **Create** |
| **Re-run this interaction** | **Pacts** → **Create** and **Verification evidence** → **Create** |

Every read and run is scoped to your current workspace.
