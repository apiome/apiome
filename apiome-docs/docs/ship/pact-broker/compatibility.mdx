Apiome speaks the Pact Broker's API, so the `pact-broker` CLI and the Pact libraries work against it
after you change only their **broker base URL** and **token**. This page lists every endpoint of
the Pact Broker's API and how much of it Apiome serves. A conformance suite runs the official tools
against Apiome in CI to keep the list true.

## What the statuses mean

| Status | Meaning |
| --- | --- |
| ✅ **Supported** | Every method the Pact Broker allows works, in the Pact Broker's shape. |
| ◐ **Partial** | Some methods work. The others answer `501`. |
| 🗓 **Planned** | Not served yet. The linked issue schedules it. |
| — **Not planned** | Not served, and nothing is scheduled. The notes say what to use instead. |

## When you reach an endpoint Apiome does not serve

The `pact-broker` CLI finds every endpoint through the links on the broker's index. Apiome's index
links only what it serves. So a command for a missing feature stops before it sends a request, and
says the broker does not have it:

```text
$ pact-broker delete-branch --branch main --pacticipant checkout-web
This version of the Pact Broker does not support deleting branches. …
```

A client or script that builds the URL itself never gets a bare `404` for a missing endpoint.
It gets `501 Not Implemented` with a `Link` header to this page, and a body that names the endpoint,
its status, the methods that do work, the tracking issue (when one is scheduled) and the Apiome
route to use instead:

```json
{
  "detail": {
    "code": "pact-broker-not-implemented",
    "message": "PUT is not supported on “A pacticipant” (partial). Supported: GET, DELETE. …",
    "pointer": "/v1/tenants/acme/pact-broker/pacticipants/checkout-web",
    "endpoint": "/pacticipants/{pacticipant}",
    "status": "partial",
    "supported_methods": ["GET", "DELETE"],
    "alternative": "/v1/tenants/{tenant}/pacticipants/{pacticipant}",
    "documentation": "https://docs.apiome.dev/ship/pact-broker/compatibility",
    "pact_broker_version": "2.124.0"
  }
}
```

A path that is not part of the Pact Broker's API at all gets the same `501`, without the
endpoint fields. A `404` from a supported endpoint still means what it means on the Pact Broker:
that pact, version or pacticipant does not exist.

## Behaviour that matches the Pact Broker

- **Main branch detection.** The first time a version of a pacticipant is published on `develop`,
  `main` or `master`, that branch becomes its **main branch**, unless one is already set. This is
  the Pact Broker's `auto_detect_main_branch`. It means `{"mainBranch": true}` selectors work
  without any set-up. See [Choose pacts to verify with selectors](./selectors.mdx).
- **Pact-Ruby verification results.** The verifier in the `pact-cli` image sends `testResults` as
  an object (`{"tests": [...], "summary": ...}`). Apiome keeps its `tests` list. See
  [Publish verification results](./verification-results.mdx).
- **Labels.** `…/labels`, `…/pacticipants/label/{label}` and `…/pacticipants/{p}/labels/{label}`
  answer in the Pact Broker's shape. See [Labels, deletes and retention](./retention.mdx).
- **Deletes are soft.** `DELETE …/pacticipants/{p}` and `…/versions/{v}` answer `204` as on the Pact
  Broker, but what they delete can be restored for 30 days, and a deployed version is protected
  unless `force=true`. See [Labels, deletes and retention](./retention.mdx).
- **`GET …/for-verification`.** The Rust verifier inside pact-js, pact-python and pact-go reads this
  resource with `GET` before it posts its selectors. Apiome answers both forms.

## The conformance suite

The suite runs the real tools against a fresh Apiome. It drives three clients through
publish → verify → record-deployment → can-i-deploy:

| Client | What it exercises |
| --- | --- |
| **`pact-broker` CLI** (`pactfoundation/pact-cli`) | `create-environment`, `publish`, `pact-provider-verifier` with result publishing, `record-deployment`, `can-i-deploy` (yes, then no for an unverified version), `create-version-tag`, `record-release`, `record-support-ended`, `record-undeployment`, `describe-environment`, `list-environments`, `create-webhook`, `create-or-update-webhook`. |
| **pact-js** | A PactV3 consumer test, then the `Verifier` (the Rust core) fetching pacts with selectors and publishing its result. |
| **pact-jvm** | A JUnit 5 consumer test, the Gradle plugin's `pactPublish`, then a JUnit 5 provider test that verifies from the broker and publishes its result. |

The suite also compares the HAL documents the clients read (the index, the pacticipant, the pact,
for-verification, the verification result, environments, the matrix, can-i-deploy, a webhook and a `501`)
with checked-in **golden transcripts**. Any change to what a Pact client sees therefore shows up in
review.

Run it on your machine with Docker and `uv`:

```bash
scripts/pact_conformance/run.sh                         # every client
scripts/pact_conformance/run.sh --clients cli           # the CLI only
scripts/pact_conformance/run.sh --update-golden         # after an intended change to a response
```

CI runs the **Pact Broker conformance** workflow on every pull request that changes the Pact
Broker routes or the suite. You can also start it from the **Actions** tab.
