Apiome is a Pact Broker. The `pact-broker` CLI, the `pact` CLI, pact-js and pact-jvm work against
it unchanged: give them your workspace's **broker base URL**
(`https://api.apiome.dev/v1/tenants/<workspace>/pact-broker`) and an API key as the **token**.
Consumers publish their pacts, providers verify them and report back, deploy jobs record what runs
where, and `can-i-deploy` stops a release that would break something.

All of it is served through the API and the Pact tools, and all of it can be done in the
[**Contracts** workspace](#the-contracts-workspace) of the app: every `apiome pact` command has a
screen there, and every screen that changes something shows the command that does the same
([one model, every surface](#one-model-every-surface)).

## When to use it

- **You test with Pact and want the broker next to your specs.** Your pacts, verification results
  and deployments live in the same workspace as the projects that describe your APIs, under the
  same members, roles and API keys.
- **You are moving off a self-hosted Pact Broker.** Point the same CLI commands and library
  options at Apiome; [Pact Broker compatibility](./compatibility.mdx) lists every endpoint and
  whether Apiome serves it.
- **You want deploys gated on contracts.** Ask [can-i-deploy](./can-i-deploy.mdx) before each
  deployment, and let [contract webhooks](./webhooks.mdx) start a provider build when a pact
  changes.

## Set up in ten minutes

**Set up contracts** takes a workspace from nothing to a yes or no before every deploy, on one page
you can leave and come back to. **Click Contracts** in the rail, then **click “⋯”** → **“Set up
contracts”** — or **“Open the guided set-up”** on the landing's first-run checklist, or on
**Settings** → **CI and commit statuses**. The page is `/ade/dashboard/pacts/setup`.

<Screenshot id="pact-setup" alt="Set up contracts: six numbered sections. Who talks to whom and Where things run are Done, Connect your pipelines is Next and open with a Create a key button, the two broker variables and two repositories ticked for Write secrets, and three sections are To do. The side panel shows 2 of 6, about 8 minutes left, what you get at the end, and the apiome pact setup command."/>

The six sections come in the order they depend on each other. Each shows **Done**, **Next** or **To
do**; only the next one is open, and **clicking a section's title** opens or closes any of them. A
section is **Done** when what it sets up exists — whoever made it, here, in CI or from the CLI — so
nothing is set up twice when you come back.

1. **Who talks to whom.** Apiome proposes a pacticipant for every project (as a **Provider**) and
   for every registered repository no project is read from (as a **Consumer**), with where it was
   found and its owner team. **Tick** the ones that talk to each other and **click “Create N
   pacticipants”**. One that already exists reads **Already a pacticipant** and cannot be created
   again. With nothing to propose, **click “Add one by hand”** or follow **import a project**.
2. **Where things run.** **Tick** `production`, `staging` or `development`, or type another name and
   **click “Add another”**; leave **“Require a verified contract before anything reaches
   production”** ticked to make can-i-deploy refuse a version with no contract there. **Click
   “Create N environments”**.
3. **Connect your pipelines.** **Click “Create a key”**: an API key that can publish pacts, read
   verdicts and record deployments. It is shown once — **click “Copy”**. Under **Where to point** are
   the two variables every Pact tool reads, `PACT_BROKER_BASE_URL` and `PACT_BROKER_TOKEN`. Under
   **Add them to**, **tick** your GitHub repositories and **click “Write secrets to N
   repositories”**: Apiome stores both as Actions secrets with the GitHub account each repository
   was registered with, and lists each repository as written or not written with the reason. Coming
   back later, the section shows the key's prefix instead of offering a second key; paste the key
   into **The key to store** to write it to another repository. Wired your pipelines another way?
   **Click “I connected them myself”**.
4. **The first consumer pact.** Choose **We already write Pact tests** and **click “Publish a
   pact”** ([Publish and fetch pacts](./publish-pacts.mdx#publish-from-the-ui)), or **Start from the
   spec** and **click “Derive a pact”** ([Export a contract](./export-contracts.mdx)). The section is
   done when the first pact is published.
5. **The provider's side.** Under **The spec as the contract**, **click “Turn on”** beside a
   provider to publish each published version of its project as its provider contract
   ([bi-directional](./bi-directional.mdx)) — no provider test to write. To replay pacts against a
   running provider instead, or as well, **click “Run a verification”**
   ([hosted verification](./hosted-verification.mdx)). If your own pipeline verifies the provider,
   **click “Our pipeline verifies the provider”**.
6. **Gate deploys and tell people.** Leave **“Add a can-i-deploy step to each pipeline”** and
   **“Record deployments on merge”** ticked, choose the **Environment**, check the pacticipant beside
   each repository, and **click “Open N pull requests”**. Each pull request adds
   `.github/workflows/apiome-contracts.yml` from the branch `apiome/contracts-setup`. **Click “Show
   the workflow”** to read the file first. Commit statuses are on by default and notifications are
   [webhooks](./webhooks-console.mdx); the section links to both. **Click “Finish set-up”**.

**“Finish later”** returns to Contracts; everything done so far is kept, and anyone with the
Contracts admin permission can pick the page up. **“I already have a broker”** opens the
[Migration wizard](./migration.mdx) instead.

### What the page shows in special cases

| When | What you see |
| --- | --- |
| Apiome finds no project or repository | Section 1 says so and offers **Add one by hand** and **import a project** |
| No registered repository has a linked GitHub account | **Add them to** becomes two `gh secret set` commands to copy, and section 6 offers only **Show the workflow** — the file to add by hand |
| A repository cannot be written to (no admin access, a branch rule, an archived repository) | That repository is listed as not written, or **No pull request**, with GitHub's reason and the workflow to add by hand; the others still go through |
| A pull request from the set-up is already open | It is listed as **Pull request already open** with its link; its branch is brought up to date |
| The workspace was [migrated from a broker](./migration.mdx) | Sections 1 and 2 arrive **Done**, and the side panel says the workspace was copied |
| You are not a Contracts admin | The page is readable; each section reads **Ask a Contracts admin to do this step** in place of its buttons |
| Projects and repositories number more than 200 | The first 200 are proposed and the page says how many are not listed |

### The same, from a script

`apiome pact setup` does sections 1, 2, 3 and 6 for a workspace created by script, and can be run
again: what exists is reported as *already there* and left alone.

```bash
export PACT_BROKER_BASE_URL=https://api.apiome.dev/v1/tenants/acme/pact-broker
export PACT_BROKER_TOKEN=$APIOME_API_KEY

apiome pact setup                       # show the six sections and how far the set-up is
apiome pact setup --from-projects \
  --environments production,staging --require-contract \
  --ci github --write-secrets           # pacticipants, environments, pull requests, secrets
apiome pact setup --from-projects --ci github --dry-run   # print what a run would do
```

| Flag | What it does |
| --- | --- |
| `--from-projects` | Creates a pacticipant for each proposed project and repository that has none |
| `--environments a,b` | Creates the environments that do not exist; `production` is marked production |
| `--require-contract` | With `--environments`: can-i-deploy to production requires a contract |
| `--ci github` | Opens the pull requests of section 6 for every GitHub repository a pacticipant names, and prints the workflow for any it could not open one in. Other CI systems have recipes on [Run Pact in CI](./ci-pact.mdx) |
| `--ci-environment name` | The environment the pipeline asks about (default: `production`, else the first) |
| `--write-secrets` | Stores this command's own broker address and key as the two Actions secrets |
| `--dry-run` | Prints what a run would do and changes nothing |

Every pacticipant, environment and repository ends as one line — created, already there, opened,
written, or skipped with the reason. The command exits `1` when anything failed; a repository
skipped with a reason is not a failure. The command cannot create its own first key: create one on
the page or under [API keys](../../workspace/api-keys.mdx).

The page reads `GET /v1/tenants/{t}/pact-setup` and saves its own marks with `PUT` on the same path;
secrets and pull requests are `POST …/pact-setup/github/secrets` and
`POST …/pact-setup/github/pull-requests`
([REST reference](../../reference/rest/pacticipants.md)). Reading needs **Pacts: view**; every action
on the page needs the Contracts admin permission (**Pacts: delete** — Admin and Owner). Saving,
writing secrets and opening pull requests are recorded in the [access audit](../../govern/access-audit.mdx)
as `pacts.setup.update`, `pacts.setup.github.secrets` and `pacts.setup.github.pull_requests`; the
key's value is never stored or recorded.

## The Contracts workspace

**Click Contracts** in the rail (under **Ship**). It opens on the **Contracts** landing: what needs
your attention, every integration, and where to start. A row of tabs under the title —
**Overview**, **Pacticipants**, **Matrix**, **Can I deploy**, **Verification**, **Environments**,
**Webhooks**, **Health** and **Settings** — is on every Contracts page, with the page you are on highlighted.
Every screen is open to anyone who can view pacts, and each empty screen shows the CLI command that
fills it.

<Screenshot id="pact-overview" alt="The Contracts landing: the tab row with Overview selected, a status strip reading 1 failing, 1 stale, 1 without a provider contract and 1 pending with the failing detail open, a facts line (6 integrations, 3 verified, 9 pacticipants, 3 environments), the integrations table worst first, and Start something grouped by consumer, provider and pipeline."/>

### What the landing shows

- **The status strip.** One chip each for **failing**, **stale**, **without a provider contract**
  and **pending** integrations, shown only when there is one. The worst chip is open; **click a
  chip** to read its detail instead. **Show the failing ones** and **Show the stale ones** filter
  the table.
- **The facts line.** How many integrations, how many are verified, and how many pacticipants and
  environments the workspace has. **Click “Show stats”** for the
  [contract health](./contract-health.mdx) rollup: pairs per state, pass rate, flakiness and mean
  duration.
- **The integrations table.** One row per consumer → provider pair, worst first:

  | Column | What it says |
  | --- | --- |
  | **Integration** | The consumer and the provider, each linked to its page, with the consumer version of the newest pact and the provider version that last verified it |
  | **Kind** | **Pact** (a provider verifier replays the pact) or **Bi-directional** (a [provider contract](./bi-directional.mdx) is compared with it) |
  | **Latest verdict** | **Failing**, **Stale**, **No provider contract** (nothing to compare it with yet), **Not verified yet** or **Verified**, and **Pending** while the provider has never passed it ([pending pacts](./pending-and-wip.mdx)) |
  | **Deployed together in** | The environments where both sides are deployed now |
  | **Verified** | When the newest result was recorded, or **never** |

  **Type in the search box** and **press Enter** to match consumer and provider names. The chips —
  **All**, **Failing**, **Stale**, **Bi-directional** and **Mine** (a team you are on owns either
  side) — filter the rows, and **Previous** / **Next** page through them. The search, the chip and
  the page are kept in the address, so you can share the link. Anything in the address the page
  cannot use (an unknown filter, a page that does not exist) is listed under the toolbar, and the
  default is used instead. Each row's **⋯** menu opens the pact, its verification history, the
  pair's health, or **Can I deploy?** for its consumer version. **Click “Network”** to draw the
  integrations on the page as a [network](./network.mdx).
- **Start something.** The ways in, by who you are: **I consume an API**, **I provide an API** and
  **I run the pipeline**. Each entry opens its screen. Until one integration is verified, a
  **Your first contract, in four steps** checklist is shown above them.

The header's **Publish a pact** and **Publish provider contract**, and its **⋯** menu (**Run a
verification**, **Derive a pact from a project**, **Can I deploy?**, **Set up contracts**,
**Migrate from a broker**), open the same screens. **Publish provider contract** is also the action
of the strip's **without a provider contract** chip. Only a role that can publish pacts
(**Pacts** → **Create**) sees the header actions and **Start something**; anyone who can view pacts
sees the strip and the table.

A workspace with no pacts shows **No contracts yet** instead of the strip and the table, with the
checklist open. If the integrations cannot be read, one banner says why, with **Try again**.

### One model, every surface

The app, `apiome pact`, the Pact CLI and libraries, the GitHub Action and the `pact` MCP tools all
read and write the same Pact Broker API, so whatever one of them records the others see at once.

- **Every command has a screen.** Each of the 28 `apiome pact` commands is done from a Contracts
  screen; [The same command, in the app](./cli.mdx#the-same-command-in-the-app) lists where.
- **Every screen shows its command.** A screen that changes something has a **The same, from
  anywhere** block: what you filled in as an `apiome pact` command, a Pact CLI command, a GitHub
  Action step and a REST request, with secrets written as variables. An action no command does yet
  (editing a webhook, a workspace secret, stopping a live run) says why and shows the REST request.
- **CI keeps it that way.** A new command without a screen, or a new Contracts write without a
  command or a written reason, fails the build
  ([The CLI ↔ UI parity ledger](../../admin/contribute-to-the-docs.mdx#the-cli--ui-parity-ledger)).

The landing reads `GET /v1/tenants/{t}/pact-integrations`
([REST reference](../../reference/rest/pact-broker.md#read-integrations-v1-tenants-tenant-slug-pact-integrations-get)).

A project's **Consumers** screen can also
[publish a pact to the broker](./publish-pacts.mdx#from-the-import-dialog) while you import
it: **click “Import Pact file”** and **tick “Also publish to the Pact Broker”**; its **open the
Publish page** link carries the pact over to the full page.

## How the pieces fit

1. **The consumer publishes.** Its Pact tests write a pact file, and its build
   [publishes it](./publish-pacts.mdx) with the consumer version and branch. The consumer and the
   provider are registered as [pacticipants](./concepts.mdx) the first time a pact names them.
   Identical pacts are stored once as one **pact version**, so an unchanged pact is verified once.
2. **A webhook starts the provider.** A
   [`contract_requiring_verification_published`](./webhooks.mdx#events) webhook fires for each
   provider version that has not verified the pact yet — the head of the main branch and what is
   deployed or released — and can start a GitHub Actions workflow directly.
3. **The provider verifies.** Its verifier sends
   [consumer-version selectors](./selectors.mdx) (`{ mainBranch: true }`, `{ deployedOrReleased: true }`)
   and gets each pact to check once. With `enablePending`, a new expectation comes back
   [pending](./pending-and-wip.mdx) and its failure does not fail the build.
4. **The verifier reports back.** It [publishes a result](./verification-results.mdx) per pact:
   passed or failed, with the outcome of each interaction. Results are what the matrix is made of.
5. **Deploy jobs record where versions run.** `pact-broker record-deployment` (or
   `record-release`) [records each version](./environments.mdx) in its environment, replacing the
   one deployed there before.
6. **Can-i-deploy decides.** Before each deployment,
   [`pact-broker can-i-deploy`](./can-i-deploy.mdx) reads the matrix against what runs in the
   target environment and answers **yes**, **no** or **unknown**, with a reason for each
   integration. The job stops when the answer is not yes.

**Apiome as the verifier.** A provider without a Pact library in its language can leave steps 3
and 4 to Apiome. One request [verifies it from Apiome](./hosted-verification.mdx): the same
selectors pick the pacts, each pact is [compiled into a contract suite](./verification.mdx), the
[provider states](./provider-states.mdx) are set up, and every interaction is replayed against a
registered verification target. Apiome then publishes a result for each pact. This covers HTTP
interactions, gRPC calls recorded by the Pact protobuf plugin, and GraphQL operations.

**Bi-directional instead of a verifier.** A provider that does not run Pact verification publishes
its OpenAPI document as a [provider contract](./bi-directional.mdx) instead, with
[self-verification evidence](./bi-directional.mdx#self-verification-evidence) from a tool such as
Schemathesis, Dredd or Newman. Apiome compares each pact with that document by the
[comparison rules](./comparison-rules.mdx) as soon as either side publishes, and stores the verdict
as a verification result, so steps 4 and 6 work the same way. A consumer without Pact tests can
[export a pact](./bi-directional.mdx#consumers-without-a-pact-file) from the surface it declared in
Apiome. A provider that sends messages publishes its AsyncAPI document instead, and its consumers'
[message pacts](./message-pacts.mdx) are compared with it the same way.

**Inside the registry.** The broker is not a separate tool beside your specifications; its data
flows into them:

- **One consumer model.** A published pact becomes the consumer's next
  [contract revision](./publish-pacts.mdx#one-consumer-model) in the provider's project, so
  breaking-change analysis sees consumers that publish pacts.
- **The deploy gate.** The project [deploy gate](./can-i-deploy.mdx#in-the-deploy-gate) has a
  `contracts` signal that gives the same verdict as can-i-deploy.
- **The publish gate.** A version publish can warn or be
  [blocked on failing contracts](./can-i-deploy.mdx#block-a-publish-on-failing-contracts).
- **Diff and CI.** `apiome diff --consumers` and the `diff-action`
  [name the pacticipant](../contract-testing-and-ci-gates.mdx#broker-consumers-in-the-diff-and-in-ci)
  behind each consumer verdict.
- **Browse and the portal.** Public project pages show
  [pact badges and the consumers](./badges.mdx#consumers-on-browse-and-the-portal) that depend on
  the project.

Along the way, [badges](./badges.mdx) show the state of a public project's pacts, and
[retention](./retention.mdx) keeps the registry small: it deletes old versions but keeps anything
deployed or released, and always starts as a dry run.

## Who can do what

Everything here is guarded by the **Pacts** resource. **Viewer** can read; **Editor** can publish,
verify, record deployments and create webhooks — give CI an API key from an Editor; only **Admin**
and **Owner** can delete. Each page's *Who can do what* section has the details, and custom roles
get **Pacts** on [Roles](../../workspace/roles.mdx).
