Apiome is a Pact Broker. The `pact-broker` CLI, the `pact` CLI, pact-js and pact-jvm work against
it unchanged: give them your workspace's **broker base URL**
(`https://api.apiome.dev/v1/tenants/<workspace>/pact-broker`) and an API key as the **token**.
Consumers publish their pacts, providers verify them and report back, deploy jobs record what runs
where, and `can-i-deploy` stops a release that would break something.

All of it is served through the API and the Pact tools, and you can read and act on it in the
[**Contracts** workspace](#the-contracts-workspace) of the app.

## When to use it

- **You test with Pact and want the broker next to your specs.** Your pacts, verification results
  and deployments live in the same workspace as the projects that describe your APIs, under the
  same members, roles and API keys.
- **You are moving off a self-hosted Pact Broker.** Point the same CLI commands and library
  options at Apiome; [Pact Broker compatibility](./compatibility.mdx) lists every endpoint and
  whether Apiome serves it.
- **You want deploys gated on contracts.** Ask [can-i-deploy](./can-i-deploy.mdx) before each
  deployment, and let [contract webhooks](./webhooks.mdx) start a provider build when a pact
  changes.

## The Contracts workspace

**Click Contracts** in the rail (under **Ship**). It opens on **Pacticipants**, whose header links
to **Matrix**, **Can I deploy?**, **Webhooks** and **Environments**. Every screen is open to
anyone who can view pacts, and each empty screen shows the CLI command that fills it.

| Screen | How you get there | What it shows |
| --- | --- | --- |
| [**Pacticipants**](./pacticipants.mdx) | **Contracts** in the rail | Every application in your pacts; each one's versions, branches, tags, environments and pacts |
| [**Pact detail**](./pact-detail.mdx) | A pact on a pacticipant's **Pacts** section | One pact's interactions, its verification status and what changed since the previous pact |
| [**Network**](./network.mdx) | **Network diagram** on a pacticipant's **Pacts** section | The pacticipants connected through pacts, each integration coloured by its verdict |
| [**Verification**](./verification-console.mdx) | **Verification** on a provider's **Pacts** section | A provider's results with their logs and mismatches; re-run one pact or verify the stale ones |
| [**Matrix**](./matrix.mdx) | **Matrix** on the **Pacticipants** header | Which consumer versions were verified against which provider versions, with the verdict explained |
| [**Can I deploy?**](./can-i-deploy.mdx#check-in-the-console) | **Can I deploy?** on the **Pacticipants** header | Whether one version is safe to deploy to an environment, and the CLI command that asks the same |
| [**Webhooks**](./webhooks-console.mdx) | **Webhooks** on the **Pacticipants** header | Contract webhooks and every delivery; create, test and redeliver |
| [**Environments**](./environments-dashboard.mdx) | **Environments** on the **Pacticipants** header | Which version runs where, each environment's deployment history, and the deploy simulator |
| [**Pact comparisons**](./bi-directional.mdx#in-the-app) | `/ade/dashboard/pacts/comparisons` | The fidelity report of each bi-directional comparison |
| [**Provider states**](./provider-states.mdx#see-provider-states-in-the-app) | `/ade/dashboard/pacts/provider-states` | A provider's registered states, and a check of its pacts against them before a run |

A project's **Consumers** screen can also
[publish a pact to the broker](./publish-pacts.mdx#publish-from-the-import-dialog) while you import
it: **click “Import Pact file”** and **tick “Also publish to the Pact Broker”**.

## How the pieces fit

1. **The consumer publishes.** Its Pact tests write a pact file, and its build
   [publishes it](./publish-pacts.mdx) with the consumer version and branch. The consumer and the
   provider are registered as [pacticipants](./concepts.mdx) the first time a pact names them.
   Identical pacts are stored once as one **pact version**, so an unchanged pact is verified once.
2. **A webhook starts the provider.** A
   [`contract_requiring_verification_published`](./webhooks.mdx#events) webhook fires for each
   provider version that has not verified the pact yet — the head of the main branch and what is
   deployed or released — and can start a GitHub Actions workflow directly.
3. **The provider verifies.** Its verifier sends
   [consumer-version selectors](./selectors.mdx) (`{ mainBranch: true }`, `{ deployedOrReleased: true }`)
   and gets each pact to check once. With `enablePending`, a new expectation comes back
   [pending](./pending-and-wip.mdx) and its failure does not fail the build.
4. **The verifier reports back.** It [publishes a result](./verification-results.mdx) per pact:
   passed or failed, with the outcome of each interaction. Results are what the matrix is made of.
5. **Deploy jobs record where versions run.** `pact-broker record-deployment` (or
   `record-release`) [records each version](./environments.mdx) in its environment, replacing the
   one deployed there before.
6. **Can-i-deploy decides.** Before each deployment,
   [`pact-broker can-i-deploy`](./can-i-deploy.mdx) reads the matrix against what runs in the
   target environment and answers **yes**, **no** or **unknown**, with a reason for each
   integration. The job stops when the answer is not yes.

**Apiome as the verifier.** A provider without a Pact library in its language can leave steps 3
and 4 to Apiome. One request [verifies it from Apiome](./hosted-verification.mdx): the same
selectors pick the pacts, each pact is [compiled into a contract suite](./verification.mdx), the
[provider states](./provider-states.mdx) are set up, and every interaction is replayed against a
registered verification target. Apiome then publishes a result for each pact. This covers HTTP
interactions, gRPC calls recorded by the Pact protobuf plugin, and GraphQL operations.

**Bi-directional instead of a verifier.** A provider that does not run Pact verification publishes
its OpenAPI document as a [provider contract](./bi-directional.mdx) instead, with
[self-verification evidence](./bi-directional.mdx#self-verification-evidence) from a tool such as
Schemathesis, Dredd or Newman. Apiome compares each pact with that document by the
[comparison rules](./comparison-rules.mdx) as soon as either side publishes, and stores the verdict
as a verification result, so steps 4 and 6 work the same way. A consumer without Pact tests can
[export a pact](./bi-directional.mdx#consumers-without-a-pact-file) from the surface it declared in
Apiome. A provider that sends messages publishes its AsyncAPI document instead, and its consumers'
[message pacts](./message-pacts.mdx) are compared with it the same way.

Along the way, [badges](./badges.mdx) show the state of a public project's pacts, and
[retention](./retention.mdx) keeps the registry small: it deletes old versions but keeps anything
deployed or released, and always starts as a dry run.

## Who can do what

Everything here is guarded by the **Pacts** resource. **Viewer** can read; **Editor** can publish,
verify, record deployments and create webhooks — give CI an API key from an Editor; only **Admin**
and **Owner** can delete. Each page's *Who can do what* section has the details, and custom roles
get **Pacts** on [Roles](../../workspace/roles.mdx).
