`apiome pact` is the Apiome CLI's Pact Broker command group. It has the commands of the
`pact-broker` CLI you already run in CI — `publish`, `can-i-deploy`, `record-deployment` and the
rest — with the same flags, the same sentences in the log and the same exit codes. A pipeline moves
over by changing `pact-broker` to `apiome pact`.

It also has the commands only Apiome has: publishing an OpenAPI
[provider contract](./bi-directional.mdx), [hosted verification](./hosted-verification.mdx),
[sending a verifier report](./verification-results.mdx#send-a-report-from-your-own-ci),
[exporting a consumer surface as a pact](./publish-pacts.mdx) and
[exporting a pact as a Postman collection](#export-a-pact-as-a-postman-collection). There is no
screen for these commands; they run in a terminal or a CI job, and an AI agent can
[ask the same questions over MCP](#ask-from-an-ai-agent-mcp).

## Before you start

You need:

1. **The Apiome CLI.** See [Install the CLI](../../reference/install-the-cli.md).
2. **The broker base URL** of your workspace — your API address followed by
   `/v1/tenants/<workspace>/pact-broker`, for example
   `https://api.apiome.dev/v1/tenants/acme/pact-broker`.
3. **An API key** from a member whose role holds **Pacts** → **Create** (the built-in **Editor**
   role does). Create one on [API keys](../../workspace/api-keys.mdx). Read-only commands such as
   `can-i-deploy` need only **Pacts** → **View**. Give each job a key with a
   [Pact scope](#pact-keys-and-scopes) rather than full access.

## Point the CLI at your workspace

`apiome pact` reads the two variables Pact tooling already uses:

```bash
export PACT_BROKER_BASE_URL=https://api.apiome.dev/v1/tenants/acme/pact-broker
export PACT_BROKER_TOKEN=<your API key>
```

The broker base URL names both the API and the workspace, so nothing else is needed. If you
already use the Apiome CLI, `APIOME_BASE_URL`, `APIOME_TENANT_ID` and `APIOME_API_KEY` work too.

When several are set, the first one found wins:

| Order | Where | Base URL | Credential |
| --- | --- | --- | --- |
| 1 | The command's flags | `--broker-base-url` (`-b`) | `--broker-token` (`-k`) |
| 2 | The CLI's root flags | `apiome --base-url … --tenant …` | `apiome --api-key …` |
| 3 | Pact's variables | `PACT_BROKER_BASE_URL` | `PACT_BROKER_TOKEN` |
| 4 | Apiome's settings | `APIOME_BASE_URL` + `APIOME_TENANT_ID` | `APIOME_API_KEY` |

Prefer the variables to `-k`: a secret on the command line is visible to other processes.

If your operator set up a [broker host](./publish-pacts.mdx#the-broker-host-alias), the short form
`https://acme.<broker host>` works for the commands that call Pact Broker routes. `list-pacticipants`,
`describe-version --latest` and `verify` call Apiome's own API, which the short form does not
serve; they stop and ask for the long form.

A pipeline set up for basic auth works too: when no token or key is set, `PACT_BROKER_PASSWORD` is
used as the API key and `PACT_BROKER_USERNAME` is ignored. A username without a password stops the
command with the reason.

## Pact keys and scopes

Apiome's broker has no users or passwords of its own: every credential is a workspace
[API key](../../workspace/api-keys.mdx). Pact tooling may send it three ways, and all three are
the same key:

| Tooling setting | Sent as |
| --- | --- |
| `--broker-token`, `PACT_BROKER_TOKEN`, `pactBrokerToken` | `Authorization: Bearer <api-key>` |
| `--broker-username` / `--broker-password`, `PACT_BROKER_USERNAME` / `PACT_BROKER_PASSWORD`, `pactBrokerUsername` / `pactBrokerPassword` | Basic auth: the **password** is the API key; the username can be anything |
| `apiome pact` | `X-API-Key: <api-key>` |

Basic auth with an empty password, or any other `Authorization` scheme, is refused with `401` and
a message that says where the key goes.

Three scopes keep a Pact key away from everything else in the workspace. Each admits only the
broker (`/v1/tenants/<workspace>/pact-broker`) and the hosted verifier
(`/v1/tenants/<workspace>/pact-verifier`); `pact:read` also reads the workspace's
[pacticipants](./concepts.mdx):

| Scope | Allows | Commands |
| --- | --- | --- |
| `pact:read` | Every read of the broker, the hosted verifier and the pacticipants, and fetching the pacts to verify | `can-i-deploy`, `describe-version`, `list-pacticipants`, a verifier fetching its pacts |
| `pact:publish` | Publishing pacts and provider contracts, tagging a version or recording its branch, recording a deployment or release | `publish`, `publish-provider-contract`, `record-deployment`, `record-undeployment`, `record-release`, `record-support-ended` |
| `pact:verify` | Publishing verification results, sending a verifier report, hosted verification, registering provider states, tagging the provider version | `verify`, `publish-verification-results`, a Pact verifier with `publishVerificationResults` |

Create a key with the matching preset on [API keys](../../workspace/api-keys.mdx):

| Job | Preset | Scopes |
| --- | --- | --- |
| Gate a deploy with `can-i-deploy` only | **Pact: read-only** | `pact:read` |
| Publish a consumer's pacts; record deployments | **Pact: consumer + deploy** | `pact:read` `pact:publish` |
| Verify a provider in CI | **Pact: CI verifier** | `pact:read` `pact:verify` |

:::note Security
- A Pact scope is checked **before** the key's role: the member who created the key still needs
  **Pacts** → **View** (reads) or **Create** (writes), and a key works only in its own workspace.
- Deleting anything, webhooks, environments and cleanup need a **Full access** key — run
  `create-environment` and `create-webhook` with one, once, outside the pipeline. So do
  `export-consumer-contract` and `publish-consumer-contract`, which call a project's consumer
  contracts rather than the broker.
- A CI verifier key cannot publish a pact, so a compromised provider build cannot change what its
  consumers expect.
- Store the key as a CI secret and prefer the variables to `-k`.
:::

## The commands

| Command | Does | Replaces |
| --- | --- | --- |
| `publish` | Publish pact files for a consumer version | `pact-broker publish` |
| `list-pacticipants` | List the workspace's pacticipants | `pact-broker list-pacticipants` |
| `describe-version` | Show a version's branches, tags and build URL | `pact-broker describe-version` |
| `can-i-deploy` | Ask whether a version can be deployed | `pact-broker can-i-deploy` |
| `record-deployment` | Record a deployment to an environment | `pact-broker record-deployment` |
| `record-release` | Record a release to an environment | `pact-broker record-release` |
| `create-environment` | Create an environment | `pact-broker create-environment` |
| `create-webhook` | Create a contract webhook | `pact-broker create-webhook` |
| `verify` | Verify a provider with Apiome's hosted verifier | a Pact verifier in your build |
| `publish-provider-contract` | Publish an OpenAPI provider contract with its evidence | `pactflow publish-provider-contract` |
| `publish-verification-results` | Send a report from a verifier you ran | — |
| `export-consumer-contract`, `publish-consumer-contract` | Turn a declared consumer surface into a pact | — |
| `export-postman` | Write a pact as a Postman collection with test scripts | — |
| `migrate` | Import a Pact Broker or PactFlow workspace | not available yet |

Every option of every command is in the [CLI reference](../../reference/cli/pact.md).

## Publish pacts

```bash
apiome pact publish ./pacts \
  --consumer-app-version "$GIT_COMMIT" \
  --branch "$GIT_BRANCH" \
  --build-url "$CI_BUILD_URL"
```

Name pact files or folders; a folder publishes every `*.json` file in it. Every file is read
before anything is sent, and a file that is not a pact stops the run with its name and the reason.
Pacts of several consumers are sent as one request per consumer.

Give the commit SHA as `--consumer-app-version`, as above. Apiome can then post each pact's verdict
to that commit as a GitHub or GitLab status: **pending** until the provider verifies it. See
[Commit statuses](./commit-statuses.mdx).

- `--auto-detect-version-properties` (`-r`) reads the branch and build URL from GitHub Actions,
  GitLab, Jenkins, Buildkite, CircleCI, Travis, Bitbucket, AppVeyor, CodeShip or Azure DevOps, and
  falls back to `git`.
- `--tag` (`-t`) tags the version; `--tag-with-git-branch` (`-g`) tags it with the detected branch.
- `--merge` is refused: Apiome keeps the pact a version published, and refuses a different one for
  the same version.

## Ask can-i-deploy

```bash
apiome pact can-i-deploy \
  --pacticipant "Billing Service" --version "$GIT_COMMIT" \
  --to-environment production \
  --retry-while-unknown 6 --retry-interval 10
```

It prints the matrix rows, then `Computer says yes \o/` or `Computer says no ¯\_(ツ)_/¯` with the
reason — the lines `pact-broker` prints. Name the version one way: `--version`, `--latest`
(with `--tag` for the latest tagged version), `--branch` or `--main-branch`. Use `--to` for a tag
instead of an environment, and `--ignore` to leave an application out. `--dry-run` prints the
verdict without stopping the job. One pacticipant is checked per run; check several by running the
command once for each.

See [Can I deploy?](./can-i-deploy.mdx) for how the verdict is reached.

## Record deployments and releases

```bash
apiome pact create-environment --name production --display-name Production --production
apiome pact record-deployment --pacticipant "Billing Service" --version "$GIT_COMMIT" --environment production
apiome pact record-release --pacticipant "Mobile App" --version 4.2.0 --environment production
```

The environment is found by name. An unknown name stops with the `create-environment` command that
creates it. Add `--application-instance` (`--target`) to `record-deployment` when the application
runs several copies in one environment. See [Environments and deployments](./environments.mdx).

## Ask from an AI agent (MCP)

An agent connected to Apiome's [MCP server](../../getting-started/connect-an-mcp-host.mdx) can ask
the same questions without a terminal. Four MCP tools cover the commands an agent needs most:

| Tool | Does what this command does | Needs |
| --- | --- | --- |
| `pact.list` | Lists the latest pact of each consumer and provider pair, with how its latest verification went | **Pacts** → **View** |
| `pact.matrix` | `GET …/matrix`: the verdict and the rows behind it | **Pacts** → **View** |
| `pact.can_i_deploy` | `apiome pact can-i-deploy` | **Pacts** → **View** |
| `pact.record_deployment` | `apiome pact record-deployment` | **Pacts** → **Create** |

For example, an agent asks `pact.can_i_deploy` with
`{"pacticipant": "Billing Service", "version": "4f1e2d0", "to_environment": "production"}`. It
reads `summary.deployable`: `true`, `false`, or `null` while a verification result is still
missing. On `null`, `retryAfterSeconds` says how many seconds to wait before asking again.

- **Use an MCP key.** Create one with **Create MCP key** on
  [API keys](../../workspace/api-keys.mdx#create-an-mcp-key). A REST API key does not work here.
  Apiome checks the **Pacts** permissions of the person who created the key. If that person loses the permission,
  the key loses it too. A key whose creator was removed is refused with
  `mcp-pact-key-has-no-owner`. Create a new key in that case.
- **Use the whole workspace.** Pacts belong to the whole workspace, so a key limited to projects
  is refused.
- **Answers are bounded.** `pact.list` returns up to 100 pacts a page. Pass `nextCursor` back as
  `cursor` to get the next page. `pact.matrix` and `pact.can_i_deploy` return up to `max_rows`
  rows (default 50, at most 100). `rowsTotal` and `rowsTruncated` say how many rows were left out.
  The verdict always counts every row.
- **Nothing is ignored.** If a selector has a key the tool doesn't know, or a value of the wrong
  type, or you give both `to_environment` and `to_tag`, the tool refuses it and says why. A refusal
  from Apiome includes its code in brackets, such as `[pact-matrix-invalid]`.
- **Recording is a write.** `pact.record_deployment` is marked as a write, so MCP hosts can ask before
  they run it. The four tools form the **pact** toolset. Admins can turn it off for the workspace,
  or for one key, in [MCP settings](../../workspace/tenants.mdx#mcp-settings).

Every argument is listed in the [MCP tool reference](../../reference/mcp/tools.md#pact-can-i-deploy).

## Create a webhook

```bash
apiome pact create-webhook https://ci.example.com/hooks/ledger \
  --request POST \
  --header "Content-Type: application/json" \
  --data '{"pact": "${pactbroker.pactUrl}"}' \
  --provider "Ledger API" \
  --contract-requiring-verification-published
```

Choose at least one event flag. `--data @body.json` reads the body from a file. The password of
`--user name:password` is stored sealed and never printed. See
[Contract webhooks](./webhooks.mdx).

## Verify a provider

```bash
apiome pact verify \
  --provider "Ledger API" --provider-app-version "$GIT_COMMIT" --branch main \
  --target ledger-staging \
  --consumer-version-selector '{"mainBranch": true}' \
  --consumer-version-selector '{"deployedOrReleased": true}' \
  --enable-pending
```

Apiome replays each selected pact against the registered verification target `ledger-staging`
and publishes a result per pact. It prints one row per pact and every interaction it could not
replay, with the reason. `--no-publish-verification-results` is a dry run. See
[Verify a provider from Apiome](./hosted-verification.mdx). Each published result is also posted as
a [commit status](./commit-statuses.mdx) to the provider's commit and to the consumer's commit,
when their version numbers are commit SHAs.

## Export a pact as a Postman collection

`export-postman` writes a pact as a **Postman Collection v2.1**. A provider team can then run the
consumer's requests in Postman, or in CI with Newman, before any Pact tooling is set up:

```bash
apiome pact export-postman --provider "Ledger API" --consumer "Billing Service" --branch main \
  --provider-base-url http://localhost:8080 -o ledger.postman_collection.json
newman run ledger.postman_collection.json
```

1. **Choose the pact.** `--provider` and `--consumer` give the latest pact between them. Add one of
   `--consumer-version`, `--tag`, `--branch` or `--pact-version` (the content SHA) to pick another
   one. To export a pact file you have not published yet, use `--pact-file billing-ledger.json`
   instead.
2. **Point it at the provider.** Requests go to `{{baseUrl}}`. `--provider-base-url` fills in that
   variable. Without it, the variable is empty: set it in Postman, or pass
   `newman run … --env-var baseUrl=http://localhost:8080`.
3. **Set up the provider states.** Postman cannot set them up for you. Each request's description
   names its states (`Given: an invoice 1042 exists`), and the summary lists them all.

Each HTTP interaction becomes one request, with a saved example of the expected response and a test
script. The script checks the status, each expected header and the body by Pact's default rules: an
object may carry extra keys, an array must have the same length, and every other value must be
equal. `--no-tests` leaves the scripts out.

The summary lists everything the collection does not carry, with the reason:

| Outcome | For |
| --- | --- |
| `left-out` | Message interactions, gRPC calls, interactions without a method, and request bodies that are not text. Postman sends HTTP requests with text bodies only. |
| `not-asserted` | Response values governed by a matching rule (a regex or type match would be stricter as an equality test), and response bodies that are not text. The saved example still shows the recorded values. |
| `not-applied` | Request generators: the request sends the pact's example values. |
| `info` | The provider states to set up before the run. |

`--fail-on-left-out` exits `1` when an interaction was left out. A pact with no HTTP interaction at
all is refused with `pact-postman-no-http-interactions`. To make a collection from an API
specification rather than a pact, use `apiome export postman` (see
[Export to an API client](../export-to-an-api-client.md)). The command calls
`POST …/v1/tenants/<workspace>/pact-postman-collections`
([REST reference](../../reference/rest/pact-broker.md)) and needs **Pacts** → **View**.

## Choose the output

`--output` (`-o`) picks the format of every command:

| Value | Prints |
| --- | --- |
| `table` | Aligned columns and `pact-broker`'s sentences (the default) |
| `json` | The server's answer, unchanged — the same as `apiome --json pact …` |
| `markdown` | Tables and lists ready for a job summary or a pull-request comment |

```bash
apiome pact can-i-deploy -a "Billing Service" -e "$GIT_COMMIT" --to-environment production \
  -o markdown >> "$GITHUB_STEP_SUMMARY"
```

## Exit codes

`apiome pact` exits like `pact-broker`:

| Code | Means |
| --- | --- |
| `0` | It worked; for `can-i-deploy`, the version can be deployed (or `--dry-run`); for `verify`, the run passed |
| `1` | Anything else: the server refused (no permission, a key of another workspace, an unknown version, a conflict), a flag was wrong, `can-i-deploy` said no or could not decide, or `verify` failed |

The rest of the Apiome CLI exits `2` for a bad flag or a refused request; inside `apiome pact` both
are `1`, so a script written for `pact-broker` keeps working. The message on stderr says what went
wrong.

## Migrating from a Pact Broker

`apiome pact migrate` is listed so that pipelines can find it, but the import of an existing Pact
Broker or PactFlow workspace is not available yet. The command exits `1`, says so, and reads and
writes nothing.
