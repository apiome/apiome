A **maturity ladder** is an ordered list of levels, such as **Bronze**, **Silver** and **Gold**,
that the APIs scored against a style guide climb. Each style guide has at most one ladder. A
level answers the question "what level is this API at?" with requirements a team can see and
meet, instead of a single grade.

A guide's **Policy** tab on [Style guides](./style-guides.mdx#policy) does not show the ladder yet,
so a ladder is read and saved through the REST API (see [With the API](#with-the-api)). Saving a ladder records it in the guide's history and its
policy pack. From then on every policy evaluation of a version or MCP server version reports its
level — read it with [`GET …/lint/level`](#read-a-level). Set a **required publish level** and
the level also gates publishing, the deploy gate, the API change check suite and the lint CI gate
(see [Gate publishing on a level](#gate-publishing-on-a-level)).

## What a level requires

A level lists what it **adds** to the levels below it:

| Field | What it requires |
| --- | --- |
| `rules` | For each listed rule, the worst finding severity it may still report: `error`, `warning`, `info` or `none` (the rule must report nothing). Rule ids come from [Built-in lint rules](../build/lint-rules.md). |
| `axes` | A floor on an [axis score](../build/axis-score.md): `quality`, `protocol`, `security`, `supply_chain`, `supportability` or `compatibility`, with a `minGrade` (A–F), a `minScore` (0–100) or both. The axis must be assessed. |
| `evidence` | Evidence the level needs: `review_approved` (an approved [review](./reviews.mdx)) or `verification_passing`. |
| `waiversSatisfy` | Whether a waived finding counts as meeting a rule requirement. Leave it out and it is `true` on every level except the top one. |

Each level also has a `key` (lowercase, such as `bronze`) and a `label` (such as `Bronze`). List
levels lowest first.

## Levels are cumulative

Level *n* includes every requirement of the levels below it, so you never repeat a requirement
to keep it. A level may restate a requirement at the same strength, or tighten it. It may not
relax one. The save is refused when a level:

- lets a rule report a worse severity than a lower level allows (for example `warning` at Bronze,
  `error` at Silver);
- asks for a worse `minGrade` or a lower `minScore` on an axis a lower level already set;
- turns `waiversSatisfy` on after a lower level turned it off.

The refusal is `422` with `detail.code` `ladder-level-not-cumulative`, the `level` and `rule` at
fault, and a `pointer` into the request body:

```json
{
  "detail": {
    "code": "ladder-level-not-cumulative",
    "message": "Level 'silver' relaxes rule 'naming.schema-pascal-case' to maxSeverity 'error'; level 'bronze' already requires 'warning'",
    "pointer": "/levels/1/rules/0/maxSeverity",
    "level": "silver",
    "rule": "naming.schema-pascal-case"
  }
}
```

Other refusals use the same shape:

| `detail.code` | Why |
| --- | --- |
| `ladder-unknown-rule` | A `ruleId` is not a built-in rule. |
| `ladder-unknown-axis` | An `axis` is not one of the six axis keys. |
| `ladder-axis-threshold-missing` | An axis entry has neither `minGrade` nor `minScore`. |
| `ladder-duplicate-level`, `ladder-duplicate-rule`, `ladder-duplicate-axis` | A level key, or a rule or axis within one level, is listed twice. |
| `ladder-empty` | The ladder has no levels. A guide without a ladder has none; it is never an empty ladder. |
| `ladder-invalid` | Any other malformed field. |

## The default ladder

The built-in **Apiome Recommended** guide comes with a read-only default ladder you can start
from. It is a template: it is not applied to your workspace, and the built-in guide itself has no
ladder.

| Level | Requires |
| --- | --- |
| **Bronze** | No error-severity findings, except from documentation rules. |
| **Silver** | Bronze, plus a quality grade of B or better and no errors at all. |
| **Gold** | Silver, plus a quality grade of A, the security axis assessed at A with every security rule clean, and an approved review. |

Waivers count at Bronze and Silver. Gold, the top level, asks for waived findings to be fixed.

## How a level is judged

Levels are checked lowest first, and the check stops at the first level that is not met. That
level is the **next level**, and what keeps the API from it are its **blockers**. Each level is
checked against everything it and the levels below it require:

- **Rules** — a finding of a listed rule that is worse than the rule's `maxSeverity` blocks the
  level. Findings marked **fixed** or **false positive** never count. A **waived** finding counts
  only on a level whose `waiversSatisfy` is off; an expired waiver, or one that is only
  requested, counts like an open finding.
- **Axes** — the axis must be **assessed** and meet the floor. An axis that was never assessed
  blocks the level with `reason: not_assessed`. It is never treated as clean: a version whose
  security axis was never scored cannot reach a level that asks for security.
- **Evidence** — `review_approved` is met by an approved [review](./reviews.mdx) of the version
  (the guide's approval rules, or one approval when the guide sets none); `verification_passing`
  by a passing verification-policy evaluation. Missing evidence blocks with `reason: missing`,
  evidence that cannot be read with `reason: not_assessed`. MCP server versions have neither, so
  a level that asks for evidence is `not_assessed` for them.

A version that meets no level has `level: null` with `reason: below-first-level`. A guide without
a ladder gives `level: null` with `reason: no-ladder` — never a level.

## What is recorded

A saved ladder is frozen beside the rules and gates in two places, so a later level can always
be explained by the ladder that was in force:

- the guide's **revision history** gains a `ladder_changed` revision whose `ladder` field holds
  the ladder (and whose snapshot fingerprint moves);
- a new **policy version** is published with the ladder (`ladder` on
  `GET …/policy-versions/{id}`), and its content fingerprint moves.

The save is also written to the access audit as `style_guide.ladder_changed`. Saving the same
ladder again records nothing. Revisions and policy versions of a guide without a ladder say
`"ladder": null`.

## With the API

Any workspace member can read a guide's ladder. Only a workspace administrator can save one, and
the built-in guide's ladder cannot be set (`409 STYLE_GUIDE_READ_ONLY`).

```bash
# Read the ladder — "ladder": null when the guide has none.
# For the built-in guide, "template" holds the default ladder.
curl -H "Authorization: Bearer $TOKEN" \
  https://<host>/v1/style-guides/acme/$GUIDE_ID/ladder

# Save a two-level ladder
curl -X PUT -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  https://<host>/v1/style-guides/acme/$GUIDE_ID/ladder \
  -d '{
    "name": "Payments maturity",
    "levels": [
      {"key": "bronze", "label": "Bronze",
       "rules": [{"ruleId": "naming.schema-pascal-case", "maxSeverity": "warning"}]},
      {"key": "silver", "label": "Silver",
       "axes": [{"axis": "quality", "minGrade": "B"}]}
    ]
  }'
```

The response returns the stored `ladder`, its `contentFingerprint` and `updatedAt`. The endpoints
are in the [Style guides REST reference](../reference/rest/style-guides.md#get-style-guide-ladder-v1-style-guides-tenant-slug-guide-id-ladder-get).

### Read a level

Any workspace member can read the level of a version or an MCP server version:

```bash
curl -H "Authorization: Bearer $TOKEN" \
  https://<host>/v1/versions/acme/$PROJECT_ID/$VERSION_ID/lint/level

curl -H "Authorization: Bearer $TOKEN" \
  https://<host>/v1/mcp/acme/endpoints/$ENDPOINT_ID/versions/$MCP_VERSION_ID/lint/level
```

```json
{
  "subjectType": "catalog_revision",
  "evaluationId": "6f1c…",
  "ladderName": "Payments maturity",
  "level": "bronze", "levelLabel": "Bronze", "levelIndex": 0,
  "nextLevel": "silver", "nextLevelLabel": "Silver",
  "blockers": [
    {"levelKey": "silver", "kind": "axis", "axis": "quality", "minGrade": "B",
     "reason": "below_threshold", "grade": "C", "score": 74, "count": 1, "sample": []}
  ],
  "waiversCounted": 1,
  "unassessedAxes": [],
  "reason": null
}
```

A rule blocker names the `ruleId`, its `maxSeverity`, how many findings are over it (`count`) and
up to three of their fingerprints (`sample`). `waiversCounted` is how many waived findings the
levels the version met have excused, and `unassessedAxes` lists every axis the ladder names that
was never assessed.

The level is part of the version's policy evaluation (`gateResults.maturity` on
`GET …/lint/policy` and `…/lint/gate`). Reading it again with nothing changed returns the same
`evaluationId`; a new finding, decision, axis score or ladder records a new evaluation. Add
`?policyVersionId=` to judge an earlier policy version. The endpoints are in the
[Lint REST reference](../reference/rest/lint.md#lint-revision-level-v1-versions-tenant-slug-project-id-version-record-id-lint-level-get)
and the [MCP catalog REST reference](../reference/rest/mcp-catalog.md#get-mcp-endpoint-version-lint-level-v1-mcp-tenant-slug-endpoints-endpoint-id-versions-version-id-lint-level-get).

## Gate publishing on a level

A level becomes binding when the guide names the level a version must reach before it publishes.
Set `requiredPublishLevel` with the guide's policy settings (workspace administrators only):

```bash
curl -X PUT -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  https://<host>/v1/style-guides/acme/$GUIDE_ID/policy \
  -d '{"requiredPublishLevel": "silver", "ciOutcomes": {"failOnMaturityLevel": true}}'
```

- The value must be the `key` of one of the guide's levels. Anything else is refused with `422`
  and `detail.code` `required-publish-level-unknown`, which lists the valid keys. A guide without a
  ladder has no valid keys.
- Send `null` to clear it. Leave the field out to keep the current value.
- The level is frozen into the policy version the save publishes (`requiredPublishLevel` on
  `GET …/policy-versions/{id}`), beside the ladder. Gates read the frozen value.
- While a level is required, a ladder save that drops that level is refused with
  `ladder-required-level-removed`. Clear or change `requiredPublishLevel` first.

Four places then judge the version's level against the required level, with the same rule, so
they never disagree about one version:

| Where | What happens below the required level | Without a ladder |
| --- | --- | --- |
| **Publish** | Refused with `422` and `detail.maturityGate` (level, required level, blockers). Force-publish with a reason gets past it; every judged publish is audited as `version.maturity_gate`. See [Publish a version](../ship/publish-a-version.md#the-maturity-level-gate). | Not armed. |
| **Deploy gate** | The `maturity` signal is `fail`. Set `maturity.minMaturityLevel` in the deploy-gate policy to require a different level; leave it `null` to use the guide's required publish level. See the [Deploy gate REST reference](../reference/rest/deploy-gate.md). | `not_configured`, left out of the verdict. |
| **API change check suite** | The `maturity` component is `fail`. It is `advisory` by default, so it is reported but does not change the verdict until the suite policy makes it `required`. See the [check suite REST reference](../reference/rest/api-check-suite.md). | `skipped`, never `pass`. |
| **Lint CI gate** | `gate.maturityGate` reports the level, and [`apiome lint gate`](../reference/cli/lint.md#lint-gate) prints it. SARIF and JUnit carry it as `apiome.maturity.*` properties. `gate.passed` fails only when the guide's `ciOutcomes.failOnMaturityLevel` is on. | No level line. |

`failOnMaturityLevel` is **off** by default, so an existing pipeline keeps its exit code until you
turn it on.

The level is judged with these statuses:

| Status | Meaning |
| --- | --- |
| `pass` | The version is at or above the required level. |
| `fail` | The version is below it. `blockers` list what keeps it from its next level. |
| `not_configured` | The guide has no ladder, or no level is required. Nothing is judged. |
| `unknown` | The required level is not a level of the frozen ladder, or the level could not be read. Never blocks a publish. |
