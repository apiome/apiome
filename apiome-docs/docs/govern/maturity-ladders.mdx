A **maturity ladder** is an ordered list of levels, such as **Bronze**, **Silver** and **Gold**,
that the APIs scored against a style guide climb. Each style guide has at most one ladder. A
level answers the question "what level is this API at?" with requirements a team can see and
meet, instead of a single grade.

The Style guides screen is not yet available, so a ladder is read and saved through the REST API
(see [With the API](#with-the-api)). Saving a ladder records it in the guide's history and its
policy pack. It does not yet change any lint result, publish or gate.

## What a level requires

A level lists what it **adds** to the levels below it:

| Field | What it requires |
| --- | --- |
| `rules` | For each listed rule, the worst finding severity it may still report: `error`, `warning`, `info` or `none` (the rule must report nothing). Rule ids come from [Built-in lint rules](../build/lint-rules.md). |
| `axes` | A floor on an [axis score](../build/axis-score.md): `quality`, `protocol`, `security`, `supply_chain`, `supportability` or `compatibility`, with a `minGrade` (A–F), a `minScore` (0–100) or both. The axis must be assessed. |
| `evidence` | Evidence the level needs: `review_approved` (an approved [review](./reviews.mdx)) or `verification_passing`. |
| `waiversSatisfy` | Whether a waived finding counts as meeting a rule requirement. |

Each level also has a `key` (lowercase, such as `bronze`) and a `label` (such as `Bronze`). List
levels lowest first.

## Levels are cumulative

Level *n* includes every requirement of the levels below it, so you never repeat a requirement
to keep it. A level may restate a requirement at the same strength, or tighten it. It may not
relax one. The save is refused when a level:

- lets a rule report a worse severity than a lower level allows (for example `warning` at Bronze,
  `error` at Silver);
- asks for a worse `minGrade` or a lower `minScore` on an axis a lower level already set;
- turns `waiversSatisfy` on after a lower level turned it off.

The refusal is `422` with `detail.code` `ladder-level-not-cumulative`, the `level` and `rule` at
fault, and a `pointer` into the request body:

```json
{
  "detail": {
    "code": "ladder-level-not-cumulative",
    "message": "Level 'silver' relaxes rule 'naming.schema-pascal-case' to maxSeverity 'error'; level 'bronze' already requires 'warning'",
    "pointer": "/levels/1/rules/0/maxSeverity",
    "level": "silver",
    "rule": "naming.schema-pascal-case"
  }
}
```

Other refusals use the same shape:

| `detail.code` | Why |
| --- | --- |
| `ladder-unknown-rule` | A `ruleId` is not a built-in rule. |
| `ladder-unknown-axis` | An `axis` is not one of the six axis keys. |
| `ladder-axis-threshold-missing` | An axis entry has neither `minGrade` nor `minScore`. |
| `ladder-duplicate-level`, `ladder-duplicate-rule`, `ladder-duplicate-axis` | A level key, or a rule or axis within one level, is listed twice. |
| `ladder-empty` | The ladder has no levels. A guide without a ladder has none; it is never an empty ladder. |
| `ladder-invalid` | Any other malformed field. |

## The default ladder

The built-in **Apiome Recommended** guide comes with a read-only default ladder you can start
from. It is a template: it is not applied to your workspace, and the built-in guide itself has no
ladder.

| Level | Requires |
| --- | --- |
| **Bronze** | No error-severity findings, except from documentation rules. |
| **Silver** | Bronze, plus a quality grade of B or better and no errors at all. |
| **Gold** | Silver, plus a quality grade of A, the security axis assessed at A with every security rule clean, and an approved review. |

Waivers count at every level of the default ladder.

## What is recorded

A saved ladder is frozen beside the rules and gates in two places, so a later level can always
be explained by the ladder that was in force:

- the guide's **revision history** gains a `ladder_changed` revision whose `ladder` field holds
  the ladder (and whose snapshot fingerprint moves);
- a new **policy version** is published with the ladder (`ladder` on
  `GET …/policy-versions/{id}`), and its content fingerprint moves.

The save is also written to the access audit as `style_guide.ladder_changed`. Saving the same
ladder again records nothing. Revisions and policy versions of a guide without a ladder say
`"ladder": null`.

## With the API

Any workspace member can read a guide's ladder. Only a workspace administrator can save one, and
the built-in guide's ladder cannot be set (`409 STYLE_GUIDE_READ_ONLY`).

```bash
# Read the ladder — "ladder": null when the guide has none.
# For the built-in guide, "template" holds the default ladder.
curl -H "Authorization: Bearer $TOKEN" \
  https://<host>/v1/style-guides/acme/$GUIDE_ID/ladder

# Save a two-level ladder
curl -X PUT -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  https://<host>/v1/style-guides/acme/$GUIDE_ID/ladder \
  -d '{
    "name": "Payments maturity",
    "levels": [
      {"key": "bronze", "label": "Bronze", "waiversSatisfy": true,
       "rules": [{"ruleId": "naming.schema-pascal-case", "maxSeverity": "warning"}]},
      {"key": "silver", "label": "Silver", "waiversSatisfy": true,
       "axes": [{"axis": "quality", "minGrade": "B"}]}
    ]
  }'
```

The response returns the stored `ladder`, its `contentFingerprint` and `updatedAt`. The endpoints
are in the [Style guides REST reference](../reference/rest/style-guides.md#get-style-guide-ladder-v1-style-guides-tenant-slug-guide-id-ladder-get).
