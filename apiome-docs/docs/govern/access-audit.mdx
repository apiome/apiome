**Access audit** is the immutable record of every access and permission change in the workspace —
role and permission changes, members joining and leaving, administrator overrides, style-guide
changes and Browse reader sign-ins. Entries are append-only and hash-chained: they cannot be edited
or deleted, which is what SOC 2 and ISO 27001 access reviews ask for. **Go to Govern → Access
audit.**

<Screenshot id="audit" alt="Access audit: role, permission, member and style-guide events with actor, target and source" />

Every member can read the ledger (it needs `members:view`, which every built-in role has).

## Find events

- **Category chips** — **All events**, **Role changes**, **Permissions**, **Members**, **Admin
  overrides** and **Style guides**, each with its count.
- **Date range** — **Last 24 hours**, **Last 7 days**, **Last 30 days** (the default), **Last 90 days**
  or **All time**.
- **Search actor, event, target…** narrows the rows on screen.

<Screenshot id="audit-filtered" alt="The ledger filtered to Permissions and searched for release, leaving one event" />

The table's columns — **When**, **Actor**, **Event**, **Target** and **Source** (web, api, api_key,
admin, sso, scim or system) — all sort. The foot reads *Showing 1–25 of 140 events · newest first*;
one read reaches at most the 1,000 most recent entries in the range, so narrow the range to reach
older ones. **Refresh** reloads the ledger.

## Read an event

**Click a row** to open its drawer:

- the exact UTC time and a one-sentence summary — *priya.raman@northwind.io assigned a role to
  sam.okafor@northwind.io from the web console.*;
- **Actor** and **Target**, with the before → after values for a change;
- **Recorded detail** — every field the entry stored;
- **Hash chain** — the previous entry's hash, this entry's hash, and whether they link;
- **Event JSON** — the entry exactly as stored, with **Copy**.

**Open roles** or **Open members** in the footer goes to the screen the event changed.

<Screenshot id="audit-drawer" alt="An event's drawer: a role assigned from Editor to Release manager, its detail and verified hash chain" />

## Check the hash chain

Each entry stores the hash of the entry before it, so altering or removing one breaks the chain at
that point. The drawer's **Hash chain** section says which applies:

| Status | Means |
| --- | --- |
| *Verified against the entry written before it.* | The link holds. |
| *Does not match the entry written before it — the chain is broken here.* | Investigate: the ledger was altered. |
| *The first entry in this workspace's chain.* | Nothing came before it. |
| *The entry before it is outside this view, so the link was not checked.* | Widen the date range to check it. |
| *This entry was written without chain hashes.* | It predates hashing. |

<Screenshot id="audit-chain" alt="The Hash chain section: previous and current SHA-256 hashes, verified against the entry before it" />

The chain is checked entry by entry in the drawer; there is no whole-ledger check in the app.

## Export CSV

**Click “Export CSV”** to download `<workspace>-access-audit.csv` with the columns `when`, `actor`,
`event`, `target` and `source`. It covers the chosen category and date range (up to 1,000 rows); the
search box does not narrow it.

## Read it with the REST API

Anyone with **Members: view** can read their workspace's audit:

- `GET /v1/access/{tenant}/audit` lists rows, newest first. `filter` keeps one category: `role`,
  `permission`, `member`, `admin`, `styleGuide` or `portal`. `since` takes an ISO 8601 start time, and
  `limit` caps the count (at most 1000).
- `GET /v1/access/{tenant}/audit/export` returns the same rows as CSV, for access-review evidence.

Each row has **when**, **actor**, **event** (`action`), **target**, **source** and a structured
**detail**, plus `prev_hash` and `entry_hash`, its link in the chain. Both endpoints are in the
[REST reference](../reference/rest/access.md#list-audit-v1-access-tenant-slug-audit-get).

## What is in which audit

The access audit records **who changed access**. Other activity has its own record:

| Record | What it holds | Where to read it |
|---|---|---|
| Access audit | Role, permission, member, admin, style-guide and portal-reader events, plus governance changes such as `agent.toolset.body_samples.update` and each `agent.invocations.export` | This page |
| Agent invocation audit | One row per `tools/call` an agent key makes: key, tool, time, latency, outcome and sizes, never a body | [Agent access → Export the invocation audit](../bring-in/agent-access.mdx#export-the-invocation-audit), one finalized UTC day at a time as JSON Lines or CSV |
| Usage export | Daily usage rollups of a project's API traffic | [Runtime usage → Export usage](./runtime-usage.mdx#export-usage) |

## Browse reader events

[Portal readers](../ship/portal-readers.mdx) sign in to Browse with an email link. Their events have
source `portal`, and `filter=portal` lists only them:

| Event | Recorded when | Detail |
|---|---|---|
| `portal.reader.enrolled` | A person signs in to the portal for the first time and becomes a reader. | `source` (`magic_link`), `membership_id` |
| `portal.reader.signed_in` | A sign-in link is exchanged for a session. | `session_id`, `method`, `user_agent_family` (for example `Firefox`) |
| `portal.reader.session_revoked` | A reader signs out. | `session_id`, `reason` |

The actor and target of each row are the reader's email address. Rows never contain a sign-in link,
a session token, an IP address or a full browser string.

A request for a sign-in link is not recorded. A link that was never used leaves no trace in the
audit.

## Pact Broker events

Every change to the [Pact Broker](../ship/pact-broker/overview.mdx) writes one row, whether it came
from the Pact CLI, a Pact library, the console or an MCP tool. Source `api_key` is a CI runner's key;
`web` is a signed-in member. The target names what changed, for example
`pacticipant/billing-service/version/3f2a9c1` or `pact-webhook/<uuid>`.

| Event | Recorded when |
|---|---|
| `pacts.pacticipant.create`, `pacts.pacticipant.update` | A pacticipant is registered or changed. |
| `pacts.version.record`, `pacts.tag.add` | A version is recorded (also on a branch) or tagged. |
| `pacts.publication.create` | Pacts are published (`pact-broker publish`, a single pact, or from a project's **Consumers** screen). |
| `pacts.verification.publish` | A verifier publishes a result, or an external report is ingested. |
| `pacts.verification.run` | Apiome runs a verification (**Verify**, **Re-verify**, **Verify stale pacts**). |
| `pacts.environment.create`, `.update`, `.delete` | An environment is created, changed or deleted. |
| `pacts.deployment.record`, `pacts.deployment.update` | A deployment is recorded, or marked undeployed. |
| `pacts.release.record`, `pacts.release.update` | A release is recorded, or its support ended. |
| `pacts.webhook.create`, `.update`, `.delete` | A webhook is created, changed or deleted. |
| `pacts.webhook.execute`, `pacts.webhook.redeliver` | A webhook is tested, or a delivery is sent again. |
| `pacts.provider_state.create`, `.update`, `.delete` | A provider state is created, changed or deleted. |
| `pacts.commit_status.retry` | A commit status is sent again. |
| `pacts.verification_settings.update` | The workspace's [verification settings](../ship/pact-broker/stale-pacts.mdx) are saved. |
| `pacts.verification_override.save`, `.delete` | A verification override is saved or removed. |
| `pacts.republish_request.acknowledge` | A consumer acknowledges a re-publish request. |
| `pacts.secret.create`, `.update`, `.delete` | A [workspace secret](../ship/pact-broker/secrets.mdx) is created, rotated or changed, or deleted. The entry never holds the value. |
| `pacts.contract_source.update` | A provider's [standing contract sources](../ship/pact-broker/bi-directional.mdx#publish-automatically) are changed (**Do this on every publish**, **Follow this file**, or a source stopped). |
| `pacts.contract.auto_publish` | A standing source published (or tried to publish) a provider contract. The detail holds the `trigger` (`project-publish` or `push`), the `outcome` (`published`, `unchanged`, `failed` or `skipped`), the source and, unless it published, the `reason`. Its source is `system`. |
| `pacts.migration.import` | A batch of records [imported from another Pact Broker](../ship/pact-broker/migration.mdx) (one entry per request of `apiome pact migrate`). The entry never holds the records. |
| `pacts.pacticipant.delete`, `.restore`, `pacts.version.delete`, `.restore` | A pacticipant or version is deleted or restored; the detail holds the `reason`. |
| `pacts.label.add`, `pacts.label.remove` | A label is added or removed. |
| `pacts.retention.apply`, `pacts.purge` | A retention run is applied, or deleted rows are purged after 30 days; the detail holds the counts. |
| `pacts.settings.commit_statuses`, `pacts.settings.agents` | A Contracts admin changes the [commit-status switches](../ship/pact-broker/commit-statuses.mdx#choose-which-statuses-are-written) or [what agents may do](../ship/pact-broker/cli.mdx#choose-what-agents-may-do); the detail holds the switches. |
| `pacts.agent.refused` | An MCP agent asked for a pact action the workspace's Agents switches refuse, or to record a deployment to production; the detail holds the action and the code. |

The detail holds the route, its path parameters and, when the call created something, its id. It
never holds a request body, so a webhook's token or a pact's content is never copied into the audit.
A call that is refused changes nothing and writes no `pacts.*` row; a missing permission writes
`permission.denied`.

## Security probe consent events

[Security probe consent](../ship/contract-testing-and-ci-gates.mdx#grant-consent-before-security-probes)
on a verification target is recorded here, with the target's id as the row's target:

| Event | Recorded when | Detail |
|---|---|---|
| `security_probe.consent.grant` | Someone grants consent (replacing any earlier consent on the target). | `consent_id`, `target_slug`, `environment`, `profiles_allowed`, `expires_at`, which `identities` were named, `replaced_consent_ids` |
| `security_probe.consent.revoke` | Someone revokes the target's consent. | `consent_id`, `target_slug` |
| `security_probe.run.refused` | A probe run is refused before it sends anything. | `code` (for example `probe-consent-missing`, `probe-consent-expired`, `probe-kill-switch-off`), `profile`, `explicit_approval`, `consent_id` |

The detail never contains a credential: an identity is listed by name (`identity_a`), not by the
reference it points to.
