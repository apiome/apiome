<Route path="/ade/dashboard/repositories" />

Register a Git repository and Apiome scans it for API specifications you can import — one at a time
or many at once — and keeps them refreshed. **Go to Bring in → Repositories.** The tabs across the
top are **Repositories**, **Discovered specs**, **Quota & rate limits** and **Webhook IP
allowlist**.

<Screenshot id="repositories" alt="Repositories: one summary line — 4 repositories, files indexed, imports, last scan, 1 needs attention and a 1 stale · 1 failed chip — above the repository table" />

One line under the header sums up the workspace: how many **repositories**, **files indexed**,
**imports (30d)**, the **last scan** and — when there are any — how many **need attention**.
**Click “Show stats”** to open the same figures as a row of cards, with the split by provider;
the page remembers your choice.

The line ends with a **Refresh activity** chip. While any spec imported from a repository is
stale or failed to refresh, the chip says so — for example *1 stale · 1 failed*. **Click the
chip** to open **Refresh activity**: a count of specs in each refresh state and the repositories
that need attention, each linking to its **Specs** tab.

<Screenshot id="repositories-refresh-activity" alt="Refresh activity in a drawer: specs by refresh state and two repositories that need attention" />

The list shows each repository's **Provider**, **Branch**, **Files**, **Health**, **Status**, **Last
scan** and how many files are **Importable**. Filter by provider and visibility, sort by most recently
scanned or by name, and switch between **Grid** and **List**. A row's menu has **Open detail** and
**Remove from list**.

## Add a repository

<Route path="/ade/dashboard/repositories/new" />

1. **Click “Add repository”** (or press <Kbd keys="N"/>).
2. Under **Where does the repository live?** choose:
   - **Linked account** — pick from your connected GitHub, GitLab or Bitbucket account. Browsing a
     provider's repositories works for GitHub only; **Manage linked accounts →** connects one.
   - **Public Git URL** — paste an **HTTPS URL** such as
     `https://github.com/apiome/apiome.git` and **click “Test”**.
3. **Click “Continue”.** Apiome says **Repository registered.** and starts its first scan.

<Screenshot id="repository-add" alt="Add a repository with no linked accounts yet: Linked account and Public Git URL choices, and Connect an account" />

The page also shows a **Proposed steps 2–4** card marked *Redesign proposal — not in the app today*:
it describes planned steps (browse, scan settings, confirm) that are not part of the product yet.

## A repository's page

<Route path="/ade/dashboard/repositories/[id]" />

**Click a repository.** One line under its name gives its **files**, the **importable** estimate,
**branches**, **imports (30d)** and the **last scan**; **click “Show stats”** for the same figures
as cards. Five tabs follow:

- **Preview** — files indexed, the importable estimate, branches, recent scans and recent imports.
- **Files** — every file Apiome indexed on the branch; **Branch** at the top of the tab switches
  branches. The table's toolbar has the **importable preset**; **click “Filters”** for the glob, the regex, **Hide non-importable**, **Recurse hidden
  dirs** and **Skip vendored / node_modules** — the button counts how many are set, for example
  **Filters (2)**. The filters are kept in the page address, so a filtered list survives a reload
  and can be shared. A file's menu has **View details**, **Import…**, **Open on provider** and
  **Copy path**.
- **Specs** — the specs imported from this repository; **“Refresh now”** re-reads them.
- **Imports** — the import history, and the repository's **Sync history**: every merge, conflict
  and replacement its files took part in (see [Merge history and conflicts](#merge-history-and-conflicts)).
- **Settings** — the source, **Scan cadence** (**Auto-refresh**), what happens on a refresh
  conflict (**Hold for review**, **Overwrite** or **New branch**), which projects may open pull
  requests back into the repository (see [Send changes back as a pull request](#send-changes-back-as-a-pull-request)),
  and **Remove repository**.

### Import from a repository

1. On **Files**, tick the specifications to import and **click “Import selected”**.
2. **One file** opens **Map & import**: choose an **Existing project** or **Create a new project**,
   and the version to create, then import.
3. **Several files** open **Import N selected files**: **Review** each file's target (a new
   version of an existing project, or a new project), **Verify**, then **“Import N specs”**. Each
   spec becomes its own import job.

### Merge several repositories into one project

A large platform often splits one API across many repositories, one per service. To see it as one
Apiome project, import each service's file into the **same project**:

1. Import the first service's file with **Map & import** and **Create a new project**.
2. For each other service, open its repository's **Files** tab, choose its file and **click
   “Import selected”**. Pick **Existing project**, choose the same project and a new version.
3. Each import creates a version that holds **every** contributing file: the classes and paths of
   the file you just imported, plus those of the other files, carried forward unchanged.

Rules of the merge:

- **Each class and path comes from one file.** If the file you import defines a class name or a
  pathname that another contributing file already defines, the import fails and nothing is written.
  The error names the class or path and both files, for example: *class "User" is defined by
  acme/users (main:openapi.yaml) and acme/billing (main:openapi.yaml)*. Rename or remove the
  duplicate in one of the files, then import again. **Dry run** reports the same conflict.
- **Re-importing a file replaces its own content.** A class or path the file no longer defines is
  removed from the new version; the other files' content stays.
- **Precedence** is the order the files first contributed (1 is the first). It orders the
  contributing files, and the project keeps the first file's project information (its description,
  contact and licence); a later file only fills in what is missing. It never settles a conflict.
- **Tags are shared.** Operation tags with the same name from different files are one tag in the
  project.
- Classes and paths that no repository defined, such as ones edited in Apiome, are carried forward
  too. If the file you import defines the same name, the file's version replaces it, and the import
  log says so.
- A version imported from one repository before this feature counts as coming from that file, so its
  content is kept when the second repository is imported.

The project's **Sources** tab on [Versions](../build/versions.mdx#sources) lists the contributing
files and shows the source of every class and path.

#### Federation on or off

Merging is called **federation**, and it is on for every project unless someone turns it off. The
**Federation** switch is at the top of the project's **Sources** tab on
[Versions](../build/versions.mdx#federation):

- **On** — each repository file you import is merged with the other contributing files, as
  described above.
- **Off** — each repository file you import **replaces** the API. Classes and paths that other files
  defined are not carried into the new version, and the import log says how many were dropped.

The switch applies to the next import; versions already created do not change. Changing it needs
the `projects:edit` permission and is recorded in the audit log as `repository.federation_toggled`.

#### Merge history and conflicts

Every import that federation acts on is recorded:

| Result | Means |
| --- | --- |
| **Merged** | Several files were merged into a new version. The row says how many classes and paths were carried forward from the other files |
| **Conflict** | Two files define the same class or path, so the import wrote nothing |
| **Replaced** | Federation was off, and the import dropped content that other files defined |

To see a conflict, open the history and **click “Show the conflict”**. For each class or path that
collides, Apiome shows both files' definitions as one comparison: lines marked **−** (red) are only
in the file that already contributes, lines marked **+** (green) are only in the file you imported,
and unmarked lines are the same in both. Fix one of the files, then import again.

<Screenshot id="repository-sync-history" alt="A repository's Sync history: a conflict on the class Customer, opened to compare both files' definitions, and an earlier merge" />

The history is on two screens:

- the project's **Sources** tab on [Versions](../build/versions.mdx#merge-history), under **Merge
  history**;
- the repository's **Imports** tab, under **Sync history** — the imports of this repository's files.

A dry run is not recorded. Each merge is written to the audit log with its history row:
`repository.federation_merged`, `repository.federation_conflicted` or
`repository.federation_replaced`.

### Send changes back as a pull request

Changes made in Apiome can go back to the repository: Apiome renders a version of the project and
opens a pull request into the files the project was imported from. This is **PR-back**. It is off
for every repository until someone allows it.

**Allow projects** on the repository's page:

1. Open the repository and **click the Settings tab**.
2. In **Pull requests back to this repository**, choose who may open pull requests:
   - **Only the projects listed** — tick each project that may.
   - **Every project except those listed** — tick the projects that may not.
3. Optionally set:
   - **Target branch** — the branch the pull requests merge into. Leave it blank to use the branch
     the files were imported from.
   - **Reviewers** — GitHub logins or teams, separated by commas, for example
     `octocat, acme/api-reviewers`. Each new pull request requests a review from them.
   - **Commit message** — a template that can use `{{project}}`, `{{version}}`, `{{repository}}`,
     `{{branch}}` and `{{fileCount}}`. Leave it blank for *Sync `{{project}}` `{{version}}` from Apiome*.
4. **Click “Save PR-back settings”.**

<Screenshot id="repository-pr-back-settings" alt="Pull requests back to this repository: an allow list with one project ticked, target branch, reviewers and commit message" />

Saving needs the `imports:edit` permission and is recorded in the audit log as
`repository.pr_back_settings.update`.

**Open the pull request** from the project's **Sources** tab on
[Versions](../build/versions.mdx#sync-back-to-repositories). What the pull request contains:

- **The rendered spec.** Each source file gets back the paths and schemas it defines, written as
  JSON or YAML to match the file's extension. In a project merged from several repositories, a
  class or path that no file defines (one added in Apiome) goes to the file with precedence **1**.
  A file that is not JSON or YAML (such as a `.graphql` file) is left as it is, and the pull
  request says so.
- **A change report as its description.** For each file, what changed between the file on the
  target branch and the rendered spec, written with the project's change report template.
- **One pull request per project and target branch.** It is opened from the branch
  `apiome/pr-back-<project>-<target branch>`. Running PR-back again, for example after a new version,
  updates the open pull request instead of opening another. Apiome rebuilds that branch each time, so
  make review changes in Apiome, not on the branch.

PR-back pushes with the GitHub account the repository was registered through. That account needs
write access to the repository: a classic token with the `repo` scope, or a fine-grained token with
write access to **Contents** and **Pull requests**. A repository registered from a public URL has no
account, so it cannot receive pull requests. Every pull request PR-back opens is recorded in the
audit log as `repository.pr_back_opened`, and every update as `repository.pr_back_updated`.

## Quota & rate limits

<Route path="/ade/dashboard/repositories/telemetry" />

Repositories are polled within an hourly quota. **Quota & rate limits** shows how much of it this
workspace uses — polls, repositories and files deferred, and content scanned — over **7d**, **30d**
or **90d**.

## Webhook IP allowlist

<Route path="/ade/dashboard/repositories/webhook-ip-allowlist" />

Provider webhooks are only accepted from the provider's published address ranges, refreshed daily.
To allow a self-hosted Git server, add its range under **Additional ranges for this workspace** —
**Address or CIDR** (for example `203.0.113.0/24`) and **Why** — and **click “Allow range”**.
**Bypass allowlist** turns enforcement off with a stated reason. Only workspace administrators can
change it.

<Screenshot id="webhook-allowlist" alt="Webhook IP allowlist: enforcement, provider ranges and additional ranges for the workspace" />

## With the CLI or the API

- CLI: `apiome repos add --url https://github.com/apiome/apiome.git`, `apiome repos list`,
  `apiome repos files <repo>`, `apiome repos import <repo> --files "**/openapi*.yaml"
  --new-project` — see the [CLI quick-start](../reference/cli-quickstart.md).
- REST: `GET` / `POST /v1/tenants/{tenant}/repositories`, `GET …/repositories/{repo}/files`,
  `POST …/repositories/{repo}/refresh`, `GET …/repository-quota-telemetry`,
  `GET …/repository-webhook-ip-allowlist` — see the [API reference](../reference/api-reference.md).
  A project's contributing repositories and the source of each class and path:
  `GET /v1/tenants/{tenant}/projects/{project}/repository-sources` — see
  [Project repository sources](../reference/rest/project-repository-sources.md).
  Federation: `GET` / `PUT /v1/tenants/{tenant}/projects/{project}/repository-federation`,
  `GET …/projects/{project}/federation-merges` and `GET …/repositories/{repo}/federation-merges` — see
  [Repository federation](../reference/rest/repository-federation.md).
  PR-back: `GET` / `PUT …/repositories/{repo}/pr-back-settings`,
  `GET /v1/tenants/{tenant}/projects/{project}/pr-back/repositories` and
  `POST …/projects/{project}/pr-back` (`dryRun: true` previews without writing) — see
  [PR-back](../reference/rest/pr-back.md).
  The repository audit export (`GET …/repository-audit-export`) also lists connector changes and
  runs (`repository.connector.*`).
