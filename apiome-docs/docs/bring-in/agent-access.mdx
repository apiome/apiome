**Agent access** turns a published version of your API into MCP tools an AI agent can call — only
the operations you choose, with keys you issue. **Go to MCP servers → Agent access.** It has three
tabs: **Toolsets**, **Agent keys** and **Usage**. You need permission to manage API keys.

## Enable agent access

1. **Click “Enable Agent Access”.**
2. Choose the **Published version** to expose, and where **Calls go to**: **Production** or
   **Mock**.
3. Confirm. Apiome creates a **toolset**: one tool per operation. Read operations are exposed right
   away; write operations stay off until you switch each one on and confirm **Let agents call a
   write operation?**

<Screenshot id="agent-access" alt="Agent access, Toolsets tab: a toolset for Pet Store 1.0.0 with its operations, kinds and exposure switches" />

## Create an agent key

1. On the toolset, **click “Create agent key”** (or **Agent keys → Create agent key**).
2. Enter a **Name** (for example `claude-desktop`) and a **Description**, choose the **Toolset**,
   tick the **Tools this key may call**, and set **Expires in (days)** — expiry cannot change later.
3. **Copy the key** from **Agent key created** — it is shown only once — and **click “I've saved my
   key”**.

The agent connects to Apiome's MCP endpoint with that key; see [Connect an MCP
host](../getting-started/connect-an-mcp-host.mdx).

<Screenshot id="agent-access-keys" alt="The Agent keys tab: a key with its toolset, status, tools, expiry and today's calls" />

**Show revoked keys** includes revoked ones; **Revoke key** stops a key at once.

## Usage

**Usage** shows calls, error rate, latency and active agents over **7 days**, **30 days** or **90
days**, with charts per day, per tool and per agent.

## Body samples

To debug an agent's calls you can keep the bodies of a share of a toolset's `tools/call`
invocations for a short time. This is off by default and uses the same control as a usage source's
[body samples](../govern/runtime-usage.mdx#open-a-sample-window):

1. Open the toolset version's project, go to **Consumers** and click **Usage data**.
2. Under **Agent toolsets**, find the version and click **Sample bodies…**.
3. Enter the **Rate (%)** (up to 100) and **Stop after (days)** (at most 7).
4. Tick **I understand that sampled request and response bodies are stored, after redaction, for up
   to 7 days.**, then click **Start sampling**.

**Stop sampling** ends it at once. Kept bodies are capped at 16 KiB each and deleted after 7 days.
Changing the window takes permission to edit API keys and is recorded in the access audit as
`agent.toolset.body_samples.update`. With the API:
`PATCH /v1/tenants/{tenant}/agent-toolsets/{toolset}/body-samples` with
`{"rate": 0.1, "until": "…", "acknowledgement": "…"}`, or `{"rate": 0}` to stop.

## Export server.json

Hosts, gateways and registries pass MCP servers around as a registry `server.json` document. Apiome
describes its agent runtime in that shape, so you can hand a toolset to any of them, or commit the
file and diff it in CI. There are two exports:

- **One toolset**: one server named `apiome.<tenant>/agent-toolset-<toolset id>`, with that
  toolset's tools.
- **Tenant-wide**: one server named `apiome.<tenant>/agent-runtime`, listing every **enabled**
  toolset. The agent key decides which toolset an agent gets.

From the CLI (it uses your workspace API key):

```bash
apiome mcp server-json export --toolset <toolset id>          # one toolset, to stdout
apiome mcp server-json export --tenant-wide --out server.json # every enabled toolset, to a file
```

Pass exactly one of `--toolset` or `--tenant-wide`. The output always comes out byte for byte the
same: keys sorted, two-space indent and one trailing newline. It only changes when the toolset
does.

Each document holds:

| Field | What it is |
| --- | --- |
| `remotes` | One `streamable-http` remote: the agent runtime's public `/agent/mcp` URL |
| `version` | The published version label (`1.0.0`). Tenant-wide: `1.0.0+<first 12 characters of the digest>` |
| `_meta["dev.apiome/agent-runtime"].auth` | How to sign in: `oauth` with the runtime's `protectedResourceMetadata` URL when OAuth is set up, otherwise `agent-key` — send `Authorization: Bearer <agent key>`, which the remote also lists as a secret header |
| `_meta["dev.apiome/agent-runtime"].digest` | A fingerprint of the tools agents are served. It changes when you switch a tool on or off or an accepted description is served, and at no other time |
| `_meta["dev.apiome/agent-runtime"].manifest` | One toolset only: the toolset's MCP manifest — the same tools as **Compile** returns |
| `_meta["dev.apiome/agent-runtime"].toolsets` | Tenant-wide only: each toolset's server name, version, tool names and digest. A toolset that cannot be built is listed under `unavailable` instead |

The document never holds a key: the header value is the placeholder `Bearer {agent_key}`.

**Import it back** the same way as any MCP server manifest (**MCP servers → Import**, or
`POST /v1/mcp/{tenant}/manifests`). A one-toolset export gives a catalog entry with the same tools,
and its manifest digest matches the export's `digest`. The tenant-wide export holds no tools of its
own, so it cannot be imported.

Your tenant's [MCP registry endpoint](../ship/mcp-registry.mdx) also lists the tenant-wide entry,
but only to callers who sign in with one of the tenant's credentials.

## With the API

`GET` / `POST /v1/tenants/{tenant}/agent-toolsets`, `GET …/agent-toolsets/{toolset}/tools`,
`GET` / `POST /v1/tenants/{tenant}/agent-keys`, `GET /v1/tenants/{tenant}/agent-usage`,
`GET …/agent-toolsets/{toolset}/server.json` and `GET /v1/tenants/{tenant}/agent-access/server.json`
(these two need permission to view API keys) and
`PATCH …/agent-toolsets/{toolset}/body-samples` (permission to edit API keys) — see the [API reference](../reference/api-reference.md).
