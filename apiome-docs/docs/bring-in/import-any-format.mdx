Apiome is not limited to OpenAPI. It imports gRPC and Protocol Buffers, GraphQL, AsyncAPI, OData,
Avro, SOAP / WSDL, TypeSpec, RAML, API Blueprint, Smithy, agent descriptors, modern RPC and event
formats, and healthcare, finance and EDI standards. The full list, with which importer handles each
format and what this deployment can run, is on [Supported formats](./supported-formats.md).

OpenAPI and Swagger become a [project](../build/projects.mdx) you can edit and publish. Every other
format becomes a **catalog** item and keeps its own structure: a Protobuf service stays a service, an
X12 envelope stays an envelope. Either way, the API is versioned, compared, linted, searched and
exported the same way as everything else in Apiome.

<Screenshot id="catalog-cards" alt="The Catalog in Cards view, grouped by protocol" />

## When to use it

- **Your APIs aren't all REST.** Keep the gRPC services, GraphQL schemas, event APIs and Avro records
  in one catalog, next to the OpenAPI documents, instead of one list per format.
- **You want to see what an API is before you change it.** Import a WSDL, a RAML file or a Smithy
  model to read its surface, lint it and follow its versions, without converting it first.
- **You are moving to OpenAPI.** Import the old format, then
  [convert it to OpenAPI](./convert-to-openapi.md) and see what the conversion keeps.

## How the pieces fit

- **One import flow.** Each format has its own importer, but every one is detected, previewed and
  committed the same way, and records the same provenance.
- **One model underneath.** Every importer reads its format into the same internal model of
  services, operations, types and channels. That is why the catalog can search, compare and lint a
  GraphQL schema and a WSDL with the same tools.
- **Versions and fingerprints.** Each import is a revision with a fingerprint of its model, so you
  can tell whether two revisions say the same thing, and compare them with the changes graded
  **breaking**, **dangerous** or **safe** in the format's own terms.
- **The format's own rules.** Lint runs a rule pack written for the format, plus the linters that
  format's community uses where the server has them, and gives every item a score and a grade.
- **The format's own tools.** Formats that need a compiler or a reference parser (`buf`, `tsp`,
  `smithy`, `drafter` and others) run it on the server. When a tool is missing,
  [Supported formats](./supported-formats.md) says so in its **Runtime** column.
- **Organized by protocol.** Every item is filed as **REST**, **RPC**, **Event**, **Graph**,
  **Data Schema** or **Agent**, and you can add a domain and tags. All of them are filters on the
  Catalog, in search and on Browse.
