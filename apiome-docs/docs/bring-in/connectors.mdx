A **connector** points Apiome at somewhere your APIs already live — an API gateway, a schema
registry, a URL — and keeps the [Catalog](./catalog.mdx) in step with it. Each API the connector
finds becomes a catalog item, and each new revision of that API becomes a new revision of the item.

Connectors are refreshed by the same engine as [Repositories](./repositories.mdx): one cadence,
one quota, one audit trail.

:::note
Connectors are managed through the REST API for now; there is no screen for them yet. Each kind needs
a source before it can sync. The two [Kong](#kong) kinds and [AWS API Gateway](#aws-api-gateway) sync
today; the other gateway and URL sources follow. A connector's **`syncable`** field, and the **`syncableKinds`** list on
`GET /v1/tenants/{tenant}/connectors`, show which kinds can sync on your deployment.
:::

## Source kinds

| Kind | Where the APIs come from |
| --- | --- |
| `kong-konnect` | Kong Konnect control planes |
| `kong-admin` | A Kong Gateway Admin API |
| `aws-apigateway` | Amazon API Gateway, by region and account |
| `azure-apim` | Azure API Management, by resource group |
| `apigee` | Apigee, by organization and environment |
| `url` | A specification published at a URL |
| `schema-registry` | A schema registry |
| `mcp-registry` | An MCP server registry |

A connector has a **name**, an optional **base URL** (the control-plane or admin address), a
**scope** (the kind's coordinates: control-plane ids, region and account, resource group, org and
environment), a **refresh interval** and a **conflict policy** (`hold-for-review`, `overwrite` or
`new-branch`, the same choices as a repository).

## Register a connector

1. **Create it:** `POST /v1/tenants/{tenant}/connectors` with `kind`, `name` and, when the kind has
   one, `baseUrl` and `scope`. For example:

   ```json
   {
     "kind": "kong-admin",
     "name": "Prod gateway",
     "baseUrl": "https://kong-admin.example.com",
     "scope": { "workspace": "default" },
     "refreshIntervalSeconds": 3600
   }
   ```

2. **Store its credential:** `PUT /v1/tenants/{tenant}/connectors/{id}/credentials` with the fields
   the kind needs, for example `{"credentials": {"token": "…"}}`.
3. **Sync it:** `POST /v1/tenants/{tenant}/connectors/{id}/sync`. The response is the finished run.

You need the **Imports** permission: **View** to read connectors, **Create** to register one,
**Edit** to change, sync or set credentials, and **Delete** to remove one.

## Credentials

A credential is **write-only**. Apiome encrypts it as soon as it arrives. No response, log line or
audit entry ever contains it, and the API only reports **`hasCredentials`** and the names of the
stored fields. To change a credential, **send the whole credential again**; there is no partial edit.
Deleting a connector destroys its credential.

Secrets do not belong in **scope**: a scope key that looks like one (`token`, `password`, `apiKey`,
`clientSecret`, …) is refused.

An [AWS API Gateway](#aws-api-gateway) connector stores **no** credential at all: Apiome assumes a
role in your account instead. Sending it one is refused with `connector-credentials-refused`.

## Base URLs and private networks

Apiome calls the base URL itself, so it must be `http` or `https`, carry no `user:password@`, and
resolve only to public addresses. A URL that resolves to a private, loopback or link-local address
is refused with the reason **`private-address`**. For a gateway that only listens inside your
network, an operator can allow its range with `APIOME_CONNECTOR_PRIVATE_NETWORK_ALLOWLIST`, a
comma-separated list of CIDRs such as `10.20.0.0/16`.

## What a sync does

Each sync is a **run**:

1. It **lists the connector's inventory**: every API the source can see.
2. It **records what it saw** under `GET …/connectors/{id}/items`, with each API's environment,
   hosts, base path, remote revision and, for gateways, its **`deployment`** details.
3. It **skips what has not changed.** An API whose remote revision or update time is not newer than
   the last import is not fetched.
4. It **fetches and imports the rest** into the catalog. The document always becomes a **catalog
   item**, even when it is OpenAPI. To make it a Project, [convert it](./convert-to-openapi.md).
5. It **writes a change report** whenever it adds a revision to an item that already had one, so
   you can see which paths and operations changed between the two revisions.

Problems that belong to the connector rather than to one API, such as a gateway route that is not
attached to any service, are listed as **findings** in the run's `summary.findings`.

| Item status | Meaning |
| --- | --- |
| **discovered** | Seen in the inventory, not imported yet |
| **imported** | Imported; `catalogItemId` is its catalog item |
| **ignored** | Never fetched |
| **missing** | No longer in the inventory |

## What never changes on a refresh

- **Nothing is deleted.** An API that disappears from the inventory becomes **missing**. Its
  catalog item, and every revision of it, stays in the catalog.
- **Ignored APIs stay ignored**, even when they leave and come back.
- **A converted item is not written to.** Once a catalog item has been converted, the next sync
  creates a new catalog item instead of changing the old one.

## Runs and failures

`GET …/connectors/{id}/runs` lists runs, newest first, with their **status**, **trigger**
(`manual` or `scheduled`), counts and, for a failure, **`errorClass`** and **`httpStatus`**.

A run that could not fetch anything is a **failed** run, never a success with zero changes. For
example, if a run fetches 0 of 12 APIs because the gateway refused the credential, it fails with
`errorClass: "auth"` and `httpStatus: 401`. The connector's **status** then turns **failing**
until a run succeeds. The error classes are `auth`, `not-found`, `rate-limited`, `unavailable`,
`credentials-unreadable`, `import-failed`, `invalid-configuration` (the connector is missing a
token or base URL it needs, or Apiome has no AWS identity to assume a role from), `address-refused`
(a request was redirected to a private address) and `unexpected`.

A run also lists, under `summary.unchangedItems`, every API it did **not** re-import and why. For
example: "deploymentId `rv7b2yhnzn` is unchanged since the last import".

Set **status** to **paused** to stop scheduled syncs; a manual sync still runs. Scheduled syncs
stop with every other refresh when `APIOME_REFRESH_ENABLED` is off.

## Kong

The two Kong kinds read your gateway configuration live, so you do not need to keep a `kong.yaml`
in a repository. Each **Kong service** becomes one catalog item. Its document is the service with
its routes and plugins, written as the [Kong declarative file](./supported-formats.md)
it is equivalent to, so a synced service imports exactly like that file would.

| Kind | Base URL | Credential | Scope |
| --- | --- | --- | --- |
| `kong-konnect` | Optional. Leave it empty to use your region's Konnect API. | `{"token": "kpat_…"}` or `{"token": "spat_…"}` | `region` and `controlPlanes` |
| `kong-admin` | Required: the Admin API address | `{"token": "…"}`, optional | `workspace` and `environment`, both optional |

### Konnect

1. **Create a token** in Konnect. Use a personal access token (`kpat_…`) or the system access token
   (`spat_…`) of a system account. The token needs the **Viewer** role on every control plane you
   want to sync. The connector only reads, so read-only access is enough.
2. **Register the connector.** Set **`region`** to `us`, `eu`, `au`, `me`, `in` or `sg` (default
   `us`). List the ids of the **control planes** to sync in **`controlPlanes`**. Leave it out to
   sync every control plane the token can read.

   ```json
   {
     "kind": "kong-konnect",
     "name": "Konnect EU",
     "scope": { "region": "eu", "controlPlanes": ["5f1c2a3b-…"] }
   }
   ```

3. **Store the token:** `PUT …/connectors/{id}/credentials` with `{"credentials": {"token": "kpat_…"}}`.
4. **Sync it.**

A synced item's **environment** is its control plane's name.

### Admin API

For a self-managed gateway, set the connector's **base URL** to the Admin API address. When your
Admin API uses RBAC, store a token with read access; Apiome sends it in the `Kong-Admin-Token`
header. With Kong Enterprise workspaces, set **`workspace`** to the workspace to read. Set
**`environment`** to label the items; it defaults to the workspace name. If your Admin API only
listens inside your network, an operator has to allow its range (see
[Base URLs and private networks](#base-urls-and-private-networks)).

### What a Kong sync records

- **Deployment details.** Each item's **`deployment`** lists the control plane id and name (or the
  workspace), the service's tags and **enabled** flag, and the protocols, hosts and paths its routes
  declare.
- **Suggested owners.** A service tag of the form `owner:<team-slug>`, such as `owner:payments`,
  is recorded as a suggested owner under `deployment.suggestedOwners`. A suggestion is only a
  suggestion; it never makes the team the owner. A malformed owner tag is a finding.
- **Plugins.** Auth plugins such as `key-auth` become the item's security schemes, labelled
  *inferred*. Every other plugin, such as `rate-limiting` or a custom plugin, is listed in the
  item's coverage ledger as **partially mapped**. Its configuration stays in the item's captured
  source, so nothing is dropped. Plugin settings that hold secrets are redacted before import.
- **Findings.** A route that is not attached to a service has no catalog item to land in, so it is
  reported as a `route-without-service` finding. Consumers and consumer-scoped plugins configure
  callers, not the API, and are counted as findings but never imported.

A Kong service only gets a new revision when its document changes. If you change one route, the
next sync imports one new revision of that service's item, writes one change report, and leaves
the other items alone. If the token is revoked, the run fails with `errorClass: "auth"`,
`httpStatus: 401` and Kong's error message.

## AWS API Gateway

The `aws-apigateway` kind reads the REST and HTTP APIs in one AWS account. **Each deployed stage
becomes one catalog item.** Its definition is the stage's export with its API Gateway extensions,
imported exactly as an [exported file](./aws-api-gateway-import.md) would be.

Apiome never stores AWS keys. You create a read-only role in your account, and Apiome assumes it for
each sync. Apiome uses its own AWS identity to do so: the AWS credentials of the deployment it runs
on, such as an instance profile, a workload identity or environment variables.

### Create the role

1. **Choose an external ID**, a value only you and Apiome know, such as `apiome-7c1d9a2f`.
2. **Create an IAM role** whose trust policy lets Apiome's AWS identity assume it with that external
   ID. Replace the principal with the identity your Apiome operator gives you:

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Effect": "Allow",
         "Principal": { "AWS": "arn:aws:iam::111122223333:role/apiome" },
         "Action": "sts:AssumeRole",
         "Condition": { "StringEquals": { "sts:ExternalId": "apiome-7c1d9a2f" } }
       }
     ]
   }
   ```

3. **Attach this permissions policy.** It is read-only; the connector never changes anything:

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Sid": "ApiomeCatalogRead",
         "Effect": "Allow",
         "Action": "apigateway:GET",
         "Resource": [
           "arn:aws:apigateway:*::/account",
           "arn:aws:apigateway:*::/restapis",
           "arn:aws:apigateway:*::/restapis/*",
           "arn:aws:apigateway:*::/apis",
           "arn:aws:apigateway:*::/apis/*"
         ]
       }
     ]
   }
   ```

| What a sync calls | IAM action | Resource |
| --- | --- | --- |
| `AssumeRole` | `sts:AssumeRole` | Your role, from its trust policy |
| `GetAccount` (dry run) | `apigateway:GET` | `arn:aws:apigateway:<region>::/account` |
| `GetRestApis` | `apigateway:GET` | `arn:aws:apigateway:<region>::/restapis` |
| `GetStages`, `GetExport` (REST APIs) | `apigateway:GET` | `arn:aws:apigateway:<region>::/restapis/*` |
| `GetApis` | `apigateway:GET` | `arn:aws:apigateway:<region>::/apis` |
| `GetStages`, `ExportApi` (HTTP APIs) | `apigateway:GET` | `arn:aws:apigateway:<region>::/apis/*` |

### Register the connector

**Create it** with the role, the external ID and the regions to read. There is no base URL and no
credential:

```json
{
  "kind": "aws-apigateway",
  "name": "AWS production",
  "scope": {
    "roleArn": "arn:aws:iam::123456789012:role/apiome-catalog",
    "externalId": "apiome-7c1d9a2f",
    "regions": ["eu-west-1", "us-east-1"]
  }
}
```

Apiome **checks the role before it saves the connector**. It assumes the role, calls `GetAccount`,
and lists one REST and one HTTP API in each region. If AWS refuses any call, the connector is not
created. The response is a `422` with `detail.code` set to `connector-check-failed`, and
`detail.reason` names what is missing, for example
`apigateway:GET on arn:aws:apigateway:eu-west-1::/account`. The same check runs again whenever you
change the scope.

### What an AWS sync records

- **One item per deployed stage.** The item's **environment** is the stage name, its **hosts** hold
  the stage's invoke URL, and its remote revision is the stage's `deploymentId`.
- **Unchanged stages are skipped.** A stage whose `deploymentId` has not changed since the last
  import is not exported again. The run lists it under `summary.unchangedItems` with that reason.
  When a redeploy produces the same definition, the stage is exported but nothing new is imported.
- **Deployment details.** Each item's **`deployment`** records the region, account, API id and type
  (`rest` or `http`), stage, `deploymentId`, invoke URL and the API's tags.
- **Suggested owners.** An API tagged `apiome:owner` with a team slug, such as `payments`, gets that
  team as a suggested owner. A suggestion never makes the team the owner. A malformed value is a
  finding.
- **Findings.** A region with no APIs is a successful run with no candidates and a `region-empty`
  finding, so an empty result is visible. A stage with no deployment (`stage-not-deployed`) and a
  WebSocket API (`websocket-api-not-exported`) are findings, because neither can be exported.
- **Failures name the permission.** If AWS refuses the role or a call, the run fails with
  `errorClass: "auth"`, and its message names the missing permission, such as
  `Missing permission sts:AssumeRole on arn:aws:iam::123456789012:role/apiome-catalog`.

## Quota and audit

Every document a connector fetches counts against the workspace's repository polling quota, the
same budget Git refreshes use. Fetches show under **Polls** on
[Quota & rate limits](./repositories.mdx#quota--rate-limits). A scheduled sync that runs out of
quota defers the rest to a later run, and a manual sync is never held back by the quota.

Every connector change and run is written to the audit trail as `repository.connector.*`, so the
repository audit export lists connector runs next to Git refreshes.

## API

| Method and path | What it does |
| --- | --- |
| `GET /v1/tenants/{tenant}/connectors` | List connectors, the kinds, and the kinds that can sync |
| `POST /v1/tenants/{tenant}/connectors` | Register a connector |
| `GET` / `PATCH` / `DELETE …/connectors/{id}` | Read, change or delete one |
| `POST …/connectors/{id}/sync` | Sync now and return the run |
| `GET …/connectors/{id}/items` | The inventory (`?status=` filters it), with each item's `deployment` |
| `GET …/connectors/{id}/runs` | The runs, newest first |
| `PUT …/connectors/{id}/credentials` | Store or replace the credential |

See the [API reference](../reference/api-reference.md) for the request and response shapes.
