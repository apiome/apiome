A catalog item describes an API that keeps running after you import it. **Live refresh**
re-discovers that API from its live endpoint on a schedule you choose. When the API has changed,
the check adds a new version to the item, just as importing the new schema yourself would. When
nothing changed, it adds nothing. A check that fails is reported on the item. It never changes the
item or its versions.

Live refresh works for two kinds of source:

| Discover with | Endpoint | What the endpoint must allow |
| --- | --- | --- |
| **GraphQL introspection** | An `http://` or `https://` URL, such as `https://api.example.com/graphql` | Introspection queries |
| **gRPC server reflection** | `host:port`, such as `grpc.example.com:443` | The server reflection service. Tick **Use TLS** for a TLS port |

Refresh is **off** for every item until you set it up.

## Set up refresh

You need `projects:edit` (an **Editor** or **Owner**).

1. **Open the catalog item** from **Bring in → Catalog**.
2. **Click the Provenance tab.** The **Live refresh** card is under the provenance steps.
3. **Click “Set up refresh…”.**
4. In **Discover with**, choose **GraphQL introspection** or **gRPC server reflection**.
5. In **Endpoint**, enter the live endpoint.
6. In **Cadence**, choose how often Apiome checks it (see [Cadences](#cadences)).
7. In **Keep versions**, choose how many versions refresh may keep (50 by default; see
   [Version retention](#version-retention)).
8. If the endpoint needs a credential, choose it in **Credential** and enter the token or header.
9. **Click “Save”.**

<Screenshot id="catalog-item-refresh-dialog" alt="The Live refresh dialog: Discover with GraphQL introspection, the endpoint URL, a Daily cadence and Keep current credential" />

To run the first check straight away, **click “Check now”** on the card.

### Cadences

| Cadence | When Apiome checks |
| --- | --- |
| **Off** | Never. The setting is kept, so you can turn it back on later |
| **Manual only** | Only when you click **“Check now”** |
| **Hourly** | About once an hour |
| **Daily** | About once a day |
| **Weekly** | About once a week |

A scheduled check runs once the time since the last check exceeds the cadence. To be polite to
your servers, Apiome limits how many checks run at once and spaces out checks against the same
host.

### Credentials

| Credential | What you enter | What Apiome sends |
| --- | --- | --- |
| **None** | Nothing | No credential |
| **Bearer token** | The token | `Authorization: Bearer <token>` |
| **Custom header** | A header name and value | That header |
| **OAuth access token** | An access token you already have | `Authorization: Bearer <token>` |

Apiome encrypts the credential when you save it and never shows it again. The card only says
**Stored (encrypted)**. When you edit the setting, **Credential** starts on **Keep current
credential**: pick another option only to replace or remove it.

## Read the card

<Screenshot id="catalog-item-refresh" alt="The Live refresh card: status Source changed, GraphQL introspection, the endpoint, Daily cadence, a stored credential, and the last and next check" />

| Status | Meaning |
| --- | --- |
| **Not checked yet** | Refresh is set up but has not run yet |
| **Up to date** | The live API matches the item's current version |
| **Source changed** | The live API differed from the item's current version, so the check added a version |
| **Last check failed** | The endpoint could not be reached or refused discovery. **Last failure** gives the reason |
| **Off** | Refresh is not set up, or its cadence is **Off** |
| **Paused for workspace** | An administrator switched catalog refresh off for the workspace |

The card also shows the method, endpoint, cadence, credential, when the item was **Last
checked**, the **Next check**, and how many refresh versions it **Keeps**.

The first check compares the live API with the version you imported. If you imported the same
schema, it reads **Up to date**.

## When the API changes

A check that finds the live API changed adds a version to the item. The version is the same one
you would get by importing the new schema yourself:

- **The label** is the date and time of the check in UTC, such as `2026-10-27T14:03Z`. Two
  versions in the same minute get `-2`, `-3` and so on.
- **The content** goes through the normal import: the same format details, fingerprint and lint
  score, and the discovered schema is kept as the version's source, so you can convert it later.
  For GraphQL the source is the schema as SDL. For gRPC it is a binary descriptor set
  (`reflection.binpb`).
- **The Provenance tab** shows the source as **Live discovery**, labelled with the endpoint. The
  version also records whether a scheduled check or **“Check now”** added it.
- **A change report** compares the new version with the one before it and classifies each change
  as breaking or not.

The version is credited to the person who clicked **“Check now”**. For a scheduled check, it is
credited to the person who last saved the refresh setting.

What counts as a change is the API itself: its types, operations and fields. Reordering the schema
or reformatting it is not a change.

### When a check fails

A failed check does not change the item: no version is added, and its versions, format details
and fingerprint stay as they were. A check also fails, without adding a version, when the item was
deleted or the discovered schema cannot be imported. Each failure in a row delays the next
scheduled check: by 5 minutes after the first, then 10, 20 and so on, up to one day. The card shows how many checks have failed in a row. The
next successful check clears the failure.

**Check now** always runs straight away, even while scheduled checks are delayed.

## Drift

Each version a check adds over an earlier one is **drift**: the live API moved. Apiome grades every
change in it, and the drift takes its worst grade:

| Grade | Meaning | Example |
| --- | --- | --- |
| **Breaking** | Existing callers can break | A field or an operation was removed, or a type narrowed |
| **Dangerous** | Compatible, but worth a review | A default changed, or an enum value was added |
| **Safe** | Existing callers keep working | An operation or an optional field was added |

### See drift on the catalog

The catalog card (and the table row) shows a drift badge until someone dismisses it. Its colour is
the grade. Hover over it for the version and the counts; click it to open what changed.

<Screenshot id="catalog-drift-badge" alt="A catalog card with a red Breaking drift badge beside its format pills" />

### See what changed

The item page shows a banner above the tabs while it has drift:

<Screenshot id="catalog-item-drift-banner" alt="The drift banner on a catalog item: Live refresh found breaking changes in version 2026-10-28T06:00Z, with See what changed and Dismiss" />

1. **Click “See what changed”.** The **Versions** tab opens on **What changed**.
2. Read the **Grade**, the two **Versions**, the **Changes** by grade, what **Found by** (a
   **Scheduled check** or **Check now**) and whether **Alerts** went out.
3. Read the table: every change, worst first, with why it got its grade.
4. The two versions are already ticked in the timeline below, so their inline diff is open. To
   compare them again later, **click “Compare these versions”**.

<Screenshot id="catalog-item-drift-changes" alt="What changed on the Versions tab: Breaking drift from 1.4.0 to 2026-10-28T06:00Z, one breaking and two safe changes with their reasons" />

When an item has drifted more than once, pick a version from the row above the facts to see that
drift. The link in an alert opens the same view.

If [version retention](#version-retention) has pruned the version a drift was compared with,
**Versions** marks it **(pruned)**, a note says so, and **Compare these versions** compares with the
newest earlier version that is still kept. The graded changes are kept with the drift either way.

### Dismiss drift

**Click “Dismiss”** on the banner to clear the banner and the badge for everyone. The drift and its
changes stay on **What changed**. You need `projects:edit` (an **Editor** or **Owner**).

## Drift alerts

A scheduled check that finds drift tells two places, and a third when email is on:

- **The workspace's webhooks.** Every active push-webhook subscription gets a
  `catalog.drift.detected` event: the item, both versions, the grade, the counts and the top five
  findings, with a link to **What changed**. Deliveries are signed and retried with backoff, like
  every other Apiome webhook.
- **The item's owner team.** Each member gets a notification in their inbox, and the team's chat
  channel gets a post. An item with no confirmed owner lands in the **Unowned findings** report
  instead.
- **The owner team's email**, when **Email me about drift too** is ticked — see
  [Drift email](#drift-email).

A version added with **“Check now”** is never announced: you are looking at the result.

### Choose what is announced

You need `imports:edit` (an **Editor** or **Owner**).

1. **Open Bring in → Catalog.**
2. **Click “Drift alerts”** in the page header.
3. Under **Announce**, tick the grades to announce. By default **Breaking drift** and **Dangerous
   drift** are announced, and safe drift only shows its badge.
4. In **Delivery**, choose **Right away** or **Daily digest**.
5. With **Daily digest**, leave **Send breaking drift right away, not in the digest** ticked to keep
   breaking drift immediate.
6. **Click “Save”.**

<Screenshot id="catalog-drift-alerts" alt="The Drift alerts dialog: Breaking and Dangerous ticked, Safe unticked, Daily digest delivery with breaking drift sent right away" />

The daily digest is one `catalog.drift.digest` webhook a day listing every drift since the last
one, with totals by grade. Each item's worst drift is also sent to its owner team. Drift that is not
announced still shows its badge.

### Drift email

Tick **Email me about drift too** in **Drift alerts** and **click “Save”** to email drift as well.
The email goes to each member of the item's confirmed owner team — the same people who get the
inbox notification — at the address on their Apiome account:

- With **Right away**, each announced drift is one email: the item, the grade, the two versions,
  the counts, the top five findings and a **See what changed** link.
- With **Daily digest**, each member gets one email per digest, listing the drift of the items their
  team owns. Breaking drift sent right away is emailed right away.

Nobody is emailed about an item with no confirmed owner, or about a version added with **Check
now**. Email needs a mail sender on the server; without one nothing is emailed and the other
alerts go out as usual — see [Email for notifications](../admin/operating-apiome.mdx#email-for-notifications).

## Version retention

A daily refresh of an API that keeps changing adds a version every day. **Keep versions** caps that:
after each version refresh adds, Apiome keeps the newest N versions that refresh created and prunes
the older ones. Pruning is a soft delete, like deleting a version yourself.

These are never pruned:

- versions you imported by hand (they do not count toward N either);
- tagged versions;
- versions a conversion to OpenAPI was made from;
- versions whose drift was graded **Breaking**, and the version each was compared with;
- locked versions;
- the item's newest version.

Opening or diffing a pruned version answers **410 Gone** with the code `version-pruned` and when it
was pruned, rather than "not found".

## Change or stop refresh

- To change the endpoint, cadence or credential, **click “Edit refresh…”**. A new endpoint or
  method starts a fresh history.
- To pause without losing the setting, set **Cadence** to **Off**.
- To remove the setting and its stored credential, **click “Turn off”**.

## Switch refresh off for the workspace

An administrator with `imports:edit` can stop every check in the workspace at once. Each item
keeps its setting and shows **Paused for workspace**. Checks resume when the switch is turned back
on.

```bash
apiome catalog refresh-policy set --disabled
apiome catalog refresh-policy set --enabled
```

The operator of a self-hosted deployment can also stop every check in every workspace with
`APIOME_CATALOG_REFRESH_ENABLED=false`.

## With the CLI or the API

The CLI has the same actions as the card. Pass the credential in a file (or `-` for standard
input), never on the command line:

```bash
apiome catalog refresh set <item-id> --adapter graphql \
  --endpoint https://api.example.com/graphql --cadence daily \
  --auth-type bearer --credentials-file token.json   # {"token": "…"}
apiome catalog refresh set <item-id> --endpoint https://api.example.com/graphql --cadence daily \
  --keep-versions 20                     # keep the newest 20 refresh versions
apiome catalog refresh show <item-id>
apiome catalog refresh check <item-id>   # exits 7 when the check failed
apiome catalog refresh off <item-id> --yes

apiome catalog drift list <item-id> --changes          # drift events, and the newest one's changes
apiome catalog drift dismiss <item-id> <event-id>
apiome catalog drift-alerts show
apiome catalog drift-alerts set --delivery daily_digest --safe   # options left out keep their value
```

See [`apiome catalog`](../reference/cli/catalog.md) for every option.

REST: `GET`, `PUT` and `DELETE /v1/catalog/{tenant}/{item}/refresh`,
`POST /v1/catalog/{tenant}/{item}/refresh/check`, and `GET` and `PUT
/v1/catalog/{tenant}/refresh-policy`. The setting's `keepVersions` (1–1000) sets
[version retention](#version-retention). See the [Catalog refresh reference](../reference/rest/catalog-refresh.md).

Drift: `GET /v1/catalog/{tenant}/{item}/drift`, `POST
/v1/catalog/{tenant}/{item}/drift/{event}/dismiss`, and `GET` and `PUT
/v1/catalog/{tenant}/drift-notifications`. The catalog list and item carry the newest open drift as
`drift`. See the [Catalog drift reference](../reference/rest/catalog-drift.md).
