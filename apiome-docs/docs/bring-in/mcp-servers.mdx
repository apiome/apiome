**MCP servers** catalogs the Model Context Protocol servers your workspace uses: Apiome discovers
each server's tools, resources and prompts, lints them and grades the server. **Go to Bring in → MCP
servers.** Its tabs are **Servers**, **Analytics** (*Preview*), **Capabilities**, **Compare** and
**Agent access**; the middle three appear once you have a server.

This page is about servers *you* bring in. To let an MCP host read *your* published specs, see
[Connect an MCP host](../getting-started/connect-an-mcp-host.mdx).

<Screenshot id="mcp-servers" alt="MCP servers in the dense list view: servers grouped by host with grade, transport and capabilities" />

Search by name, host, URL or category; **Filters** narrows by host, grade, transport, safety,
complexity, protocol, health, visibility, auth and category. Sort by grade (the default), name,
last discovered, capabilities or health, and switch between **Grid** and **Dense list**.

## Add an MCP server

**Add MCP server** opens a dialog of its own, with three steps: **Connect → Discover → Done**. It
asks only for the server; spec imports are in the [import wizard](./import-wizard.mdx). Discovery
connects, lists the server's tools, resources and prompts, then lints and grades them. To try it on
the local stack, use Apiome's own MCP server.

1. **Click “Add MCP server”.** **One server** is selected at the top of the form.
2. Enter the **Endpoint URL** — `http://localhost:8765/mcp` on the local stack — and, optionally, a
   **Display name** (`Apiome specs`).
3. Choose the **Transport**: **Streamable HTTP** (the default; right for the example),
   **Server-Sent Events (SSE)** or **Standard I/O (stdio)**. Choose **Server-Sent Events (SSE)**
   for a server that still speaks the older 2024-11-05 MCP transport, usually at a URL ending in
   `/sse`. You can leave **Streamable HTTP** if you are not sure — see
   [Servers on the older SSE transport](#servers-on-the-older-sse-transport).
4. Choose the **Auth type**: **None (anonymous)**, **Bearer token**, **Custom header** or **OAuth
   2.1 access token**. Secrets are stored encrypted and never shown again.
5. **Click “Discover →”.** When it finishes, the dialog says the server is cataloged — **click “View
   endpoint”**.

If discovery fails, read the reason, then **“Discard”** (which removes the server) or **“Add this
server anyway”**. **“← Back”** returns to the form and removes a server you did not keep.

### Servers on the older SSE transport

Some MCP servers still use the transport from the 2024-11-05 MCP revision. Apiome opens an event
stream to the server's URL, and the server answers with a second URL that Apiome sends its requests
to. Apiome reaches these servers in two ways:

- **Transport set to Server-Sent Events (SSE).** Apiome uses the older transport straight away.
- **Transport left on Streamable HTTP.** Apiome tries Streamable HTTP first. If the server answers
  that it does not take Streamable HTTP requests at that URL — **400**, **404**, **405**, **406** or
  **415** — Apiome tries the older transport on the same URL. Discovery, re-discovery and
  capability tests ([`POST …/endpoints/{endpoint_id}/test`](../reference/rest/mcp-catalog.md#test-mcp-endpoint-capability-v1-mcp-tenant-slug-endpoints-endpoint-id-test-post))
  all do this.

Apiome does not switch transports when a server asks for credentials (**401**), refuses (**403**)
or rate-limits (**429**): those answers come from a server that understood the request, so discovery
reports them as they are. If the server answers neither transport, discovery reports the first
answer.

Apiome sends requests only to a second URL on the same host, scheme and port as the event stream.
A server that points elsewhere is refused, so your server's credentials are never sent to another
host.

Over the older transport, a server may negotiate the **2024-11-05** protocol version. The
**Lint & score** tab flags that version as unsupported, because it is not one of the current
revisions.

### Authentication

Most MCP servers outside your network need a credential. Apiome stores one credential per server
and sends it on every request it makes to that server: discovery, re-discovery, the scheduled
sweep and **Test** calls.

| Auth type | What Apiome sends | Set it with |
| --- | --- | --- |
| **None (anonymous)** | Nothing | The default; clear a credential to return to it |
| **Bearer token** | `Authorization: Bearer <token>` | **Add MCP server**, or `PUT …/credentials` with `{"token": "…"}` |
| **Custom header** | One header you name, such as `X-Api-Key: <value>` | **Add MCP server**, or `PUT …/credentials` with `{"name": "…", "value": "…"}` |
| **OAuth 2.1** | `Authorization: Bearer <access token>`, renewed by Apiome | **Settings → “Connect with OAuth”** (see [Connect with OAuth](#connect-with-oauth)), or paste an **OAuth 2.1 access token** in **Add MCP server** |

How credentials are kept:

- **Encrypted, never shown again.** Secrets are sealed with AES-256-GCM before they are stored,
  under the key in `APIOME_MCP_CREDENTIAL_ENCRYPTION_KEYS` (see
  [Keys that encrypt stored secrets](../admin/operating-apiome.mdx#keys-that-encrypt-stored-secrets)).
  Without that key, Apiome refuses to store a credential (`503`) instead of keeping it unprotected.
- **Headers only.** A credential travels in a request header, never in the URL. Header names and
  values carrying line breaks are refused when you save them.
- **Masked when read.** [`GET …/endpoints/{endpoint_id}/credentials`](../reference/rest/mcp-catalog.md#get-mcp-endpoint-credentials-v1-mcp-tenant-slug-endpoints-endpoint-id-credentials-get)
  returns the auth type, whether a secret is stored (`configured`), a masked placeholder and the
  non-secret `oauth_metadata`. It never returns the secret.
- **Cleared in one call.** [`DELETE …/credentials`](../reference/rest/mcp-catalog.md#clear-mcp-endpoint-credentials-v1-mcp-tenant-slug-endpoints-endpoint-id-credentials-delete)
  removes it, and the server is reached anonymously again.
- **An unreadable secret is not guessed at.** If a stored secret cannot be decrypted (for example,
  its key was removed), Apiome sends no credential, and the server's **401** shows up as
  `auth_required` on the run.

A server that answers **401** without a credential tells Apiome how to sign in. The next two
sections cover that.

### Servers protected by OAuth

A server protected by OAuth 2.1 answers discovery with **401** and a `WWW-Authenticate` header that
says where its authorization server is. Discovery still fails with `auth_required`, but Apiome
follows that pointer and records how to get a token. It does this on every discovery and
re-discovery that gets a **401**, following the
[MCP authorization spec](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization):

1. It reads the `resource_metadata` URL from the `Bearer` challenge. If there is none, it tries the
   server's `/.well-known/oauth-protected-resource` URL, first with the endpoint's path and then
   at the root (RFC 9728).
2. That document names the server's **resource** and its **authorization servers**. Apiome then
   fetches each authorization server's `/.well-known/oauth-authorization-server` metadata in turn,
   until one works (RFC 8414).
3. It stores the result with the endpoint's credential: the authorization, token and registration
   endpoints, the scopes, the resource indicator, and whether the server supports PKCE (`S256`).

Once the metadata is stored, connect the server from its **Settings** tab — see
[Connect with OAuth](#connect-with-oauth). Until then, discovery keeps running anonymously.

The metadata is read from
[`GET …/endpoints/{endpoint_id}/credentials`](../reference/rest/mcp-catalog.md#get-mcp-endpoint-credentials-v1-mcp-tenant-slug-endpoints-endpoint-id-credentials-get)
as `oauth_metadata`, and nothing in it is secret:

```json
{
  "auth_type": "none",
  "configured": false,
  "oauth_metadata": {
    "source": "oauth_discovery",
    "resource": "https://mcp.acme.example/mcp",
    "issuer": "https://auth.acme.example",
    "authorization_endpoint": "https://auth.acme.example/authorize",
    "token_endpoint": "https://auth.acme.example/token",
    "registration_endpoint": "https://auth.acme.example/register",
    "scopes_supported": ["tools:read", "tools:call"],
    "challenge_scopes": ["tools:read"],
    "pkce_s256_supported": true
  }
}
```

The discovery job's `result.oauth_discovery` reports what happened, polled with
[`GET …/discover/{job_id}`](../reference/rest/mcp-catalog.md#get-mcp-discovery-job-v1-mcp-tenant-slug-endpoints-endpoint-id-discover-job-id-get):

- `"status": "resolved"` with the issuer, resource, and authorization and token endpoints.
- `"status": "failed"` with an error `code`:
  - `not_found` — the server publishes no metadata.
  - `resource_mismatch` — the metadata describes another server.
  - `issuer_mismatch` — the authorization server's metadata names a different issuer.
  - `invalid_metadata` — a required field is missing, such as the token endpoint.
  - `invalid_url` — a URL is unsafe.
  - `fetch_failed` — the fetch failed, or the reply was not JSON.

When a fetch fails, nothing is stored.

Safety rules for these fetches:

- **HTTPS only.** Apiome fetches metadata only over `https://` (plain `http://` only to
  `localhost`). It refuses private and link-local addresses, does not follow redirects, and
  refuses documents over 256 KB. Every endpoint the metadata names must follow the same rules.
- **No secrets sent.** The fetches carry no credential.
- **Merged, not replaced.** New discovery results are merged into what is stored. Anything else
  stored under `oauth_metadata` is kept.
- **Kept on token updates.** A
  [`PUT …/credentials`](../reference/rest/mcp-catalog.md#set-mcp-endpoint-credentials-v1-mcp-tenant-slug-endpoints-endpoint-id-credentials-put)
  without `oauth_metadata` keeps the stored metadata; one that includes it replaces the metadata.
  `DELETE …/credentials` removes it along with the credential.

### Connect with OAuth

After discovery has found the authorization server, sign Apiome in to the server once. Apiome then
keeps the token up to date by itself.

1. **Open the server's page** and **click the “Settings” tab**. The **OAuth connection** section
   appears only for a server whose authorization server was discovered.
2. If the section shows a **Client ID** field, the authorization server does not register clients
   automatically. Register Apiome with it first, using the callback URL
   `https://<your Apiome host>/ade/dashboard/mcp/oauth/callback`, and paste the client ID (for
   example `apiome-prod`). Otherwise leave it out: Apiome registers itself.
3. **Click “Connect with OAuth”.** Your browser goes to the authorization server.
4. Sign in there and approve the access Apiome asks for.
5. The browser comes back to Apiome, which stores the token and returns you to **Settings**. The
   section now says **Connected**, when the token expires, and **renews automatically** when the
   server issued a refresh token.

<Screenshot id="mcp-endpoint-oauth" alt="An MCP endpoint's Settings tab: the OAuth connection section, connected, with the token's expiry, renews automatically and its scope" />

From then on, discovery runs, the scheduled sweep and **Test** calls send the token. To connect
again — for example with other scopes, or after the server revoked the token — **click
“Reconnect”**.

What Apiome does, following the
[MCP authorization spec](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization):

- **PKCE is required.** Every sign-in uses a PKCE `S256` code challenge. If the authorization server
  does not advertise `S256`, the section says **PKCE not supported** and Apiome will not connect.
- **Client registration.** With no client ID, Apiome registers a public client with Dynamic Client
  Registration (RFC 7591) and reuses it on later connects.
- **Tokens for this server only.** The `resource` parameter (RFC 8707) names the server on the
  sign-in, the code exchange and every refresh. If the access token is a JWT whose `aud` names
  another server, Apiome refuses it.
- **Scopes.** Apiome asks for the scopes in the server's `401` challenge, or else every scope it
  lists in `scopes_supported`.
- **Renewal.** A token that expires within 60 seconds is refreshed before a discovery run, a sweep
  or a test call starts. If the server still answers **401**, discovery refreshes once and tries
  again. If a refresh fails, Apiome keeps the old token, and the section shows **Automatic renewal
  failed** with the reason. **Click “Reconnect”** to fix it.
- **Stored encrypted.** The access token, the refresh token and any client secret are sealed like
  every other credential and never returned. `oauth_metadata.token` describes them without the
  secrets: `client_id`, `client_registration` (`dynamic` or `preregistered`), `scope`,
  `expires_at`, `refreshable`, `refreshed_at` and `last_refresh_error`.
- **One sign-in at a time.** A sign-in must be finished within ten minutes by the person who
  started it. Starting another replaces it, and each callback is accepted once.

With the API, a sign-in takes two calls:

1. [`POST …/endpoints/{endpoint_id}/oauth/authorize`](../reference/rest/mcp-catalog.md#start-mcp-endpoint-oauth-v1-mcp-tenant-slug-endpoints-endpoint-id-oauth-authorize-post)
   with `{"redirect_uri": "https://app.acme.example/ade/dashboard/mcp/oauth/callback"}` (plus
   `client_id`, `client_secret` or `scopes` when needed) returns the `authorization_url` to open.
2. After consent, send the parameters the authorization server added to the redirect URI —
   `state`, plus `code`, or `error` if the user declined — to
   [`POST /v1/mcp/{tenant}/oauth/callback`](../reference/rest/mcp-catalog.md#complete-mcp-endpoint-oauth-v1-mcp-tenant-slug-oauth-callback-post).
   It returns the endpoint's redacted credential status.

Errors name a `code` in the message: `409` for `not_discovered`, `pkce_unsupported` or
`client_required`; `422` for `invalid_redirect_uri`; `400` for `invalid_state`, `state_expired`,
`authorization_denied`, `issuer_mismatch`, `audience_mismatch` or `invalid_token_response`; `502`
for `registration_failed` or `token_error` (the authorization server refused, or could not be
reached); and `503` when credential encryption is not configured.

## Import from a registry

If your team already keeps its MCP servers in a registry, bring them all in at once instead of one at
a time. That can be the official MCP registry, Azure API Center, a Kong MCP registry, or another Apiome
workspace's [registry endpoint](../ship/mcp-registry.mdx).

1. **Click “Add MCP server”** and choose **From a registry** at the top of the form.
2. Enter the **Registry URL**, the registry's root: `https://registry.modelcontextprotocol.io` for the
   official registry, or `https://<apiome>/registry/mcp/<workspace>` for another Apiome workspace.
3. Optionally, enter a **Search** to import only the servers whose name matches, for example
   `io.github.acme`.
4. Choose the **Registry credential**:
   - **None (public registry)**, for the official registry and most public ones;
   - **Bearer token**;
   - **Apiome workspace API key**, to read another Apiome workspace.

   The credential is stored encrypted and never shown again.
5. Leave **Keep these servers in sync** ticked to re-sync hourly. Only servers whose registry entry
   changed are imported again. Untick it to sync only when you ask: the connector is registered
   **paused**.
6. **Click “Import servers →”.**

<Screenshot id="mcp-servers-import-registry" alt="Add an MCP server, From a registry: the registry URL, a search of io.github.acme, no credential and Keep these servers in sync ticked to re-sync hourly" />

Apiome registers an [MCP registry connector](../reference/rest/connectors.md) for the registry and runs
its first sync. Each server with a reachable `streamable-http` or `sse` remote is added here,
discovered, linted and graded. The dialog then shows:
- how many servers the registry listed;
- how many were imported;
- each server that could not be added yet, with the reason.

| Reason | What it means |
| --- | --- |
| `no-remote` | The server ships only packages that run locally, so there is nothing to discover |
| `remote-templated` | Its URL needs a value you fill in; add it with **One server** |
| `remote-refused` | Its URL resolves to a private address |
| `remote-unreachable` | Its remote did not answer; the next sync tries again |
| `name-not-namespaced` | Its name has no reverse-DNS namespace, such as `io.github.acme/weather` |
| `duplicate-name` | A server with this name is already in your catalog from another registry |
| `registry-deleted` | The registry marks the server deleted; see [Registry status](#registry-status) |

A registry URL that resolves to a private address, or a registry that refuses the request, imports
nothing: the dialog shows the reason and creates no connector. Every sync is recorded with its counts on
the connector's **Runs** tab. Change its cadence, or sync it again, under **Bring in → Connectors**.

### Uptime and latency

Every few minutes Apiome checks that each enabled server answers. The check is only the MCP
`initialize` handshake — much lighter than a discovery, and it never lists or calls the server's
tools. It sends the server's stored credentials, and records whether the server answered and how long
it took. A server on the `stdio` transport has nothing to reach, so it is not checked. A server
that scheduled discovery has paused after repeated failures is still checked, so you see when it
comes back.

The badge in the server's header sums up the last 24 hours, for example **Up · 99.6% · 118 ms**: the
status, the share of checks the server answered, and its median response time. Hover over it for the
counts and the 95th-percentile time.

| Badge | Means |
| --- | --- |
| **Up** | The latest check answered, and at least 99% of the day's checks did |
| **Degraded** | The latest check answered, but fewer than 99% of the day's checks did |
| **Down** | The latest check failed; the tooltip names why (`connect_error`, `timeout`, `auth_required`, …) |
| **Uptime unknown** | No check in the last 24 hours — a new or `stdio` server, or checks are turned off |

The history is in the REST API: `GET /v1/mcp/{tenant}/endpoints/{endpoint}/uptime` returns the
`summary` over the last `window_hours` (default 24, at most 168) and the newest `limit` checks
(default 100, at most 1000). Checks are kept for 30 days. A published, public server's embeddable
badge can show the same status:
`/mcp/badge/{tenant}/{endpoint-slug}.svg?metric=uptime`.

### How versions work

A version is a snapshot of everything the server declares: its tools, resources, prompts and server
details. Apiome creates one only when that changes.

- **The first discovery** creates **v1**. Every capability it finds is listed as **Added**.
- **A discovery that finds the same surface** creates no version. The server's last-discovered time
  moves on, and it stays on its current version.
- **A discovery that finds a change** creates the next version, **v2**, **v3** and so on, and the
  server moves to it. The version records each capability that was **Added**, **Removed** or
  **Modified**, and any change to the server's own details, such as its version number.

Each version is also tagged with the date and time of the discovery that produced it, in UTC to the
minute — `2026-11-08T14:03Z`. Two versions discovered in the same minute get `…Z` and `…Z-2`. The
timeline shows each version's tag and its **+** / **−** / **~** counts.

Comparing any two versions on the **Versions** tab recomputes the difference from the two
snapshots, so it shows the same changes as the newer version recorded.

A discovery that fails creates no version, and the server keeps its current one.

#### The change event

Every new version raises one `mcp.version.created` event inside the REST API, at the moment the
version is saved. A discovery that finds the same surface, or fails, raises none. The event carries:

| Field | Holds |
| --- | --- |
| `event_id` | An id that is the same every time for the same version, so a consumer can drop a repeat |
| `endpoint` | The server's `id`, `tenant_id`, `name` and `slug` — never its URL or credential |
| `version`, `previous_version` | The new version's `id`, `seq` and date/time `tag`, and the version it replaced (`null` for **v1**) |
| `discovered_at`, `trigger` | When the discovery ran and what started it: `manual`, `sweep` or `registry` |
| `change_summary` | `total` changes, counts `by_change_type` (`added` / `removed` / `modified`), `by_item_type` and `by_severity` (`additive` / `review` / `breaking`), the worst `max_severity`, and `initial` for **v1** |

#### Get the change event as a webhook

Every active push-webhook subscription in the workspace receives each `mcp.version.created` event —
there is nothing extra to turn on. Add a subscription with `POST /v1/push-webhook-subscriptions/{tenant}`,
giving the receiver's `url` and a `signingSecret` you keep (see the
[Webhooks reference](../reference/rest/webhooks.md)). Apiome never returns the secret again.

Each delivery is a `POST` to the subscription's URL:

| Part | Holds |
| --- | --- |
| `X-Apiome-Event` header | `mcp.version.created` |
| `X-Apiome-Signature` header | `sha256=` and the hex HMAC-SHA256 of the raw body, keyed by the subscription's signing secret |
| Body | The event fields in the table above, as JSON |

**Check the signature** before you trust a delivery: compute the HMAC of the raw body with your
secret and compare it to the header. **Use `event_id` to drop repeats** — it is the same every time
for the same version.

A delivery that fails (no answer, or any status outside `2xx`) is retried after 10 seconds, 1 minute
and 5 minutes — sooner or later if a `429` or `503` names a `Retry-After`. After the fourth failed
attempt it is dead-lettered and listed by `GET /v1/push-webhook-subscriptions/{tenant}/deliveries/dead-letter`. A webhook problem never fails the discovery. A subscription's `minSeverity`
filter applies only to published versions, so it does not hold back MCP change events.

Operators see each event in the REST API log — see
[Watch MCP re-discovery](../admin/operating-apiome.mdx#watch-mcp-re-discovery).

### How servers are graded

Every version is linted against the [MCP surface lint rules](../govern/mcp-surface-lint-rules.md)
when it is discovered, and given a score from 0 to 100. Each finding lowers the score, and a more
serious finding lowers it more. The score sets the grade:

| Grade | Score |
| --- | --- |
| **A** | 90 and above |
| **B** | 80–89 |
| **C** | 70–79 |
| **D** | 60–69 |
| **F** | Below 60 |

These are the same bands Apiome uses to grade an API specification, so an **A** means the same thing
on both. The **Lint & score** tab shows the current version's grade and its findings. The grade on
the list and on the server's page is the current version's.

The same surface always gets the same score, grade and findings, and the report carries a
fingerprint that changes only when they do. A version's score is kept with it, so an older version
keeps the grade it was given.

<Screenshot id="mcp-endpoint-lint" alt="An MCP endpoint's Lint & score tab: the grade and must, should and advisory findings" />

To score a version again — for example after the lint rules change — send
`POST /v1/mcp/{tenant}/endpoints/{endpoint}/versions/{version}/lint`. It re-lints the stored
version, replaces its score and returns the new report. `GET` on the same URL returns the stored
report without changing it, and `GET …/lint/evidence` lists the lint runs recorded for the version.
Re-linting a version whose report has not changed records no new run.

### Test a tool

The **Test** tab calls one of the server's tools on the live server, with the endpoint's stored
credential, and shows what came back.

1. **Open the Test tab.**
2. **Pick a tool** under **Tool**. The form below it has one field for each of the tool's arguments,
   taken from its input schema. Required fields are marked; an object or array argument takes JSON.
3. **Fill in the arguments.**
4. **Click “Run test”.**

The **Result** card shows whether the tool **Succeeded**, reported a **Tool error**, or the
**Call failed** before it answered, with the time the call took and its `isError` flag — for
example `142 ms · isError: false`. Below that is what the tool returned. A failed call shows the
reason instead, such as a timeout.

- **Destructive and open-world tools.** A tool marked destructive or open-world can change data or
  reach other systems. The tab shows a warning, and **“Run test”** stays off until you tick
  **I understand this call runs against the live server and may change data.**
- **No stored credential.** If the endpoint has no credential, the tab says so and the call runs
  anonymously. Add one with `apiome mcp register --bearer` or `--header`, or through the
  [API](../reference/api-reference.md), if the server needs it.
- **Arguments are checked first.** A missing required argument is flagged in the form, and
  arguments that do not match the tool's schema are rejected before the call leaves Apiome.
- **Calls are recorded and limited.** Each test call is logged with secret values masked, and each
  endpoint accepts a limited number of test calls a minute.

<Screenshot id="mcp-endpoint-test" alt="An MCP endpoint's Test tab: a tool picked, its argument form, and the result with latency and isError" />

From the CLI, `apiome mcp test <endpoint-id> --tool <name> --arg key=value` does the same. See
[apiome mcp test](../reference/cli/mcp.md#mcp-test).

#### Test over the API

The Test tab and the CLI both call
[`POST …/endpoints/{endpoint_id}/test`](../reference/rest/mcp-catalog.md#test-mcp-endpoint-capability-v1-mcp-tenant-slug-endpoints-endpoint-id-test-post).
Over the API you can also read one of the server's resources or fetch one of its prompts:

```json
{
  "item_type": "tool",
  "item_name": "get_forecast",
  "arguments": { "city": "Paris" },
  "timeout_seconds": 30,
  "confirm": false
}
```

- **`item_type`** is `tool`, `resource` or `prompt`; **`item_name`** must be on the server's
  current version, so run discovery again after the server changes.
- **`auth_override`** (optional) uses a credential for this one call instead of the stored one, in
  the same shape as a stored credential — for example
  `{"auth_type": "bearer", "payload": {"token": "…"}}`. It is never saved or logged.
- **`timeout_seconds`** is 1–120 (default 30).

A tool error or a server that cannot be reached is still a `200` response: `completed` says whether
the server answered, `isError` whether the tool reported an error, and `error` gives the reason for
a failed call. Each response carries `latencyMs` and the `invocationId` of its log entry. The API
returns an error status only when the call is not sent:

| Status | Why |
|---|---|
| `404` | The endpoint is not in your tenant, or the tool, resource or prompt is not on its current version |
| `409` | The endpoint has not been discovered yet |
| `422` | The arguments do not match the tool's schema, or the override is malformed |
| `428` | The tool is destructive or open-world and `confirm` is not `true` |
| `429` | The endpoint's test-call limit for this minute is used up |

## Servers from a registry

An [MCP registry connector](../reference/rest/connectors.md) keeps servers from an upstream
registry — the official registry, Azure API Center, a Kong registry or another Apiome workspace — in
your catalog. [Import from a registry](#import-from-a-registry) creates one for you; the Connectors
screen is not yet available, so manage it over the
[REST API](../reference/rest/connectors.md#create-connector-v1-tenants-tenant-slug-connectors-post)
with the `mcp-registry` kind.

Each server the registry lists with a reachable `streamable-http` or `sse` remote is added here,
private and unpublished, and discovered, linted and graded like a server you added by hand. You can
tell it apart by its source:

- **Added via** reads **Imported from a registry** (`added_via: registry` in the API), and its
  discovery runs are labelled **Registry refresh**.
- **Sources** lists what the registry declared, each with the provenance **registry published**
  and the connector that linked it: the registry entry (`io.github.acme/weather`), the repository,
  and the npm, PyPI, NuGet, Cargo or OCI packages. A package is pinned only when the registry names
  an exact version.

- **Registry metadata** (`registry_metadata` on the server in the API) records the entry's server
  name, version, website, the registry's status (`active`, `deprecated` or `deleted`) and dates, and the
  remote Apiome calls with the headers it declares. Secret header values are never stored. See
  the [connector items API](../reference/rest/connectors.md#list-connector-items-v1-tenants-tenant-slug-connectors-connector-id-items-get).

Each sync refreshes the server's name, URL, transport, description and registry metadata from the
registry, and retires a source link the registry no longer lists. Links you added yourself stay. A server that only ships
packages, or whose remote resolves to a private address, is not added. A server whose remote does not
answer is added, but its row on the connector stays **discovered** until it does. The connector's
**Items** tab says why.

### Sync cadence

A registry connector re-syncs **hourly**. For another schedule, set the connector's
`refreshIntervalSeconds`. To sync now, call `POST …/connectors/{id}/sync`. A **paused** connector
syncs only when you ask. An operator can change the hourly default with `APIOME_MCP_REGISTRY_SYNC_INTERVAL`
(see [Operating Apiome](../admin/operating-apiome.mdx#mcp-registry-sync)).

### Server names

A registry names each server with a reverse-DNS namespace: the owner's domain written backwards,
a `/`, then the server — `io.github.acme/weather`, `com.example/orders`. That name is the server's
identity in your workspace:

- **One name, one server.** A name already in your catalog is never added twice. A second connector
  on the same registry (another search, say) refreshes the server the first one added. The same name
  from a different registry stays **discovered** with `duplicate-name`, and the reason names the
  registry that has it.
- **No namespace, no import.** A name like `weather` or `acme/weather` stays **discovered** with
  `name-not-namespaced`.
- **Slugs follow the name.** A new server's slug is the whole name, `io-github-acme-weather`, so
  `io.github.acme/weather` and `com.example/weather` never compete for `weather`.

### Registry status

Each sync reads the status the registry gives an entry (`_meta`), records it in the server's
**Registry metadata**, and lists every entry that is not active in the run's findings
(`mcp-registry-deprecated`, `mcp-registry-deleted`) on the connector's **Runs** tab.

| Status | What the sync does |
| --- | --- |
| `active` | Adds or refreshes the server, and discovers it |
| `deprecated` | The same as `active`. The status shows the server is on its way out |
| `deleted` | Keeps the server and marks it `deleted`, without discovering it. It adds nothing new. The row stays **discovered** with `registry-deleted` |

An entry the registry makes `active` again is imported again on the next sync. An entry the registry
stops listing at all turns **missing**, and its server stays.

### How Apiome reads a registry

Apiome speaks version `v0.1` of the
[MCP Registry API](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/api/official-registry-api.md),
the same API as the official registry (`https://registry.modelcontextprotocol.io`, with staging at
`https://staging.registry.modelcontextprotocol.io`).

- **Listing.** Each sync calls `GET /v0.1/servers?version=latest` 100 servers at a time. It sends
  your **Search** as `search` and the scope's `updatedSince` as `updated_since`.
- **Paging.** Apiome follows `metadata.nextCursor` until the registry stops sending one. If the
  registry sends the same cursor twice, paging stops. A registry that still has more pages after
  10,000 servers fails the sync with “narrow it with a search” instead of importing only part of
  the list.
- **A changing schema.** The registry API is still a preview, so Apiome reads what it can.
  Unknown fields are kept. Entries in the older flat or snake_case shapes are read like current
  ones. An entry with no server name is skipped. A `deleted` entry is read, so its server can be
  marked (see [Registry status](#registry-status)).
- **Registry URL.** A **Registry URL** that ends in `/v0.1` or `/v0.1/servers` still works. Apiome
  uses the root.

### Search your catalog and the registry together

`GET /v1/mcp/{tenant}/search?q=…&include_registry=true` searches your catalog as usual and also asks
the MCP registry for servers whose names match. The registry is the official one unless an operator
sets `APIOME_MCP_REGISTRY_SEARCH_URL` (see
[Operating Apiome](../admin/operating-apiome.mdx#mcp-registry-search)).

- **Labels.** Your own results stay in `hits`, each with `source: local`. The registry's matches come
  after them in `registry_hits`, each with `source: registry`, the server name, version, status,
  website and the remote Apiome would call (without credentials).
- **No duplicates.** A registry server you already have is left out of `registry_hits`, and
  `registry_duplicates` counts those servers. A server counts as yours when it was imported with that
  registry name, or when its URL is one of the server's remotes (ignoring credentials, the query
  string and a trailing `/`). Your matching hit gets the name in `registry_server_name`. A server you
  imported from a registry carries its name there too.
- **First page only.** The registry is searched when `offset` is `0`. `registry_limit` (1–100, default
  20) caps how many registry servers are requested.
- **Search words.** The registry matches names by substring, so Apiome sends your words without
  quotes, `OR` or `-excluded` words.
- **When the registry fails.** Your results still come back. `registry_included` is `false`, and
  `registry_error` says why: search turned off, a timeout, or the registry's error.

The public browse app has the same search with an **Include MCP Registry** toggle — see
[Search MCP servers, including the MCP Registry](../ship/browse-published-specs.md#search-mcp-servers).

## With the CLI or the API

The `apiome mcp` commands do everything on this page from a terminal or a CI job: register a
server, discover it, grade it and call one of its tools. They need an API key and a workspace — see
[Sign in the CLI](../reference/sign-in-the-cli.mdx). Every command is listed in the
[`apiome mcp` reference](../reference/cli/mcp.md).

1. **Register the server.** Use `--bearer <token>` or `--header 'Name:Value'` to store a
   credential at the same time. It is sealed on the server and never printed.

   ```bash
   apiome mcp register --name "Apiome specs" --url http://localhost:8765/mcp
   ```

   The table that comes back starts with the endpoint's **ID**. `apiome mcp list` shows every
   server, and `apiome mcp show <id>` shows one.
2. **Discover it.** The command starts a discovery run and waits for it. It then prints the new
   version, whether the surface changed, and the grade. Add `--no-wait` to start the run and return
   at once.

   ```bash
   apiome mcp discover <id>
   ```

3. **Grade it.** This lints the current version and lists the findings. `--min-grade B` fails the
   command when the grade is worse than B, and `--fail-on-policy` also applies your workspace's
   lint policy.

   ```bash
   apiome mcp lint <id> --min-grade B
   ```

4. **Call a tool.** Each `--arg key=value` is read as JSON when it parses (`5`, `true`), and as
   text otherwise. A tool marked destructive or open-world needs `--confirm`.

   ```bash
   apiome mcp test <id> --tool spec_search --arg q=payments
   ```

Add `--json` before `mcp` to print the REST response unchanged, for scripts. Exit codes, for CI:

| Code | When |
| --- | --- |
| `0` | The command succeeded and every gate passed. |
| `1` | Discovery failed or timed out, the grade is below `--min-grade`, a policy gate failed, or the tool reported an error. |
| `2` | A usage error, such as a missing `--confirm` for a destructive tool or a bad `--min-grade`. |

- REST: `GET` / `POST /v1/mcp/{tenant}/endpoints`, `POST …/endpoints/{endpoint}/discover`,
  `POST …/endpoints/{endpoint}/test`, `POST …/endpoints/{endpoint}/oauth/authorize`,
  `POST /v1/mcp/{tenant}/oauth/callback`,
  `GET …/endpoints/{endpoint}/versions`, `GET …/endpoints/{endpoint}/uptime`,
  `GET` / `POST …/versions/{version}/lint`,
  `GET …/versions/{version}/lint/evidence`, `GET /v1/mcp/{tenant}/browse`,
  `GET /v1/mcp/{tenant}/search` (add `include_registry=true` to [search the registry
  too](#search-your-catalog-and-the-registry-together)),
  `GET /v1/mcp/{tenant}/capabilities`, `GET /v1/mcp/lint/rules` — see the [API
  reference](../reference/api-reference.md).

## Registry API

Gateways and MCP hosts that discover servers through the official MCP Registry API can read your
catalog directly. Point them at your tenant's registry base URL (the full guide is
[MCP registry endpoint](../ship/mcp-registry.mdx)):

```text
https://<your-apiome-host>/registry/mcp/<tenant>/v0.1/servers
```

The same routes also answer under `/v1/tenants/<tenant>/mcp-registry/v0.1/servers`.

- **Publish lists it.** **Publish** a server and make it **Public** and it is listed in the registry
  endpoint for anyone. Send an MCP API key (`Authorization: Bearer …`), a workspace API key
  (`X-API-Key`) or a signed-in session of the same tenant to list private and unpublished servers
  too. A credential that is wrong or belongs to another tenant is refused (`401` / `403`). It never
  falls back to the public list.
- **Names.** Each server is named `apiome.<tenant>/<server-slug>`, for example
  `apiome.acme/weather`. Its `version` is the version the server reports (`serverInfo.version`),
  or the snapshot label when it reports none.
- **Paging.** Up to 100 servers a page (`limit`, default 30). Pass `metadata.nextCursor` back as
  `cursor` to get the next page. Cursors stay valid when servers are added. Filter with `search`
  (name or slug) and `updated_since`.
- **One server.** `GET …/servers/apiome.acme%2Fweather/versions/latest` returns one entry with an
  `ETag`. A client that sends it back in `If-None-Match` gets `304` until the server changes.
- **Packages and repository.** The server's linked sources fill `packages` (npm, PyPI, NuGet and
  other packages, and container images as `oci`) and `repository` (the newest linked git repo). A
  server with no linked source has `packages: []`.
- **Apiome extras.** Each entry's `_meta` carries `dev.apiome/catalog`: the server's grade and
  score, its trust posture (`score`, `grade`, `gatePassed`), the latest lint gate verdict, the owner
  team, whether any source is linked (`sources`: `linked` or `none`), its visibility and its
  manifest digest.
- **Remotes.** A server's URL is listed without any credentials, query string or fragment it was
  registered with. A `stdio` server has no remote.
- **Schema version.** `GET …/v0.1/schema` names the registry API and `server.json` schema versions
  served.

From the CLI, `apiome mcp registry list [--since 2026-10-01T00:00:00Z]` walks every page. The routes
are on the [MCP registry](../reference/rest/mcp-registry.md) REST reference page.
