Apiome has two import wizards, and which one you get depends on where you start:

| Wizard | Opens from | Sources | Creates |
| --- | --- | --- | --- |
| **Import specification** | **Import** on Projects or Versions, **Import a spec** on Home (<Kbd keys="I"/>) | File Upload, URL Import, Clipboard Paste, Git Repository, SwaggerHub, Design with AI | A new [project](../build/projects.mdx) |
| **Import to catalog** | **Import to catalog** on the [Catalog](./catalog.mdx) | File, URL, clipboard, Git repository | A catalog item, in its original format |

The sample files below are in the Apiome repository under `apiome-ui/examples/`. Avoid the
`negative/` and `adversarial/` folders — those files are broken on purpose.

## Import specification

Steps: **Source → Analyze → Preview → Import → Done** — with a **Changes** step between Preview and
Import when the spec is a new version of a project you already have
([below](#import-a-new-version-of-an-existing-project)).

<Screenshot id="import-wizard-source" alt="The Import specification wizard on its Source step: the source cards, then the three most recent imports with their state" caption="The Source step. From Projects the wizard offers File Upload, URL Import, Clipboard Paste, Git Repository and SwaggerHub." />

1. **Source** — choose a card, or press its number: **`1`** – **`5`** choose the first five
   (each card shows its key). Then fill in its intake (below). The forward button is **“Analyze →”**
   (**“Continue”** for a URL). When you have imported before, the three most recent imports are
   listed under the cards with their state; **“All import jobs”** opens the full list.
2. **Analyze** — Apiome detects the format and checks the document. A banner says **Ready to
   import**, or what blocks the import (a D/F quality grade, errors, or a format this importer does
   not take). **Click “Continue”.**
3. **Preview** — review the schemas in a **List View**, **Relationship Diagram** or **Tree View**,
   pick them with their checkboxes, **Select All** / **Select None** and the filters, and set the
   **Project Name**,
   **Slug** and **Version** under **Import Options**. **Click “Import →”.** The button reads
   **Checking for changes…** for a moment while Apiome looks for a project with that **Slug**.
4. **Import** — the job runs; you can close the dialog and it keeps going.
5. **Done** — **Import Complete!** **“Undo import”** reverses it; **“Download error report”**
   explains anything that was skipped.

<Screenshot id="import-wizard-running" alt="An import in progress: progress bar, live progress per schema and the import log" />

### Schemas that other schemas use

A schema that points to another schema (a `$ref`) can only be imported together with it. On the
**Preview** step:

- **Ticking a schema also ticks every schema it uses**, and the schemas those use. The line next to
  **Select None** says what was added, for example *Also selected Customer and Address: Order
  references them.*
- **A schema a ticked schema uses can't be unticked.** Its checkbox is greyed out and the row says
  **Required by Order**. Untick **Order** first, and **Customer** can be unticked too.
- **Select None** still clears everything, and **Select All** ticks everything. Two schemas that
  point to each other keep each other ticked; use **Select None** to clear both.

If the import fails, nothing is saved; the failures are listed with **“Retry import”**.

<Screenshot id="import-wizard-failed" alt="A failed import: the failure, the stopped progress bar, Retry import and the import log" />

**Recent import jobs** in the wizard's header lists earlier jobs.

### Properties defined differently

When the schemas you tick use the same property name with different definitions, the **Preview**
step warns before you import. For example, `status` is an enum of `active` and `inactive` in
**Customer** but `pending` and `completed` in **Transaction**. The warning lists each property, every
definition it has and the schemas that use each one.

The import still runs. Each definition becomes its own property in the project's property library
(`status`, then `status_1`), and every schema keeps its own definition. To end up with one shared
property instead, make the definitions match in the spec and import again. The warning follows your
selection: unticking the schemas on one side clears it.

### References that won't resolve

The import keeps every reference (`$ref`) as written. When a schema you tick holds a reference that
won't resolve in the project afterwards, the **Preview** step warns, schema by schema:

- **Not defined in this document** — a reference such as `#/components/schemas/Customer` when the
  spec defines no `Customer`. After import, it points at a schema the project doesn't have.
- **Not fetched** — a reference to a URL (`https://…`). Apiome doesn't download it.

The import still runs. To fix the references, add the missing schemas to the spec, or replace a URL
with a schema defined in it, and import again. A reference to a schema you didn't tick can't happen:
ticking a schema ticks every schema it uses.

### Change property descriptions

To fix or fill in a property's description as you import, rather than editing it in the project
afterwards, use **Property descriptions** on the **Preview** step:

1. **Click “Property descriptions”** to open it. It lists every property of each schema you ticked,
   by **Schema** and **Property**.
2. **Type a description** in the **Description** box. The box shows the spec's own description as a
   hint (*As in spec: …*), or *(no description in spec)* when it has none.
3. **Leave a box empty** to keep the spec's description as it is.

The descriptions you type replace the spec's for those properties in the imported project; the
spec file itself is not changed. Untick a schema and its rows leave the list.

### Import a new version of an existing project

When the **Slug** on Preview matches a project you already have, the import adds a new version to
that project instead of creating one. Before it does, the wizard stops at **Changes** so you can see
what the new version changes compared with the project's **latest** version. The step is skipped for a
first-time import and for anything that lands in the [Catalog](./catalog.mdx).

<Screenshot id="import-wizard-changes" alt="The Changes step: Changes vs. Payments API v2.4.0 (latest), counts of 1 added, 2 changed, 1 removed and 2 breaking, a breaking-changes warning, and the change list with the removed DELETE /refunds/{id} operation first" caption="The Changes step for a new version of Payments API. Breaking changes come first." />

1. **Read the summary bar** — **added**, **changed** and **removed** count every changed path,
   operation, schema and property; **breaking** counts the breaking findings. These are the same
   rules as **Compare** on [Versions](../build/versions.mdx) and the compatibility gate.
2. If anything is breaking, a warning says so. It is a warning, not a block — the compatibility gate
   decides whether the version can merge or publish.
3. On the **Summary** tab, the list puts breaking changes first. Each row shows **Added**,
   **Changed** or **Removed**, what changed (for example `schema Refund.amount minimum 0 → 0.01`) and
   its grade (**breaking**, **unknown** or **safe**). A change no compatibility rule grades has no
   badge. Narrow the list with **Show** (**All**, **Breaking**, **Added**, **Changed**, **Removed**)
   or **Filter changes**; **“Show more”** loads the next 50.
4. **Click “Side-by-side spec”** to compare the two documents: the latest version on the left, the
   incoming spec on the right, with unchanged regions folded.
5. **Click “Continue to import”.** **“← Back”** returns to Preview, where you can change the
   **Slug** to import into a different project.

**When the version number is taken.** If the project already has the **Version** you set on
Preview, the import doesn't fail: it adds the version as a new sub-version instead. The Changes step
says which one, for example *Payments API already has version 2.5.0, so this import is added as
2.5.0b*. Sub-versions take the next free letter: `2.5.0b`, then `2.5.0c` and so on. Importing `2.5.0b`
again gives the next free one too. Nothing existing changes. To use a different number instead,
**click “← Back”** and change **Version** on Preview. When an import was added as a sub-version, the
**Done** step lists it under **Version** with the number that was taken.

**Merge strategy.** Under the summary bar, **Merge strategy** decides what the new version holds:

- **Replace with this import** (the default) — the new version holds only what the spec defines.
  Anything listed as **Removed** is not in it.
- **Additive merge** — the new version keeps everything in the latest version and adds what the spec
  newly defines. Nothing is removed and nothing existing is overwritten:
  - A schema both have keeps its properties and their definitions; properties only the spec has are
    added, nested ones too.
  - A path both have keeps its operations; methods only the spec has (a new `POST`, say) are added.
  - Schemas, paths and security schemes only the latest version has are kept as they are, and the
    spec's new ones are added.
- **Override merge** — like **Additive merge**, nothing is removed and the spec's new items are
  added, but wherever both define the same thing, the spec's definition wins:
  - A property both have takes the spec's definition as a whole (for example `maxLength: 100`
    replaces a stored `maxLength: 50`). Properties only the latest version has are kept.
  - A schema both have takes the spec's description.
  - An operation both have (same path and method) takes the spec's definition. The path's other
    operations are kept.
  - A security scheme both have takes the spec's definition.

Pick **Additive merge** when the project holds edits you want to keep, and **Override merge** when
the spec is the source of truth for what it defines but doesn't define everything.

**Arrays.** With either merge selected, **Arrays** decides what happens to a list that both the
latest version and the spec define on the same property or schema: `enum` values, a schema's
`required` list, `examples`, nested lists such as `items.enum`. The merge decides whose list comes
first (the latest version's under **Additive merge**, the spec's under **Override merge**):

| Arrays | Stored `[active, inactive]`, spec `[active, archived]`, with **Additive merge** |
| --- | --- |
| **Replace** (the default) | `[active, inactive]`: only the list that comes first |
| **Append** | `[active, inactive, active, archived]`: both lists, repeats kept |
| **Deduplicate** | `[active, inactive, archived]`: both lists, without repeats |

A list only one side defines is left as the merge has it. Lists on operations (tags, parameters)
are not combined. **Done** says how many lists were appended or deduplicated.

<Screenshot id="import-wizard-changes-additive" alt="The Changes step with Merge strategy set to Additive merge, the Arrays choice under it set to Replace, and a note that the item listed as Removed stays in the new version" caption="With Additive merge, the item listed as Removed stays in the new version, and Arrays appears." />

With either merge selected, a note says that the items listed as **Removed** stay in the new
version. **Done** adds a **Merge** row, for example *Additive — 2 schemas merged (3 properties
added); 4 schemas and 5 paths kept from the latest version*, or for an override *Override — 2
schemas merged (1 property added, 2 updated), 1 operation updated; …*. A **Dry run (preview only)**
shows the same row without saving anything.

If nothing changed, the step says **No changes from v2.4.0** (with your version); importing still
records a new version. If the comparison cannot be computed, **“Try again”** asks again, and
**“Continue to import”** still works. The step appears for a **Dry run (preview only)** import too.

To try it, import `apiome-ui/examples/openapi/30-openapi-3.0-petstore.yaml`, then edit a copy (remove
an operation, add a path) and import it again with the same **Slug** and a new **Version**. Import the
copy once with each **Merge strategy** to compare: with **Additive merge** or **Override merge**, the
removed operation is still in the new version, and with **Override merge** a changed property takes
the copy's definition.

### File Upload

<Screenshot id="import-wizard-intake" alt="File Upload intake: a drop zone with Browse files and the supported extensions" />

1. **Click “File Upload”**, then drop a file on **Drop files here** or **click “Browse files”**.
   **Supports** lists the extensions Apiome reads.
2. Try `apiome-ui/examples/openapi/30-openapi-3.0-petstore.yaml`, then **click “Analyze →”**.

### URL Import

1. **Click “URL Import”** and enter the **Specification URL** — for example
   `https://raw.githubusercontent.com/apiome/apiome/main/apiome-ui/examples/openapi/30-openapi-3.0-petstore.yaml`.
2. For a protected URL, choose **Authentication**: **Bearer Token**, **API Key** (with its **Header
   Name**, such as `X-API-Key`) or **Basic Auth**.
3. **Click “Test URL”**; when it says **URL tested ✓**, **click “Continue”**.

Only `http` and `https` URLs work. The fetch runs in your browser, so the server must allow it
(CORS) — if it does not, download the file and use **File Upload**.

#### Keep a URL import up to date

A project imported from a URL keeps following that URL. Every five minutes by default, Apiome asks
the URL whether the document changed, and adds a version when it did:

- **Nothing changed** — the server answers *not modified* to the `ETag` and `Last-Modified` it sent
  at import time, or sends the same document again. Nothing happens.
- **The document changed** — Apiome imports it into the same project with the options you chose on
  the **Preview** step (selected schemas, naming, prefixes and the rest). The new version is
  labelled with the date and time, for example `2026-10-30T14:03Z`.
- **The document is older** — a `Last-Modified` earlier than the imported one never replaces it.
- **You edited the version in Apiome** — the refresh is held so your edits are not overwritten. To
  follow the URL again, import it again.

Some URL imports are never refreshed:

- **Protected URLs.** A URL imported with **Bearer Token**, **API Key** or **Basic Auth** is not
  refreshed, because Apiome never stores those credentials.
- **Dry runs.** A dry run saves nothing, so there is nothing to refresh.

Apiome checks from its server, not your browser, so the URL must be reachable from there. Addresses
on a private network are refused, as for every URL Apiome fetches. A check that fails is retried
later, waiting longer after each failure.

To turn refresh off for one URL, or to change how often it is checked, use the
[REST API](#with-the-cli-or-the-api) (`PATCH …/url-imports/{id}`). An operator can stop every
refresh — URL imports and repositories — with `APIOME_REFRESH_ENABLED=false`, and change the
default cadence with `APIOME_REFRESH_DEFAULT_INTERVAL` (seconds).

### Clipboard Paste

1. **Click “Clipboard Paste”**, then **“Paste from Clipboard”** — or paste into **Specification
   Content**.
2. Try the contents of `apiome-ui/examples/swagger/01-swagger-2-petstore.yaml`, then **click

### Git Repository

You need a linked GitHub or GitLab account first — **“Go to Linked accounts”** takes you there.

1. **Click “Git Repository”** and enter the **Repository URL** (`https://github.com/org/repo` or
   `org/repo`), then **click “Load repository”**.
2. Choose a **Branch** or **Tag** and the **Spec path** — for example `specs/openapi.yaml`.
3. **Click “Open file”**, then **“Analyze →”**.

To import many files from one repository, register it under [Repositories](./repositories.mdx)
instead.

### SwaggerHub

1. **Click “SwaggerHub”** and enter the **Owner / Organization** and **API Name** as they appear in
   the SwaggerHub URL — for `app.swaggerhub.com/apis/myorg/petstore`, `myorg` and `petstore`.
2. Keep **Use latest version**, or pick **Specific Version**. A private API needs an **API Key**.
3. **Click “Test & Fetch”**, then continue.

### Design with AI

**Design with AI** drafts a specification from a description; **“Import This Spec”** loads the
draft into the wizard as if you had pasted it. It is also on **New project → Design with AI**.

### GraphQL schemas

A GraphQL schema (`.graphql` or `.gql` SDL) can be imported as a project: the wizard converts it to
OpenAPI first, and each type becomes a class. Try `apiome-ui/examples/graphql/11-github-style-api.graphql`.

| In the schema | In the project |
| --- | --- |
| `type` and `input` | A class, with one property per field; a non-null field is required |
| `interface` | A class marked `x-graphql-interface`; a type that implements it extends it |
| `enum` | A class whose values are the enum values |
| `union` | A class that is one of its member types |
| `scalar` | A class of the matching type (`DateTime` is a `date-time` string); a custom scalar is a string |
| `Query`, `Mutation`, `Subscription` | Left out: they are operations, not data |

**Directives are kept.** Every directive applied to a type, a field or an enum value — `@deprecated`,
`@key(fields: "id")` or your own — is kept with its arguments, so nothing the schema says is lost.
A type's or a field's directives are stored as `x-graphql-directive` on its class or property, for
example `[{ "name": "key", "arguments": { "fields": "id" } }]`. An enum value's are listed under
`x-graphql-enum-value-directives` on the enum's class.

To keep the schema in its own GraphQL form instead — queries, mutations and all — import it to the
catalog (below).

### Protocol Buffers and Avro schemas

A `.proto` file (proto2 or proto3) or an Avro schema (`.avsc`) can be imported as a project too: each
message, record and enum becomes a class. Try `apiome-ui/examples/protobuf/04-telemetry-stress.proto`
or `apiome-ui/examples/avro/02-order-record.avsc`. Services and RPCs are not imported.

| In the schema | In the project |
| --- | --- |
| A Protobuf `message`, an Avro `record` | A class, with one property per field |
| An `enum` | A class whose values are the enum's values |
| `repeated` (Protobuf), `array` (Avro) | A list property |
| `map<K, V>` (Protobuf), `map` (Avro) | An object property whose values are of the map's type |
| A Protobuf `oneof` | One optional property per member, each marked `x-proto-oneof` with the group's name; the class lists its groups under `x-proto-oneofs` — at most one member is set |
| An Avro union | `null` and one type becomes an optional property; several types become a property that is one of them |
| An Avro logical type | The type it stands for, marked `x-avro-logical-type` |

Avro logical types become: `date` → a date, `time-millis` / `time-micros` → a time,
`timestamp-*` and `local-timestamp-*` → a date and time, `uuid` → a UUID, `duration` → a duration, and
`decimal` → a number that keeps its `x-avro-precision` and `x-avro-scale`. A logical type Apiome does
not know keeps its underlying type (a `long` stays a 64-bit integer) and its name.

## Import to catalog

**Click “Import to catalog”** on the [Catalog](./catalog.mdx). Steps: **Source → Detect & route →
Options → Quality → Import**.

1. **Source** — **File Upload** (drop a source file), **URL Import** (**Document URL**, then
   **“Fetch and detect”**), **Clipboard Paste** (**Source content**, then **“Detect pasted
   source”**) or **Git Repository**
   (**Repository URL**, **Branch, tag, or commit**, **Path or glob**, then **“Fetch and detect”**).
   Try `apiome-ui/examples/graphql/01-simple-user.graphql` or
   `apiome-ui/examples/asyncapi/01-user-events-2.6.yaml`. Not sure your format is supported?
   **Click “Which formats can I import?”** to open [How the catalog
   works](./catalog.mdx#how-the-catalog-works) over the wizard. A format that can be brought in
   another way, such as reading a schema from a live endpoint, gets its own card here once Apiome
   can import it that way. No format has one yet: import a GraphQL schema or a `.proto` file
   through **File Upload**, **URL Import** or **Clipboard Paste**.
2. **Detect & route** — Apiome names the format it detected (**Auto-detected: GraphQL**) and where
   it goes. OpenAPI and Swagger are routed to Projects; choose **Import as format** if the
   detection is ambiguous.
3. **Options** — for JSON Schema, choose to keep it in the catalog for later conversion or to use it
   as types. **Skip the quality step for clean imports** saves a step. **Click “Dry run”** to see
   what **Import** would do without saving anything — see [Dry run a catalog
   import](#dry-run-a-catalog-import).
4. **Quality** — a pre-flight lint. **“Import”** when it is clean, or **“Import anyway”**.
5. **Import** — the item is stored in its original format. Use **Convert to OpenAPI** when you are
   ready.

### Dry run a catalog import

A dry run runs the same importer as **Import**, then stops before anything is written. It creates
no catalog item, version or import job.

1. On **Options**, **click “Dry run”** beside **Continue**.
2. Read the result under **Dry run complete. Nothing was saved.**:

   | Row | What it tells you |
   | --- | --- |
   | **Format** | The format the importer recognized, and its paradigm. |
   | **Destination** | Where **Import** would put it: a **Catalog item**, a **Project** or **Types**. A warning says so when it would not be the catalog. |
   | **Why** | The importer's reason for that destination. |
   | **Catalog item** | The name and slug **Import** would use. An existing item with that slug gets a new revision. |
   | **Contents** | The services, operations, types and channels it would hold. |
   | **Quality** | The lint score and grade. |
   | **Fingerprint** | The revision fingerprint **Import** would record. Hover for the full value. |

   If the source could not be imported, **Import would fail** gives the reason and how to fix it.
3. **Click “Continue”** to go on to **Quality** and **Import** as usual, or **“← Back”** to change
   the source.

<Screenshot id="catalog-import-dry-run" alt="The Options step after a dry run: Dry run complete. Nothing was saved., then Format GraphQL, Destination Catalog item, the catalog item's name and slug, its contents, quality and fingerprint, with Dry run and Continue in the footer" />

The dry run is the import pre-flight. From the CLI, `apiome import preflight` gives the same answer.

## With the CLI or the API

- CLI: `apiome import auto ./30-openapi-3.0-petstore.yaml`, `apiome import graphql
  ./01-simple-user.graphql`, `apiome import preflight` — see the [CLI
  quick-start](../reference/cli-quickstart.md).
- REST: `POST /v1/tenants/{tenant}/imports` (and `…/imports/upload`), `GET …/imports/{job}`,
  `POST …/imports/{job}/commit|rollback`, `POST /v1/import/detect`, and
  `POST /v1/tenants/{tenant}/import/project-delta` (the Changes step's comparison) — see [Import a
  specification](./import-a-spec.md) and the [API reference](../reference/api-reference.md).
- URL imports: `GET /v1/tenants/{tenant}/url-imports` lists them with when each was last checked
  and refreshed, `PATCH …/url-imports/{id}` turns refresh on or off
  (`{"autoRefreshEnabled": false}`) or sets its cadence (`{"refreshIntervalSeconds": 3600}`), and
  `POST …/url-imports` is what the wizard calls after a URL import — see
  [URL imports](../reference/rest/url-imports.md).
