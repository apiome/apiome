The **document store** is where the REST API keeps files that never change once written. It has
three backends, and you choose one with environment variables on the `rest` service:

| `APIOME_DOCUMENT_STORE` | Objects are kept in | Use it for |
| --- | --- | --- |
| `db` (default) | The Apiome database | Any installation without a bucket. Nothing to set up. |
| `s3` | A bucket on an S3-compatible service | Production. Works with AWS S3, MinIO, Garage, Cloudflare R2 and Google Cloud Storage (interoperability mode). |
| `filesystem` | A directory on the REST host | Development and single-node installations. |

Apiome writes four kinds of object to the store:

- **The original document of every import** (see [Originals of imports](#originals-of-imports)).
- **The generated OpenAPI document of a version**, kept until the version changes (see
  [Rendered documents](#rendered-documents)).
- **The frozen schema of a version** (see [Frozen schemas](#frozen-schemas)).
- **Export downloads larger than the database threshold** (see
  [Large export downloads](#large-export-downloads)).

## How objects are stored

Every object is named by the SHA-256 of its bytes, inside the owning tenant's folder:

```text
<prefix>/tenants/<tenant>/objects/sha256/<first two hex digits>/<sha-256>
```

- **The same bytes are stored once.** Writing a file the tenant already holds writes nothing.
- **Tenants never share a folder.** The same file in two tenants is two objects.
- **Objects are never changed**, only added and removed.

## Choose the storage folder

`APIOME_DOCUMENT_STORE_PREFIX` is the folder all Apiome objects are written under. It applies to
every backend, and defaults to `apiome`:

```bash
APIOME_DOCUMENT_STORE_PREFIX=apiome                  # s3://<bucket>/apiome/tenants/…
APIOME_DOCUMENT_STORE_PREFIX=teams/platform/apiome   # a nested folder
APIOME_DOCUMENT_STORE_PREFIX=                        # the root of the bucket or directory
```

Use it to share one bucket with other applications, or to keep two Apiome installations apart in
the same bucket. Leading and trailing slashes are ignored; `.` and `..` segments are refused.

:::warning
Changing the prefix does not move objects. Objects written under the old folder are no longer
found, so copy them to the new folder before you restart the REST API.
:::

## Use an S3-compatible bucket

1. Create the bucket. Apiome does not create it.
2. Give the key (or IAM role) permission to read, write and delete objects under the prefix:
   `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`, and `s3:ListBucket` on the bucket.
3. Set the variables in `apiome-rest/.env` (or on the `rest` service in Compose) and restart.

### Garage

```bash
APIOME_DOCUMENT_STORE=s3
APIOME_DOCUMENT_STORE_BUCKET=apiome
APIOME_DOCUMENT_STORE_PREFIX=apiome
APIOME_DOCUMENT_STORE_ENDPOINT_URL=http://garage.internal:3900
APIOME_DOCUMENT_STORE_REGION=garage
APIOME_DOCUMENT_STORE_ADDRESSING_STYLE=path
APIOME_DOCUMENT_STORE_ACCESS_KEY_ID=GK…
APIOME_DOCUMENT_STORE_SECRET_ACCESS_KEY=…
APIOME_DOCUMENT_STORE_ALLOW_PRIVATE=true   # only when Garage is on a private network
```

`REGION` must match `s3_region` in Garage's configuration (`garage` unless you changed it). Leave
`APIOME_DOCUMENT_STORE_SSE` empty: Garage does not offer SSE-S3 or SSE-KMS.

### MinIO and Cloudflare R2

The same variables as Garage, with the service's endpoint. For MinIO use
`ADDRESSING_STYLE=path` and `REGION=us-east-1` unless you configured another. For R2 use
`ENDPOINT_URL=https://<account id>.r2.cloudflarestorage.com` and `REGION=auto`.

### AWS S3

```bash
APIOME_DOCUMENT_STORE=s3
APIOME_DOCUMENT_STORE_BUCKET=acme-apiome-documents
APIOME_DOCUMENT_STORE_REGION=eu-west-1
APIOME_DOCUMENT_STORE_SSE=kms
APIOME_DOCUMENT_STORE_KMS_KEY_ID=alias/apiome-documents
```

Leave the two key variables unset to use the instance's IAM role or the standard `AWS_*`
environment variables. Set both to use a static key pair.

## Use a directory

```bash
APIOME_DOCUMENT_STORE=filesystem
APIOME_DOCUMENT_STORE_PATH=/var/lib/apiome/documents
```

The directory is created on the first write. In Docker, mount a volume at that path, or the
objects are lost when the container is replaced. Every REST instance must see the same directory,
so use `s3` when you run more than one.

## Settings

All of these are set on the `rest` service.

| Variable | Default | Meaning |
| --- | --- | --- |
| `APIOME_DOCUMENT_STORE` | `db` | The backend: `db`, `s3` or `filesystem`. |
| `APIOME_DOCUMENT_STORE_PREFIX` | `apiome` | The folder all objects are written under. Empty for the root. |
| `APIOME_DOCUMENT_STORE_PATH` | — | `filesystem`: the storage directory. Required. |
| `APIOME_DOCUMENT_STORE_BUCKET` | — | `s3`: the bucket. Required. |
| `APIOME_DOCUMENT_STORE_REGION` | `us-east-1` | `s3`: the signing region. |
| `APIOME_DOCUMENT_STORE_ENDPOINT_URL` | — | `s3`: the service URL for anything other than AWS. |
| `APIOME_DOCUMENT_STORE_ADDRESSING_STYLE` | `auto` | `s3`: `path` (`https://host/bucket/key`), `virtual` (`https://bucket.host/key`) or `auto`. |
| `APIOME_DOCUMENT_STORE_SSE` | — | `s3`: encryption requested on each write. `s3` (SSE-S3) or `kms` (SSE-KMS). Empty uses the bucket's default. |
| `APIOME_DOCUMENT_STORE_KMS_KEY_ID` | — | `s3` with `SSE=kms`: the key. Empty uses the bucket's default KMS key. |
| `APIOME_DOCUMENT_STORE_ACCESS_KEY_ID` | — | `s3`: a static access key. Set it together with the secret key, or set neither. |
| `APIOME_DOCUMENT_STORE_SECRET_ACCESS_KEY` | — | `s3`: the secret key. Keep it in your secret manager. |
| `APIOME_DOCUMENT_STORE_PRESIGN_TTL_SECONDS` | `300` | `s3`: how long a presigned download link stays valid (1 second to 7 days). |
| `APIOME_DOCUMENT_STORE_DB_MAX_BYTES` | `33554432` | `db`: the largest single object accepted (32 MiB). |
| `APIOME_DOCUMENT_STORE_GZIP_MIN_BYTES` | `65536` | Originals of at least this many bytes are stored gzip-coded. `0` turns the coding off. |
| `APIOME_DOCUMENT_STORE_ALLOW_PRIVATE` | `false` | `s3`: allow an endpoint on a private or loopback address. |

### Endpoints on a private network

The endpoint URL passes the same check as any URL the REST API calls: it must be `http` or
`https`, carry no user name or password, and resolve to public addresses. A store on your own
network (`http://garage.internal:3900`, `http://127.0.0.1:9000`) is refused until you set
`APIOME_DOCUMENT_STORE_ALLOW_PRIVATE=true`. That setting applies to the document store endpoint
only. It does not let users import from private addresses, which `APIOME_SSRF_ALLOW_PRIVATE` would.

## Originals of imports

Every import writes the document it read to the store, after the workspace's secret scrub, and
records it as the revision's `original` in `version_documents`. An archive is written as one
object per file (`original_part`) plus a manifest (`original`). A source that is withheld writes
nothing. [What an import records](../bring-in/what-an-import-records.md#the-original-document)
describes this for users.

Where the document text is also kept depends on the backend:

| `APIOME_DOCUMENT_STORE` | The store holds | The database holds |
| --- | --- | --- |
| `db` (default) | The original | The text as before (`version_import_snapshots.source_text`, `format_metadata.sourceContent`) and the pointer |
| `s3` or `filesystem` | The original | The pointer only |

:::note
Every feature that needs the document reads it from the store, whatever the backend:
[How originals are read](#how-originals-are-read). You can run on `s3` or `filesystem` without
losing export, conversion or the source workspace's as-imported view.
:::

- **Large documents are gzip-coded.** A document of at least
  `APIOME_DOCUMENT_STORE_GZIP_MIN_BYTES` bytes (64 KiB) is stored compressed, and its
  `document_objects.encoding` is `gzip`. Smaller documents, and documents gzip does not shrink,
  are stored as they are (`identity`).
- **The digest is of the stored bytes.** For an `identity` object, `document_objects.sha256` is
  the SHA-256 of the document text. For a `gzip` object it is the SHA-256 of the compressed bytes.
- **If the store cannot be written**, the import still succeeds and the text stays in the
  database, whatever the backend. The REST log has a line `original not stored`.
- **With `db`, an original larger than `APIOME_DOCUMENT_STORE_DB_MAX_BYTES` is not stored.** The
  text stays in the database as before.
- **Existing versions are not changed.** Only imports that run after the upgrade write an original.

## How originals are read

Export, conversion, lint evidence, compatibility checks, the catalog's **Source & Code**
tab, the schema registry and the source workspace's as-imported view all read an import's
document the same way:

1. **The document store.** The revision's `original` in `version_documents`, decoded if it is
   gzip-coded. An archive comes back as its files, with the root file the import chose.
2. **The database, for older revisions.** A revision imported before originals were stored is
   read from where its text was kept then (`format_metadata.sourceContent` or
   `version_import_snapshots.source_text`).

If neither holds the document, the feature reports that the source was not kept, as before (for
an export, `422 source-not-captured`).

- **If an object cannot be read** (a bucket that is down, an object deleted by hand), the reader
  falls back to the database text when there is one. The REST log has a line `original not read`.
- **An OpenAPI, Swagger or Arazzo project is not rebuilt from its original.** Its classes, paths
  and workflows are what you edit, so exports are generated from them. The original is used only
  to show what was imported.
- **Lists do not carry the document.** The catalog list, a catalog item and version lookups
  return `format_metadata` without `sourceContent`. `GET …/catalog/{tenant}/{item}/source`
  returns the document.

### The parsed-model cache

Reading a version for export or a check means parsing its document. Each REST worker keeps the
most recently parsed models in memory, keyed by the SHA-256 of the document, so a second read of
the same document does not parse it again. An import that changes the document has a new digest,
so nothing needs to be cleared.

| Setting | Default | Meaning |
| --- | --- | --- |
| `APIOME_CANONICAL_MODEL_CACHE_ENTRIES` | `32` | The most models one worker keeps. `0` turns the cache off. |
| `APIOME_CANONICAL_MODEL_CACHE_MAX_BYTES` | `16777216` | The most document bytes the kept models may add up to (16 MiB). A document larger than a quarter of this is parsed every time. `0` turns the cache off. |

Memory use grows with both settings and with the number of REST workers. Lower them on a small
host.

## Large export downloads

A finished export keeps its download for `APIOME_EXPORT_ARTIFACT_RETENTION_HOURS` (24 by default).

| Download size | Where it is kept |
| --- | --- |
| Up to `APIOME_EXPORT_ARTIFACT_DB_MAX_BYTES` (32 MiB) | The database |
| Above that, up to `APIOME_EXPORT_ARTIFACT_MAX_BYTES` (32 MiB) | The document store (`s3` or `filesystem`) |
| Above `APIOME_EXPORT_ARTIFACT_MAX_BYTES` | Nowhere: the export fails with `EXPORT_ARTIFACT_TOO_LARGE` |

The two limits are equal by default, so every download goes to the database. To allow larger
exports, configure `s3` or `filesystem` and raise `APIOME_EXPORT_ARTIFACT_MAX_BYTES`. To move
large downloads out of the database, lower `APIOME_EXPORT_ARTIFACT_DB_MAX_BYTES`.

With `APIOME_DOCUMENT_STORE=db`, an export above the database limit fails with
`EXPORT_ARTIFACT_STORE_UNAVAILABLE`.

When a download expires it can no longer be fetched, but its object stays in the bucket or
directory. Apiome does not yet remove unused objects, so remove them yourself if space matters.

## Document records and the content stamp

The database keeps a record of each stored document, apart from the bytes. Migration V403 adds
two tables and one column:

| Name | What it records |
| --- | --- |
| `document_objects` | One row per stored object: tenant, SHA-256, size, media type, content encoding, the backend that holds it (`db`, `s3` or `filesystem`) and its key there. One row per tenant and SHA-256. |
| `version_documents` | Which object a revision uses, and for what. See the roles below. |
| `versions.content_stamp` | A counter for each revision that goes up when the revision's content changes. |

A row in `version_documents` has one of these roles:

| Role | The object is |
| --- | --- |
| `original` | The file the revision was imported from. For a set of files (an Arazzo document with its sources, a multi-file protobuf), it is the manifest that lists the files. |
| `original_part` | One file of a set, with its path inside the set. |
| `rendered_openapi` | An OpenAPI document generated from the revision. |
| `rendered_canonical` | A canonical model document generated from the revision. |
| `frozen_schema` | A frozen schema snapshot. |

A rendered document also records the content stamp it was generated at, and the generator and
its version.

### How the content stamp changes

- **It goes up by one for each transaction** that changes the revision's classes, properties,
  paths, operations, parameters, responses, servers, security schemes, component pins, canonical
  API model or the revision's own fields. A save that writes many rows still counts as one
  change.
- **Editing a shared property** in the project library raises the stamp of every revision that
  uses it.
- **Reading never changes it.** Neither do saves that change nothing, moving items on the canvas,
  or Apiome updating a revision's quality score.

A rendered document is current while its recorded stamp equals the revision's stamp. The stamp
starts at `0` for every revision, including revisions that existed before the upgrade. The
migration adds the column without rewriting the `versions` table, so it is safe to run on a
large, live database.

## Rendered documents

Apiome generates a version's OpenAPI document from its classes, properties and paths. For a large
version this takes many database reads, so Apiome generates the document once and stores the
bytes. The next request for the same version reads the stored object.

| When | What Apiome does |
| --- | --- |
| The first request for a version | Generates the document, writes it to the store and records it in `version_documents` with the role `rendered_openapi`. |
| A later request, version unchanged | Reads the stored bytes. It reads no class, property or path. |
| The version is edited | The [content stamp](#how-the-content-stamp-changes) goes up, so the next request generates a new document. |
| The project's slug, description or metadata changes | The next request generates a new document. |
| The version is published | Generates and stores the document straight away, so the first reader gets stored bytes. |
| Apiome's generator changes in an upgrade | The next request generates a new document. |

`GET /v1/schema/{tenant}/{project}/{version}` serves these bytes. Its response has an
`ETag` header, which is the SHA-256 of the document in double quotes. Send that value in
`If-None-Match` and the answer is `304 Not Modified`, with no body, while the document is
unchanged:

```bash
curl -sI https://api.example.com/v1/schema/acme/payments-api/2.1.0 | grep -i etag
# etag: "7f2c…a041"

curl -s -o /dev/null -w '%{http_code}\n' \
  -H 'If-None-Match: "7f2c…a041"' \
  https://api.example.com/v1/schema/acme/payments-api/2.1.0
# 304
```

Things to know:

- **The document is the same as before.** The stored bytes are exactly what the generator
  produces.
- **Older documents stay in the store.** An edit leaves the previous document and its record in
  place. Apiome does not yet remove unused objects.
- **A store failure does not fail the request.** If the bucket cannot be reached, Apiome generates
  the document for each request and serves it. The log has `rendered document not stored`.
- **Rendered documents are not compressed**, so the stored object's SHA-256 is the `ETag`.
- With `APIOME_DOCUMENT_STORE=db`, a document larger than `APIOME_DOCUMENT_STORE_DB_MAX_BYTES` is
  generated for each request. Use `s3` or `filesystem` for very large versions.

A version with a canonical model (a non-OpenAPI import) also gets that model stored as JSON, with
the role `rendered_canonical`, when it is published.

### Frozen schemas

[Freezing a version](../ship/publish-a-version.md#freeze-a-versions-schema) keeps its OpenAPI
document byte-for-byte. The bytes are a store object, linked to the version with the role
`frozen_schema`. The `version_spec_snapshots` row keeps the SHA-256, size, counts, who froze the
version and the download count.

| `APIOME_DOCUMENT_STORE` | Where the frozen bytes are |
| --- | --- |
| `s3`, `filesystem` | In the store only. The row's `content` column is empty. |
| `db` | In the store and in the row's `content` column. |

- If the store write fails during a freeze, the bytes are kept in the row and the freeze succeeds.
- A version frozen before this release keeps its bytes in the row and is served from there.
- **Unfreezing** removes the row and the link. The object stays in the store.
- If a frozen version's bytes cannot be read from the store, `/v1/schema` answers `503`. It never
  falls back to a newly generated document, because that could differ from the frozen one.

Migration V404 makes the `content` column optional. It changes no rows.

## Troubleshooting

Errors name the bucket and the provider's error code. Access keys and secret keys are never
written to an error or a log.

| Message | Fix |
| --- | --- |
| `APIOME_DOCUMENT_STORE=s3 needs APIOME_DOCUMENT_STORE_BUCKET` | Set the bucket. |
| `APIOME_DOCUMENT_STORE_ENDPOINT_URL is refused` | The endpoint is on a private address. Set `APIOME_DOCUMENT_STORE_ALLOW_PRIVATE=true`. |
| `… (NoSuchBucket: …)` | Create the bucket, or check the endpoint and region. |
| `… (AccessDenied: …)` | Grant the key read, write and delete on the prefix. |
| `… (SignatureDoesNotMatch: …)` | Check the secret key, and that `REGION` matches the service. |
| A host name like `bucket.host` does not resolve | Set `APIOME_DOCUMENT_STORE_ADDRESSING_STYLE=path`. |
| `/v1/schema` answers `503` for a frozen version | The frozen object is missing from the bucket or directory. Restore it from a backup, or unfreeze the version and freeze it again. |
| `rendered document not stored` in the REST log | The store refused the write. `/v1/schema` still works but generates the document for each request. Check the store settings above. |
