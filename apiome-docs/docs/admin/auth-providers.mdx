**System settings** holds three things for the whole installation: the **sign-up policy** — who
may create an account — the **sign-in providers** — the OAuth and OpenID Connect identity providers
people can use on the sign-in page and link on [Linked accounts](../workspace/linked-accounts.mdx) —
and **single sign-on**, a workspace's own SAML or OIDC identity provider for the email domains it
owns (see [Single sign-on](./single-sign-on.mdx)).
Both can be set in the **database**, from this screen, or in **`.env`**; a value stored here
overrides the environment, and a blank field falls back to it. **Sign in to the admin console and
choose System settings** in the sidebar.

<Screenshot id="admin-auth-providers" alt="System settings scrolled past the Sign-up card to the GitHub card: enabled from the database, its secret set, and a successful Validate" />

The **Sign-up** card comes first, then **Single sign-on**, then one card per provider.

:::tip Sign-in providers or single sign-on?
A **sign-in provider** here is one app registration for the whole installation — anyone with a
GitHub or Okta account can use it. **Single sign-on** connects *one company's* identity provider,
only for the email domains that company owns, and is set up on the
[Single sign-on](./single-sign-on.mdx) card. Use single sign-on when a customer wants their people
to sign in with their own Okta, Entra ID or other IdP.
::: The list shows only providers that
are **configured** — anything stored in the database for them, or a row that once existed. A
provider set up purely in `.env` does not appear until you add it.

## Sign-up policy

The **Sign-up** card decides who can create an account. One policy covers every way in — the email
form and each sign-in provider — so a mode can never apply to one and not another. It only gates
**new** accounts: people who already have an account sign in under every mode.

<Screenshot id="admin-signup-policy" alt="System settings: the Sign-up card with Open chosen, northwind.io and contoso.example as allowed email domains, throwaway.example as a blocked email domain, and Recent blocked sign-ups listing a disposable address and a rate-limited provider sign-up" />

| Mode | Who can create an account | What a refused person sees |
| --- | --- | --- |
| **Open** | Anyone. With **Allowed email domains** filled in, only addresses at those domains | *New accounts on this server are limited to approved email domains…* |
| **Invite only** | No one on their own. A workspace administrator [invites](../workspace/members.mdx) people who already have an account, and they sign in as usual | *New accounts on this server are by invitation only…* |
| **Closed** | No one | *New account sign-ups are currently disabled on this server…* |

To set the policy:

1. Under **Who can create an account**, **choose “Open”, “Invite only” or “Closed”**.
2. For **Open**, optionally fill in **Allowed email domains** — one domain per line, for example
   `northwind.io`. Leave it empty to allow any domain. Domains match exactly, so list a subdomain
   such as `mail.northwind.io` on its own line. The field is switched off for the other two modes.
3. **Click “Save”**. A **Saved** note confirms it, and the footer reads *Last changed … by …*.

An entry that is not a domain — an email address, a URL, a wildcard — is named under the field and
**Save** stays switched off until it is fixed.

**Until you save a policy, `.env` decides.** The card then carries an **Env-derived** chip and its
footer reads *Not stored — .env gives Open* (or *Closed*): `AUTH_SIGNUP_DISABLED=true` in
`apiome-ui/.env` closes sign-up, and anything else leaves it open. Saving stores the policy in the
database, where it wins over the variable. **Click “Use .env”** to remove the stored policy and go
back to the variable.

The sign-up page, `/signup`, follows the policy: **Open** lists the providers and the email form
(and names the allowed domains), while **Invite only** and **Closed** show only a notice and the
sign-in link.

A saved policy applies to the next sign-up — no restart. Other server instances pick it up when
their policy cache expires, within 30 seconds by default (`SIGNUP_POLICY_CACHE_TTL_SECONDS`, 1–300
seconds, read by both apiome-ui and apiome-rest). Tightening the policy also stops a sign-up that
is part-way through. Every change is recorded in the `apiome.signup_policy_audit` table with the
policy before and after it.

If the database cannot be read, Apiome keeps using the last policy it read; with none to fall back
on, it refuses new accounts until the database is back.

### Abuse protection

A public sign-up page invites scripted accounts and email bombing, so sign-up carries guards. Each
refuses with its own message, and each refusal is recorded:

| Guard | Applies to | What the person sees |
| --- | --- | --- |
| **Rate limits** — 20 sign-up or **Resend email** requests an hour per network, 3 sign-up emails an hour per address | Email sign-up | *Too many sign-up attempts. Wait an hour, then try again.* |
| **Rate limit** — 10 provider sign-ups a minute per network | Provider sign-up | *Too many sign-up attempts from your network…* |
| **Disposable email addresses** — a list of throwaway email services Apiome ships, plus your **Blocked email domains** | Email sign-up | *Addresses from disposable email services cannot be used to sign up…* |
| **Security check** — Cloudflare Turnstile, when [configured](./operating-apiome.mdx#sign-up-security-check) | Email sign-up form | *We could not confirm the security check…* |

Provider sign-up meets only its rate limit: the provider has already confirmed the address.

To block more domains, fill in **Blocked email domains** on the **Sign-up** card — one domain per
line, for example `throwaway.example` — and **click “Save”**. A listed domain also blocks its
subdomains. The field works in every mode and adds to the bundled list, which always applies. The
domains are stored with the policy, so **Use .env** removes them too.

**Recent blocked sign-ups**, at the foot of the card, lists the latest refusals: when, the
**Reason**, the **Path** (*Email*, or *Provider sign-up*), the **Address** when one was entered, and
a **Client** code. Equal client codes mean the same network; the code is a cut of a salted hash, so
no IP address is ever shown. **Click “Refresh”** to reload it. A rate limit is listed once per
window, however many requests were refused. Sign-up happens before any workspace exists, so these
refusals appear here, never in a workspace's [access audit](../reference/rest/access.md#list-audit-v1-access-tenant-slug-audit-get).

## Email sign-up

People can create an account with an email address and a password
([Create an account](../getting-started/create-an-account.mdx#with-an-email-address)) when the
installation can send them a confirmation link. Set all three in `apiome-ui/.env`:

| Variable | What it is |
| --- | --- |
| `SENDGRID_API_KEY` | The SendGrid key Apiome sends email with (two-factor email codes use it too) |
| `EMAIL_FROM` | The sender address, for example `Apiome <no-reply@apiome.example>` |
| `BETTER_AUTH_URL` | The public address of Apiome, which the confirmation link points at, for example `https://apiome.example` |

With any of them missing, **Create one** offers only the providers and says that email sign-up is
not available. Restart apiome-ui after changing them.

The sign-up policy above applies to email sign-up exactly as it does to providers. Other rules:

- **No account can be used before its email is confirmed.** The confirmation link works once and
  expires after 24 hours; each new email replaces the previous link.
- **The form never says whether an address is registered.** Someone who signs up with an address
  that already has an account sees the same *Check your email* page; the owner of the address gets
  an email saying the account exists, with a sign-in link.
- **Email is rate-limited.** One address gets at most 3 sign-up emails an hour, and one network at
  most 20 sign-up requests an hour.
- **Disposable addresses are refused**, and an optional security check can sit on the form — see
  [Abuse protection](#abuse-protection).

Confirmation links are stored only as a hash, in the `apiome.email_verification_token` table.

### Terms and privacy links

The sign-in and sign-up pages end with *By signing in (creating an account), you agree to our
Terms of Service and Privacy Policy* — but only for the pages your installation has. Set
`APIOME_TERMS_URL` and `APIOME_PRIVACY_URL` in `apiome-ui/.env` to their `https://` addresses;
with neither set the line is left out, rather than linking to nothing.

**OIDC** is any conformant OpenID provider (Authentik, PingFederate, ZITADEL and others); one
generic OIDC provider is supported per installation.

**Atlassian** signs people in with the Atlassian account they use for Jira and Confluence. Its
endpoints are fixed, so it needs only a client ID and a client secret.

**Bitbucket** is Bitbucket Cloud. Its **client ID** is the OAuth consumer's **Key** and its
**client secret** the consumer's **Secret**. Bitbucket Data Center is not supported.

**Slack** is **Sign in with Slack**, for teams whose shared identity is their Slack workspace. Its
endpoints are fixed, so it needs only a client ID and a client secret.

**LinkedIn** is **Sign In with LinkedIn using OpenID Connect**, for people who sign in with their
LinkedIn account. Its endpoints are fixed, so it needs only a client ID and a client secret. Its
**client secret** is the app's **Primary Client Secret**.

**Discord** is for developer communities whose members already have a Discord account. Its
endpoints are fixed, so it needs only a client ID and a client secret.

**Salesforce** signs people in with the account they use for a Salesforce org. Its **client ID**
is the app's **Consumer Key** and its **client secret** the **Consumer Secret**. Unlike Okta's,
its **Issuer** is optional: leave it empty to sign in through `https://login.salesforce.com`, or
set it to your org's My Domain (`https://acme.my.salesforce.com`) to send everyone to that org's
own login page, or to `https://test.salesforce.com` for a sandbox.

**Notion** is for product and documentation teams whose people already have a Notion account. Its
endpoints are fixed, so it needs only a client ID and a client secret — the **OAuth Client ID** and
**OAuth Client Secret** of a public Notion integration. Notion is a **Link first** provider: people
link it to an account they already have, and nobody can create an account with it (see
[How a provider's email is trusted](#how-a-providers-email-is-trusted)).

**Figma** is for designers and front-end developers whose people already have a Figma account. Its
endpoints are fixed, so it needs only a client ID and a client secret — the **Client ID** and
**Client secret** of a Figma OAuth app. Like Notion, Figma is a **Link first** provider: people
link it to an account they already have, and nobody can create an account with it.

**Linear** is for product-engineering teams that track their work in Linear. Its endpoints are
fixed, so it needs only a client ID and a client secret — the **Client ID** and **Client secret**
of a Linear OAuth application. Like Notion and Figma, Linear is a **Link first** provider: people
link it to an account they already have, and nobody can create an account with it.

**Dropbox** is for people whose personal or work identity is their Dropbox account. Its endpoints
are fixed, so it needs only a client ID and a client secret — the **App key** and **App secret**
of a Dropbox app.

**Zoom** is for organizations whose people already have a Zoom account. Its endpoints are fixed,
so it needs only a client ID and a client secret — the **Client ID** and **Client Secret** of a
Zoom **General App**.

**Hugging Face** is **Sign in with Hugging Face**, for machine-learning teams whose people already
have a Hugging Face account. Its endpoints are fixed, so it needs only a client ID and a client
secret — those of a Hugging Face OAuth app.

**Vercel** is **Sign in with Vercel**, for frontend and API teams whose people already have a
Vercel account. Its endpoints are fixed, so it needs only a client ID and a client secret — those
of an **App** in your Vercel team's settings.

**Railway** is **Login with Railway**, for indie and startup API builders who deploy on Railway.
Its endpoints are fixed, so it needs only a client ID and a client secret — those of a **Web**
OAuth app in your Railway workspace's settings. Like Notion, Figma and Linear, Railway is a **Link
first** provider: people link it to an account they already have, and nobody can create an
account with it.

**HubSpot** is HubSpot's OAuth sign-in, for the marketing and CRM teams that consume your APIs. Its
endpoints are fixed, so it needs only a client ID and a client secret — those of a **public app**
in a HubSpot developer account. HubSpot is also a **Link first** provider: people link it to an
account they already have, and nobody can create an account with it.

**Apple** is **Sign in with Apple**, for people who sign in with their Apple Account. It has no
client secret to copy. Its **client ID** is a **Services ID**, and in place of a secret you give
Apiome a **private key** — the `.p8` file of a Sign in with Apple key — with the key's **Key ID**
and your Apple Developer **Team ID**. Apiome uses the key to sign a fresh, five-minute client
secret for each sign-in, so there is nothing to renew; to rotate, see
[Rotate Apple's private key](#rotate-apples-private-key). People who choose **Hide My Email** share
a private relay address with Apiome, which never matches the address on an account they already
have — see [Apple and Hide My Email](#apple-and-hide-my-email).

**Facebook** is **Facebook Login**, for the many people whose main online identity is Facebook. Its
endpoints are fixed, so it needs only a client ID and a client secret — the **App ID** and **App
secret** of an app in Meta for Developers. Facebook is a **Link first** provider: people link it to
an account they already have, and nobody can create an account with it.

**X (Twitter)** is **Sign in with X**, for the developer-adjacent audience on X. Its endpoints are
fixed, so it needs only the **OAuth 2.0 Client ID** and **Client Secret** of an app in the X
Developer Portal. X often shares no email address at all, and Apiome never trusts the one it does
share, so X is a **Link first** provider: people link it to an account they already have, and
nobody can create an account with it.

## Register the OAuth application

Each provider needs an OAuth (or OIDC) application registered on its side. Its **callback** or
**redirect URI** is:

```text
<BETTER_AUTH_URL>/api/auth/oauth2/callback/<id>
```

where `<BETTER_AUTH_URL>` is the public URL of the Apiome web app and `<id>` is the provider's id from
the table — for example `https://apiome.example.com/api/auth/oauth2/callback/github`. Copy the
application's **client ID** and **client secret**; issuer-based providers also give you an
**issuer** URL, such as `https://acme.okta.com/oauth2/default`.

### Settings on the provider's side

Apiome requests the scopes it needs itself and trusts an email address only when the provider says
it is verified — a missing claim counts as unverified (see
[How a provider's email is trusted](#how-a-providers-email-is-trusted)). A few providers need more
than the callback URI:

| Provider | Where to register | What else to set |
| --- | --- | --- |
| GitHub | **Settings → Developer settings → OAuth Apps → New OAuth App** (or the organization's settings) | Nothing — copy the client secret straight away; GitHub shows it once |
| GitLab | **Settings → Applications → Add new application** (user, group or instance) | Tick **Confidential** and the **`read_user`** scope. For a self-managed instance, set **Base URL** |
| Microsoft | Entra admin center: **Identity → Applications → App registrations → New registration**, platform **Web** | Copy the secret's **Value**, not its ID. **Add the `xms_edov` optional claim** (Token configuration → ID token) — without it every Entra address counts as unverified and people must verify their email instead of joining their tenant. Single-tenant apps set **Tenant** |
| Google | Cloud console: **APIs & Services → Credentials → OAuth client ID**, type **Web application** | Configure the consent screen first (**Internal** for one Workspace). **Workspace domain** rejects any account outside that domain — the check is on the returned token, not just the sign-in page |
| Okta | **Applications → Create App Integration → OIDC → Web Application** | Assign who may sign in. Issuer: `https://<okta-domain>/oauth2/default`, or `/oauth2/<server-id>` for a custom authorization server |
| AWS (Cognito) | User pool: **App integration → App clients**, a confidential client with the authorization-code grant | Configure a Cognito **domain** for the Hosted UI. Issuer: `https://cognito-idp.<region>.amazonaws.com/<user-pool-id>` |
| Keycloak | Realm: **Clients → Create client**, OpenID Connect with client authentication on | Map `email` and `email verified` onto the ID token. Issuer: `https://<host>/realms/<realm>` |
| OIDC | A confidential client with the authorization-code grant | The issuer must serve `<issuer>/.well-known/openid-configuration` and emit `email` and `email_verified` |
| Auth0 | **Applications → Create Application → Regular Web Applications** | Issuer: `https://<tenant>.auth0.com`, or your custom domain |
| Atlassian | [Developer console](https://developer.atlassian.com/console/myapps/): **Create → OAuth 2.0 integration** | Under **Permissions**, add the **User identity API** with the **`read:me`** and **`read:account`** scopes. | Bitbucket | Workspace **Settings → OAuth consumers → Add consumer** | Keep **This is a private consumer** ticked. | Slack | [api.slack.com/apps](https://api.slack.com/apps): **Create New App → From scratch** | Under **OAuth & Permissions**, add the callback URL to **Redirect URLs** — Slack accepts only `https://` URLs — and add **`openid`**, **`profile`** and **`email`** to **User Token Scopes**. No issuer |
| LinkedIn | [Developer Portal](https://www.linkedin.com/developers/apps): **Create app** | The app must be associated with a **LinkedIn Page**. Keep the same app once people have signed in: LinkedIn identifies each person per app, so a new app does not recognize them. No issuer |
| Discord | [Developer Portal](https://discord.com/developers/applications): **New Application** | On the **OAuth2** page, **Add Redirect** with the callback URL and **Save Changes**. | Salesforce | Salesforce **Setup**: **External Client App Manager → New External Client App**, or **App Manager → New Connected App** | Turn on **Enable OAuth Settings**, enter the callback URL as the **Callback URL**, and add the scopes **Access the identity URL service (id, profile, email, address, phone)** and **Access unique user identifiers (openid)**. | Notion | [Integrations](https://www.notion.so/profile/integrations): **New integration**, type **Public** | Add the callback URL under **Redirect URIs**. | Figma | [Developer apps](https://www.figma.com/developers/apps): **Create a new app** | On the **OAuth credentials** tab, add the callback URL under **Redirect URLs**; the **Client ID** and **Client secret** are on the same tab, and Figma shows the secret once. | Linear | Linear **Settings → API → OAuth applications**: [new application](https://linear.app/settings/api/applications/new) (a workspace admin creates it) | Add the callback URL under **Callback URLs**. Apple accepts only `https` addresses on a real domain, not `localhost`. Create a key with **Sign in with Apple** turned on, download its `.p8` file — Apple offers it only once — and note its **Key ID** and your **Team ID**. Apiome asks for the **name** and **email** scopes only. To mail people who use Hide My Email, register the domain Apiome sends mail from under **Sign in with Apple for Email Communication**. No issuer |
| Facebook | An app in [Meta for Developers](https://developers.facebook.com/apps/) with the **Authenticate and request data from users with Facebook Login** use case | Under **Facebook Login → Settings**, add the callback URL to **Valid OAuth Redirect URIs**; Facebook requires an exact match over HTTPS. Keep the **`email`** and **`public_profile`** permissions — the only ones Apiome asks for — and leave **Require App Secret** off under **App settings → Advanced**. The **App ID** (client ID) and **App secret** (client secret) are on **App settings → Basic**. Until you switch the app to **Live**, only people with a role on the app can sign in. Apiome reads the name, email address and picture of the person signing in; it reads no pages, posts or friends. Facebook does not say whether an email address is verified, so people link Facebook from **Linked accounts** before they can sign in with it. No issuer |
| X (Twitter) | Your app in the [X Developer Portal](https://developer.x.com/en/portal/dashboard) → **User authentication settings → Set up** | Turn on **OAuth 2.0** and choose **Web App, Automated App or Bot** — a **Native App** has no client secret, and Apiome cannot use it. Add the callback URL under **Callback URI / Redirect URL**; X requires an exact match. Fill in **Website URL**, and turn on **Request email from users** (it needs a privacy policy and terms of service URL) for X to share email addresses. Copy the OAuth 2.0 **Client ID** and **Client Secret** — not the API key and secret. Apiome asks for the **users.read**, **tweet.read** and **users.email** scopes only, and uses them to read the name, email address and picture of the person signing in; it reads and posts no posts, followers or messages. X often shares no email address and Apiome does not trust the one it shares, so people link X from **Linked accounts** before they can sign in with it. No issuer |
| HubSpot | A **public app** in your [HubSpot developer account](https://developers.hubspot.com/) | On the app's **Auth** settings, add the callback URL as a redirect URL; HubSpot requires an exact match. Keep **`oauth`** as the only required scope — the only one Apiome asks for; a required scope Apiome does not ask for makes HubSpot refuse the sign-in. The **Client ID** and **Client secret** are on the same page. Apiome reads the email address of the person signing in and nothing else; it reads no contacts, companies, deals or other HubSpot data. HubSpot does not say whether an email address is verified, so people link HubSpot from **Linked accounts** before they can sign in with it. No issuer |

## How a provider's email is trusted

A provider sign-in **joins an existing account**, or **creates a new one**, only when the provider
proves the email address is verified. Apiome never takes an address on trust: a provider that let
someone claim an address they do not own would hand them that person's account. Each provider is in
one of three classes:

| Class | What the provider gives Apiome | What a sign-in does | Providers |
| --- | --- | --- | --- |
| **Trusted** | An email address and proof it is verified | Joins the account with that address, or creates one. An address the provider does not report as verified is refused: *Your sign-in provider could not confirm that your email address is verified…* | GitHub, GitLab, Microsoft, Google, Okta, AWS (Cognito), Keycloak, OIDC, Auth0, LINE, Atlassian, Bitbucket, Slack, LinkedIn, Discord, Salesforce, Dropbox, Zoom, Hugging Face, Vercel, Apple |
| **Link first** | An email address, with no proof it is verified | Never matches an account by email. Signs in only people who have already linked the provider | VK, Notion, Figma, Linear, Railway, HubSpot, Facebook, X (Twitter) |
| **Link only** | No email address | The same as **Link first** — there is no address to match | WeChat |

For a **Link first** or **Link only** provider, people **sign in another way first**, link the
provider on [Linked accounts](../workspace/linked-accounts.mdx), and can sign in with it from then
on. The class is fixed per provider and is not a setting: no administrator option makes Apiome
trust an unproven address.

Someone who tries a **Link first** provider before linking it — to sign up, or to sign in for the
first time — is sent back to the sign-in page with *Your sign-in provider could not confirm that
your email address is verified…*, even when the address matches their account. Nothing is created
or linked.

**LINE** sends its verified claim only when the channel has the approved email permission; without
it, LINE behaves as **Link first**. **Microsoft** needs the `xms_edov` claim — see the table above.

### Apple and Hide My Email

When someone signs in with Apple they can choose **Hide My Email**. Apple then shares a private
relay address, such as `x7k2p9q4mz@privaterelay.appleid.com`, that forwards to their real inbox.
Apple reports the relay address as verified, so Apiome treats it like any verified address — but:

- **It never matches an existing account.** Someone whose Apiome account uses their real address
  and who signs in with Apple and **Hide My Email** gets a **new** account under the relay address.
  To use Apple with the account they already have, they **sign in the usual way first**, open
  [Linked accounts](../workspace/linked-accounts.mdx) and **click “Link”** on the Apple card. From
  then on **“Continue with Apple”** signs in that account, whichever address Apple shares.
- **Mail reaches it only from a registered domain.** Register the domain Apiome sends invitations
  and notifications from under **Sign in with Apple for Email Communication** in the Apple
  developer account; mail from any other domain to a relay address is dropped.
- **A sign-up domain allowlist refuses it.** If new accounts are limited to certain email domains,
  `privaterelay.appleid.com` is not one of them, so a relay address cannot create an account;
  linking still works.

Apple sends the person's name only the first time they allow Apiome. Apiome stores it then, and
later sign-ins keep it.

Developers adding a provider record its class in
`apiome-ui/lib/auth/provider-trust-classes.ts`; the per-provider guide lists the class of every
provider in the Better Auth catalog, including those not yet available.

## Add a provider

1. **Click “Add Provider”** at the top right.
2. **Search** or scroll the list and **click the provider** — for example **Okta**.

   <Screenshot id="admin-auth-provider-add" alt="The Add Provider dialog searched for o, listing Google, Keycloak, OIDC and Okta with their ids" />

3. In **Configure Okta**, choose the **Enablement**:
   - **Enabled** — turn the provider on, using the credentials stored here;

4. Enter the **Client ID**, the **Client secret** and any extra settings, such as the **Issuer**.

5. **Click “Save”**. The provider's card appears in the list.

## Edit a provider

Each card carries the same fields. Its chip says how the provider is enabled now — **Enabled
(database)**, **Disabled (database)** or **Env-derived** — and every field that has no stored value
shows **using .env fallback**.

- **Change a field** and **click “Save”**. Only the fields you changed are sent. A **Saved** note
  confirms it, and the footer reads *Last changed … by …*.
- **The client secret is write-only.** The card shows only **Secret: set** or **Secret: not set** —
  never the value. **Type a new value** to replace it, or **click “Clear stored secret”** to remove it
  on the next save (the provider then uses `.env`); **Undo** cancels that.
- **Choosing “Enabled” needs every required field stored here.** Values in `.env` do not count. If
  one is missing, saving is refused and the card lists what to fill in.
- **Apple's card names its fields as Apple does.** **Services ID** is the client ID, and
  **Private key (.p8)** is the write-only secret: paste the whole `.p8` file — the field drops its
  line breaks, and Apiome reads it either way. **Team ID** and **Key ID** are extra settings.

Changes reach the sign-in page on the next sign-in, after the configuration cache expires — within
30 seconds by default (`AUTH_PROVIDER_CONFIG_CACHE_TTL_MS`, 5–60 seconds). No restart is needed.

### Rotate Apple's private key

Apple's client secret is signed afresh for every sign-in, so it never expires. Rotate the private
key itself — on a schedule, when someone with access leaves, or at once if the `.p8` file may have
leaked:

1. In the Apple developer account, **create a new key** with **Sign in with Apple** turned on and
   **download its `.p8` file**.
2. On the Apple card, **paste the new file into Private key (.p8)**, **enter its Key ID** and
   **click “Save”**. The next sign-in uses the new key; nobody is signed out.
3. **Revoke the old key** in the Apple developer account. A team can have two Sign in with Apple
   keys at a time, so the old one keeps working until you revoke it.

## Validate a provider

**Click “Validate”** to check whether the stored configuration is complete:

- *Database configuration is complete — this provider can be enabled.*
- *Not ready to enable — missing: …* — save the listed fields on the card first.

For **OIDC**, Validate also fetches the issuer's discovery document
(`<issuer>/.well-known/openid-configuration`) and reports the error if it cannot be read, so a wrong
issuer fails here rather than on the sign-in page.

## Remove a provider

**Click “Remove”** and then **“Remove provider”** to confirm. This deletes the provider's stored row —
client ID, stored secret, enablement override and settings — and sign-in for the provider falls back
to `.env`. A removed secret cannot be recovered. The provider then appears in **Add Provider** again.

## If a saved provider does not appear at sign-in

Sign-in reads what you save here from the REST API each time, and falls back to `.env` when it
cannot. The server log of the app (or Studio) says which case you are in:

| Log line | Meaning | Fix |
| --- | --- | --- |
| `INTERNAL_SERVICE_TOKEN is not set` | That container has no service token, so it never asks | Set the same `INTERNAL_SERVICE_TOKEN` there as on the REST API |
| `resolved endpoint fetch to <url> failed` | The REST API was not reached at `<url>` | Set `REST_API_BASE_URL` in that container to the REST API's address on its network, such as `http://rest:8000/v1` — `localhost` inside a container is the container itself |
| `resolved endpoint returned <status>` | The REST API answered with an error | `503`: the REST API has no token. `403`: the two tokens differ |

Studio serves its own sign-in routes, so it needs both variables as well.

## With the API

The console calls the REST API's super-admin endpoints:

- `GET /v1/admin/auth-providers` — every provider's configuration, with secrets masked;
- `PUT /v1/admin/auth-providers/{provider_id}` — update the fields sent;
- `DELETE /v1/admin/auth-providers/{provider_id}` — remove the stored row;
- `GET /v1/admin/signup-policy` — the sign-up policy in effect, and whether it is stored or
  comes from `.env`;
- `PUT /v1/admin/signup-policy` — store the policy (with `blocked_email_domains`), or send
  `"mode": null` to remove the stored one;
- `GET /v1/admin/signup-policy/blocked-attempts` — the sign-up attempts an abuse guard refused,
  newest first (`limit`, 1–200).

See the [API reference](../reference/api-reference.md). There is no CLI command for the sign-up
policy or sign-in providers.
