This page is the starting point for the people who **run** an Apiome installation rather than
use it: how the services fit together, where each one is configured, and the runbooks for
deploying, backing up and triaging. The screens operators use day to day — the admin console, the
data browser and migrations — have their own pages in this group.

## The stack

`docker compose up` from the repository root runs the back end; the web app (`apiome-ui`) runs
beside it (`yarn dev` in development, its own image in production).

| Service | What it is | Host port (default) |
| --- | --- | --- |
| `postgres` | The database every service shares | `5432` (`POSTGRES_PUBLISH_PORT`) |
| `migrate` | Applies the `apiome-db` migrations, then exits | — |
| `seed` | Loads the development seed data, then exits (never in production) | — |
| `rest` | `apiome-rest`, the REST API | `8000` (`APIOME_REST_HTTP_PORT`) |
| `mcp` | `apiome-mcp`, the MCP server | `8765` (`APIOME_MCP_HTTP_PORT`) |
| `mock` | `apiome-mock`, the mock runtime | `8775` (`APIOME_MOCK_HTTP_PORT`) |

Production applies
[`docker-compose.prod.yml`](https://github.com/apiome/apiome/blob/main/docker-compose.prod.yml) on
top of [`docker-compose.yml`](https://github.com/apiome/apiome/blob/main/docker-compose.yml): it adds
`caddy` (TLS from Let's Encrypt, the only service with host ports — `80` and `443`), `backup`
(encrypted scheduled backups) and the Studio image, and keeps `seed` out of `up`.

To try Apiome on one machine, follow [Run Apiome locally](../getting-started/run-locally.md).

### Domains, sign-in redirects and the session cookie

The web app and Studio share one sign-in. Two things follow from the hostnames you deploy them on:

- **The session cookie** is scoped to the installation's *registrable domain* — the part of the
  hostname you own. For `app.example.com` that is `.example.com`; for `app.example.co.uk` it is
  `.example.co.uk`.
- **After sign-in, a person can be sent** to any `https` host under that same domain, or to one of
  the app URLs you configured (`BETTER_AUTH_URL`, `NEXT_PUBLIC_MAIN_APP_URL`,
  `NEXT_PUBLIC_STUDIO_URL`). Any other address is replaced with the default landing page.

Apiome finds the registrable domain with the [Public Suffix List](https://publicsuffix.org/), so a
shared hosting domain is never mistaken for yours:

| The app is served from | Cookie domain | Also trusted after sign-in |
| --- | --- | --- |
| `app.example.com` | `.example.com` | every `https` host under `example.com` |
| `app.example.co.uk` | `.example.co.uk` | every `https` host under `example.co.uk` |
| `apiome.vercel.app` | `.apiome.vercel.app` | hosts under `apiome.vercel.app` only — not other `*.vercel.app` sites |

`BETTER_AUTH_COOKIE_DOMAIN` overrides the cookie domain. Set it only to a domain you own: a value
that does not match the app URLs, or that is a public suffix such as `.co.uk` or `.vercel.app`, is
ignored and the domain is worked out from the app URLs instead.

Two consequences for how you lay out hosts:

- **Put the web app and Studio under one domain you own** (`app.example.com` and
  `studio.example.com`) to share a sign-in between them. On a hosting platform's shared domain
  they are separate sites: the session cookie is not shared between them, and Studio is a trusted
  destination only when `NEXT_PUBLIC_STUDIO_URL` names it.
- **Every host under your domain is inside the sign-in boundary.** A forgotten DNS record that
  points at a service you no longer run can be claimed by someone else, and would then receive the
  session cookie. Remove DNS records when you retire a host, and review the records under the
  domain from time to time.

### What sign-in does when the database is unreachable

Each time a session is read, Apiome checks the person's active workspace against their memberships
in the database. If that check cannot run — the database is down or unreachable — the session is
given **no active workspace** rather than the one the browser remembers, because the remembered
value comes from a cookie and cannot be trusted unchecked.

People stay signed in, but pages that need a workspace cannot load until the database answers
again. Nothing has to be reset afterwards: the next request restores the workspace. The web app's
log records each failed check as `[post-login-routing] membership lookup failed`.

### Sign-up security check

The email sign-up form can carry a [Cloudflare Turnstile](https://developers.cloudflare.com/turnstile/)
check, so scripts cannot create accounts in bulk. It is off by default. To turn it on, add a
Turnstile widget for your Apiome domain in the Cloudflare dashboard, then set both keys in
`apiome-ui/.env` and restart apiome-ui:

| Variable | What it is |
| --- | --- |
| `TURNSTILE_SITE_KEY` | The widget's public site key; the browser draws the check with it |
| `TURNSTILE_SECRET_KEY` | The widget's secret key; apiome-ui checks each answer with Cloudflare |

With only one of them set, the check stays off. While it is on, **Create account** waits for the
check, and the form is refused if Cloudflare does not confirm the answer — or cannot be reached.
Provider sign-up and **Resend email** never show it. Refusals are listed under
[Recent blocked sign-ups](./auth-providers.mdx#abuse-protection); they reach it only when
`INTERNAL_SERVICE_TOKEN` is set on apiome-ui and apiome-rest, like every sign-in event.

### Email for notifications

The REST API emails some notifications — today, catalog
[drift email](../bring-in/catalog-refresh.mdx#drift-email). It sends with SendGrid, like email
sign-up in the web app. Set both in `apiome-rest/.env` (or the `rest` service's environment) and
restart apiome-rest:

| Variable | What it is |
| --- | --- |
| `SENDGRID_API_KEY` | The SendGrid key Apiome sends email with — the same key as apiome-ui's |
| `EMAIL_FROM` | The sender address, for example `Apiome <no-reply@apiome.example>` |
| `APIOME_UI_PUBLIC_URL` | The public address of the web app, which the links in an email point at |

With either of the first two missing, nothing is emailed and nothing fails: the other channels of a
notification still go out. A refused or failed send is logged by apiome-rest without the message.

### Largest spec the import wizard accepts

The **Import** wizard on **Projects** and **Versions** sends the whole parsed spec to apiome-ui in
one request, which is capped at **25 MB** by default. A larger spec fails with *Body exceeded … limit*.
To raise the cap, set `APIOME_SERVER_ACTION_BODY_LIMIT` (for example `50mb`) in `apiome-ui/.env`
**before building** apiome-ui. The value is baked into the build, so rebuild the image after
changing it. **Import to catalog** uploads through the REST API instead and is not affected.

### Keys that encrypt stored secrets

Some settings are encryption keys: they seal a secret before it is written to the database, so a
copy of the database on its own does not reveal it. Each is optional at start-up, and each fails
closed — without the key the secret is not stored, never stored unencrypted.

| Variable | Set in | Encrypts |
| --- | --- | --- |
| `APIOME_LINKED_ACCOUNT_TOKEN_ENCRYPTION_KEYS` | `apiome-ui` **and** `apiome-rest` (identical) | The sign-in tokens and personal access tokens of [linked accounts](../workspace/linked-accounts.mdx) |
| `AUTH_CONFIG_ENC_KEY` | `apiome-rest` | Client secrets saved on [Sign-in providers](./auth-providers.mdx) |
| `APIOME_MCP_CREDENTIAL_ENCRYPTION_KEYS` | `apiome-rest` | Credentials for protected MCP servers |
| `APIOME_SDK_REGISTRY_CREDENTIAL_ENCRYPTION_KEYS` | `apiome-rest` | npm and PyPI publish tokens |
| `APIOME_UPSTREAM_CREDENTIAL_ENCRYPTION_KEYS` | `apiome-rest` | Credentials a managed MCP toolset presents to your API |

Each `…_ENCRYPTION_KEYS` value is a JSON object that maps a key version to a base64-encoded
32-byte key. Single-quote it in a `.env` file:

```bash
APIOME_LINKED_ACCOUNT_TOKEN_ENCRYPTION_KEYS='{"1": "<base64 key>"}'
```

Generate a key with:

```bash
python3 -c "import base64, os; print(base64.b64encode(os.urandom(32)).decode())"
```

Store these keys in your secret manager. A lost key cannot be recovered, and the secrets it sealed
have to be entered again.

#### Linked-account tokens

The web app encrypts a linked account's tokens when it saves them, and the REST API decrypts them
to read a repository, so both must hold the same `APIOME_LINKED_ACCOUNT_TOKEN_ENCRYPTION_KEYS`.

When the key is **not set**, people can still sign in and link providers, but:

- no provider token is stored, so scans and imports of private repositories report a missing token;
- saving a Personal Access Token is refused, with a message that names the variable.

An account linked during that time has no stored token. After you set the key, its owner adds a
Personal Access Token, or unlinks the provider and links it again.

**Upgrading an installation that already has linked accounts.** Tokens saved before this
encryption existed stay readable, and stay unencrypted until you seal them. After you set the key
in both services and deploy, run this once in the `rest` service (`docker compose exec rest …`), or
from `apiome-rest` in a source checkout:

```bash
python -m app.seal_linked_account_tokens --dry-run   # reports counts, changes nothing
python -m app.seal_linked_account_tokens
```

The command prints counts only and is safe to run again. The
[Production deployment](https://github.com/apiome/apiome/blob/main/docs/runbooks/PRODUCTION_DEPLOY.md)
runbook has the Compose form of these steps.

**Rotating the key.** Add a higher version to the map in both services —
`'{"1": "<old key>", "2": "<new key>"}'` — deploy, and run the same command. It re-encrypts every
token under the newest version. Remove the old version once the command reports
`"tokens_resealed": 0`.

## Repair items with no captured source

Exports, conversions and the schema test bench are built from the source file each catalog revision
captured at import. A revision without one cannot be exported, and its users are told to re-import
it. `scripts/backfill_captured_sources.py` repairs the revisions it can, from a copy that is still
stored:

- **another revision of the same item** in the same format, or
- **the linked repository file** a repository-imported item came from, re-read at its recorded branch
  and path.

A copy is only used when it re-imports to the exact fingerprint the revision recorded, so text from
a different version is never stored. A repository file is scrubbed under the workspace's secret-scrub
policy first. Revisions that recorded no fingerprint are left alone and reported as `unverifiable`.

Run it from `apiome-rest`, with a dry run first:

```bash
PYTHONPATH=src python scripts/backfill_captured_sources.py --dry-run
PYTHONPATH=src python scripts/backfill_captured_sources.py            # every workspace
PYTHONPATH=src python scripts/backfill_captured_sources.py --tenant <tenant-uuid>
```

It prints how many revisions it scanned and repaired, and how many it could not repair and why
(`unverifiable`, `no_copy`), with one outcome per revision. Each repaired revision records where its
source came from in `sourceBackfilledFrom`. It is safe to run again.

## Watch exports

Before Export studio opens to everyone, watch how exports are doing. Sign in as a platform
administrator and **open `/v1/ops/dashboard`** on the REST API. The **Export health** card refreshes
every 5 seconds and shows:

| Row | Means |
| --- | --- |
| *n%* **failed** | Failed export jobs as a share of completed + failed ones. Canceled jobs count in neither. |
| **alert** | `ok`, `firing`, `no-data` (too few jobs in the window to judge) or `off` |
| **success rate** | Completed jobs as a share of completed + failed ones |
| **last 15 min** | How many of the jobs in the alert window failed |
| **alert at** | The failure rate and the fewest jobs the alert needs to fire (*20% of 10+ jobs*) |
| **p95 job time** | 95% of export jobs finished within this time (*≤ 30 s*), from when the job started running to its end. *> 1800 s* means the slowest jobs ran past the 30-minute job cap. |
| *target* **failed** | The five targets with the most failed jobs, with each one's failure rate |

`GET /v1/ops/import-export` returns the same numbers under `export_health`, with every target, its
failure codes and the duration histogram. The numbers are kept per server process and start again
from zero when it restarts, so with several replicas, check each one.

### The failure-rate alert

The alert **fires** when, over the last 15 minutes, at least 10 export jobs completed or failed and
at least 20% of them failed. It clears when the rate drops back under 20%, or when fewer than 10 jobs
remain in the window. Each time it fires or clears, the REST API logs one `export.failure_rate_alert`
line (a warning when it fires), so a log-based alert rule can page on it:

```sh
grep '"event": "export.failure_rate_alert"' rest.log | jq '{state, window_failed, window_jobs, window_failure_rate}'
```

Change the thresholds on the REST API:

| Setting | Default | Means |
| --- | --- | --- |
| `APIOME_EXPORT_FAILURE_ALERT_RATE` | `0.2` | Share of failed jobs that fires the alert. `0` turns the alert off. |
| `APIOME_EXPORT_FAILURE_ALERT_MIN_JOBS` | `10` | Fewest completed or failed jobs in the window before the alert can fire |
| `APIOME_EXPORT_FAILURE_ALERT_WINDOW_SECONDS` | `900` | How far back the alert looks |

When it fires, the **Export health** card names the targets that fail most, and
`GET /v1/ops/import-export` gives each one's failure codes. The codes are explained in
[Export a spec](../ship/export-a-spec.md).
